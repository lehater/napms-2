---
name: execute-task
description: Execute a prepared NAPMS GitHub Issue under the AI task workflow. Use for a Ready issue with an execution contract, from eligibility checks through a pull request and verification evidence.
---

1. Read [.ai/workflow.yaml](../../../.ai/workflow.yaml), the GitHub Issue and its Project item. Validate the saved Issue with `gh issue view <number> --json body --jq .body | python3 scripts/validate-task` (R2). Check contract freshness, executor capability, and unresolved decisions (R4, R5, R7). The optional `.[workflow]` dependencies are required. Use the Issue body from the GitHub connector when CLI access is unavailable.
2. The coordinator runs `python3 scripts/check-task-admission <number>` immediately before assignment. Use authenticated GitHub CLI with read access to the repository and Project #6 (for a classic token, `read:project`). The command checks Open/Ready, native blocker completion, and existing assignees (R1, R3, R6). Stop on `DENY`, a command failure, or missing evidence. An `ALLOW` covers those GitHub checks. Confirm no other executor is working, including work started outside GitHub.
3. One coordinator handles assignments at a time. After all R1–R7 checks pass, record the executor as the issue assignee and set Project Status to Running. Confirm both writes before starting the Worker in a dedicated branch or worktree. If either write fails, reconcile the issue and project state before retrying.
4. For a manually managed worktree, the coordinator creates it with `python3 scripts/task_worktree.py create --issue <number> --branch <branch>` from the primary checkout, after fetching `origin/main`. Use the canonical sibling directory `../.worktrees/<repository>/issue-<number>`; do not invent `/tmp` paths. If it exists, inspect and reuse only after verifying identity; never overwrite. For ordinary tasks, **reuse the primary checkout's installed dependencies**: after verifying unchanged `pyproject.toml` and Web package/lock manifests, run `python3 scripts/task_worktree.py link-env --issue <number> --branch <branch> --path <absolute-path> --base-sha <full-creation-base-sha> --scope <git|python|web|mixed>` from the primary checkout. This only creates ignored symlinks to primary `.venv` and `web/node_modules`; it does not install packages. For docs-only tasks, use `--scope git` without dependencies. For changed dependency manifests or incompatible tools, create an **isolated local environment** in that worktree instead; never overwrite or relink an existing path. Run `python3 scripts/task_worktree.py preflight --issue <number> --branch <branch> --path <absolute-path> --base-sha <full-creation-base-sha> --scope <git|python|web|mixed>` before handing the Worker its absolute path, branch, pinned base SHA (printed by `create`) and check result. Stop on DENY; loopback `EPERM` requires an approved execution environment, not repeated retries. Codex-managed `--worktree` paths remain managed by Codex and must not be relocated implicitly.
5. Implement within the contract's scope. For Python/Web tasks, use `make check` for local iterations and `make check-full` only for required integration/diagnosis: the Makefile uses `.venv/bin/python`, which may be a shared link, and forces `PYTHONPATH` to the **active** worktree's `src` (including subprocesses and Web E2E via `NAPMS_PYTHON`). For documentation-only tasks, use `--scope git`, `git diff --check`, and OpenSpec strict only when applicable; avoid installing unrelated runtimes. Never run tests with another checkout's `PYTHONPATH`; using the shared interpreter with the active checkout's source is intentional. Never run `pip install` or `npm ci` in a worktree with shared dependency links. The existing Fast/Full policy remains authoritative. `scripts/check-fast.py` bounds each local check (default 600 seconds; `--timeout-seconds` overrides it); diagnose a timeout instead of polling indefinitely or blindly restarting FULL. If a required decision or material contract change prevents progress, record the reason in the Issue and return to Preparing.
6. Open and link the pull request, record verification evidence, and set Project Status to Review. Record owner acceptance and required integration before closing the Issue as completed and setting Done. After merge, check `git status --porcelain` inside the worktree, preserve any uncommitted/unique data, and only then remove it with `git worktree remove <path>` (no `--force`). Never delete a worktree still used by an agent or server.

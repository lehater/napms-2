# Контракт REAL ConnectivityNeed для #141–#143

## Context

D-04 определяет Interaction как направленную пару компонентов внутри приложения. D-06 связывает её с процессом и участником через Need. Принятые #108–#110 определяют обоснование, жизненный цикл и историю. #126 уже ввела в каталоге подпись по направлению. Для этой работы важна граница между выбором **взаимодействия для процесса** и выбором **точных сетевых условий для заявки**. [Домен](../../../docs/domain.md) · [Аудит REAL на main](../../../docs/research/connectivity-need-ux/README.md)

Предшествующие дельты описывают принятые этапы. В части входа через Sidebar и размещения композиции этот контракт обновляет «REAL acceptance navigation» и «Create real request from saved Need» из `compose-access-request-from-need`. В части входного селектора он расширяет «Protected Process-scoped Need list and creation» из `persist-connectivity-need`. Путь по Revision остаётся доступен старым клиентам. Правила `business-connectivity-lifecycle` применяются к обоим входам.

## Decisions

Владелец согласовал пункт «Потребности» в группе «Бизнес-контекст», пять колонок реестра, создание через процесс и Interaction с фильтром приложения, обязательный businessBasis, три вкладки карточки и отдельный экран композиции заявки.

### Два входа, одна карточка

| Экран | Содержание и действие |
| --- | --- |
| «Бизнес-контекст → Потребности» | Реестр на `/connectivity-needs`. Колонки «Потребность», «Бизнес-процесс», «Взаимодействие», «Исходный компонент», «Статус». Первая ведёт в Need, три связи ведут в соответствующие REAL-карточки. Одна строка на сохранённый ID, в том числе RETIRED и записи архивированных процессов. |
| Процесс → «Потребности» | Та же строка и действия в пределах процесса. Его имя уже в шапке, поэтому отдельную колонку процесса можно опустить. |
| «Создать потребность» | Одна форма по `/connectivity-needs/new`. Из реестра выбирают активный процесс, из процесса он предзаполнен и зафиксирован. Затем необязательный фильтр приложения, выбор Interaction, показ вычисленного исходного участника и обязательное обоснование. Для сохранения достаточно подходящего Interaction и процесса, развёртывания могут появиться позже. |
| Карточка | Канонический URL — действующий `/business-processes/{pid}/needs/{nid}`. «Обзор» показывает процесс и его статус, направление и участника кратко, обоснование и статус Need, действия редактирования, retire/restore. «Коммуникация» показывает приложение и направленную пару с доступными ссылками на Interaction и Components. «Заявки» сохраняет постраничную историю, дату, статус и переход в Request → Decision → Rule по выданной сервером связи. |
| «Создать заявку» | Действие в карточке открывает `/business-processes/{pid}/needs/{nid}/requests/new`. Пользователь проверяет ревизию, выбирает source/destination Deployment, сверяет обе стороны и все trafficClauses, подтверждает. Успех открывает `/access-requests/{requestId}`, отмена возвращает в открывавшую вкладку Need. Старый вход `/access-requests/new` по-прежнему позволяет выбрать сохранённую Need. |

Используем Shell/Frame, CollectionView с EntityTable для реестра, EntityTable во вкладках процесса и заявок, DetailView для карточки, существующую ComposeRequest в отдельном маршруте, Button, Badge, ErrorNotice и подписанные нативные поля формы. Отдельный экран нужен для отмены выбора и подтверждения одной операции. Загрузка, пустая страница и отказ сервера имеют разные сообщения. Переключение actor очищает защищённые данные, черновые выборы и подтверждение. Реестр первой версии поддерживает только листание и переход в контекст процесса. Для текстового поиска и дополнительных фильтров нет подтверждённого сценария, поиск по одной загруженной странице дал бы неполный результат.

Название Need берётся из фактов процесса и направления. Interaction — «Приложение · Источник → Назначение», участник — имя исходного компонента. У нескольких исторических записей подписи могут совпасть: ключом строки и ссылки служит ID. При отсутствии фактического имени показывать «Название не задано», при недоступной связи — текст без выдуманной ссылки. UUID уместен в технических деталях. Исторический NULL basis показывается как незаполненное обоснование и доступен для исправления.

Маршруты вкладок и возврата закреплены в [навигационном контракте](../../../docs/ux/real-navigation.md). Адрес входа и смещения списков переживают reload, даже если вкладку открыли напрямую. Прямая ссылка без контекста возвращает к Needs её процесса. Связь из реестра и process-scoped deep link используют один и тот же авторизованный detail GET.

### Чтение реестра (#141)

Добавить `GET /connectivity-needs?limit=&offset=&processId=`. Без `processId` это все доступные Needs, с ним — проекция для вкладки процесса. Не обходить клиентом процессы или отдельные detail по одному на строку. Контекстный GET `/business-processes/{pid}/needs` сохраняет прежние DTO, порядок и семантику. Общая пагинация имеет пределы существующего ListQuery (по умолчанию 20, 1–100, offset ≥ 0). Стабильная сортировка по Need ID, один ID на строку, включая alias-историю. Применить scope и ограничение процесса до limit/offset/hasMore. Ответ `{items, limit, offset, hasMore}`, без общего счётчика. За последней страницей — пустой результат с hasMore=false.

Строка содержит текущие поля Need плюс краткие связанные объекты из detail: process (ID, имя, статус), interaction (canonical ID, applicationId и подпись направления), participant (ID, applicationId и имя). Источники — сохранённый Process, каноническая направленная пара и таблицы имён. Для строки не загружать историю заявок. Для вкладки коммуникации расширить detail полями назначения `destinationComponentId` и `destinationComponentName` внутри interaction, nullable для отсутствующей исторической связи. Ссылка каталога проходит собственную проверку доступа.

GET проверяет bearer actor до раскрытия данных. Те же effective `business.process.read` и `business.need.read` в `demo-business`, что у scoped read. В настроенном локальном shared-read действует то же исключение для чтения. 401/403 без записей, имён или количества, 404 для авторизованного запроса неизвестного процесса, 422 для некорректной пагинации или неизвестных ключей. Защищённые ответы не кэшируются. В обычном Vite proxy и local-demo добавить новый API-путь с разрешённым методом GET. HTML-навигация по тому же адресу открывает SPA. В #142 local-demo также должен пропускать новый GET вариантов взаимодействий. Actor видит историю по существующим правилам Request detail (свои, либо доступные decider/shared-read).

### Создание по взаимодействию (#142)

Добавить `GET /business-processes/{pid}/need-interaction-options` с необязательным `applicationId` и общей пагинацией. Возвращать на Interaction одну запись с canonical interactionId, applicationId/Name и ID/именами source/destination Components. Использовать тот же допуск, что у существующих вариантов создания: опубликованная согласованная пара внутри приложения, все её ревизии согласны о ролях, tuple ещё свободен с учётом aliases и RETIRED. Ни портов, ни проверки существования Deployment для выбора Need не требуется. Отбор, ограничение по приложению и устранение повторов выполняются на сервере **до** разбиения по страницам, порядок по canonical interactionId. Если подходящих вариантов нет, показать пустое состояние. Фильтр приложения может использовать доступный постраничный каталог приложений. При отсутствии отдельного catalog.read пользователь по-прежнему выбирает из разрешённых Need options с видимым названием приложения. Вход из реестра даёт доступ ко всем страницам разрешённых процессов.

Существующий GET `need-options` продолжает выдавать Revision-селекторы по прежним правилам. Новый GET наследует режим видимости этого GET: обычно `business.process.read` и `business.need.create` в `demo-business`, в локальном shared-read — действующее исключение для discovery. При POST независимо проверяются `business.process.read` и `business.need.create`, shared-read никогда не разрешает запись.

Расширить `POST /business-processes/{pid}/needs` второй строгой формой тела. Разрешены либо `{interactionId, businessBasis}`, либо действующая `{interactionRevisionId, businessBasis}`. Смешанные селекторы, пустой выбор, лишние поля, переданный componentId и невалидный UUID дают 422. Активный процесс, непустой basis (до 10 000 символов), совместимость всех ревизий, свободный tuple и grants проверяются заново в транзакции. Сервер сам определяет source. Ответ 201 — прежний Need DTO и его сохранённый ID. При закрытии формы до сохранения записей не возникает. Отдельное право чтения Need проверяется при переходе на карточку даже после успешного создания.

Различать 409 PROCESS_ARCHIVED, 409 DUPLICATE_NEED (активная или выведенная запись, включая конкурентный POST), 422 для неверного обоснования, 400 для несовместимой коммуникации, 404 для неизвестной ссылки, 401/403 для доступа. Для конфликта ссылка на существующую запись допустима только при разрешённом чтении и известном точном ID. Если ответ его не раскрывает, достаточно перехода в список процесса при наличии чтения. Не предлагать восстанавливать уже активную запись.

### Композиция заявки (#143)

Переиспользовать `GET …/needs/{nid}/access-request-options`. Для `kind=revisions` добавить необязательный `order=latest`. При этом порядке сервер сначала отбирает доступные опубликованные ревизии канонического Interaction с нужным участником и хотя бы одной допустимой парой развёртываний. Затем сортирует по revisionNumber по убыванию, при равенстве по ID, и только затем берёт страницу. Первый элемент при offset=0 — начальный выбор для новой композиции. Так версия за границей первой страницы старого порядка не потеряется. Запрос без нового параметра сохраняет старый порядок. Для kinds развёртываний остаётся текущий контракт с точным interactionRevisionId. Пустая страница означает отсутствие доступных вариантов на ней.

При обычном чтении вариантов сервер проверяет `business.process.read` и `business.need.read`, `access.options.read` на ресурсы обеих сторон и `access.request` на ресурс источника. Сохранить действующее shared-read исключение для GET. Смена выбранной ревизии сбрасывает развёртывания и подтверждение. Переход к другой странице вариантов позволяет выбрать старую версию, дефолт заново не подставляется поверх явного выбора. Явно показывать номер и фактические условия выбранной версии. Публикация следующей не заменяет уже выбранную. При RETIRED или ARCHIVED прямой вход в форму показывает причину и возврат к Need.

`POST /access-requests` получает прежние четыре ID (Need, выбранная Revision, оба Deployment). Сервер повторно проверяет access.request на source Resource, совместимость и lifecycle. Прямой POST сохраняет собственные правила admission независимо от discovery. При 409 или утрате полномочий показать соответствующую причину, отменить старое подтверждение. Не повторять автоматически запрос с неизвестным результатом. Предыдущее решение, правило, provenance и точная сохранённая версия остаются доступны с их прежними разрешениями.

## Migration and verification

Изменения аддитивны. Миграция данных не требуется. #141 вводит реестр и сохраняет рабочее создание в процессе до #142. #142 вводит отдельную форму при действующей карточке. #143 выносит композицию с сохранением history deep links. После каждого этапа пользователь может завершить прежний сценарий. Для каждого среза критерии приведены в [tasks.md](tasks.md). Продуктовую приёмку дизайна фиксирует владелец в PR задачи #140 перед интеграцией.

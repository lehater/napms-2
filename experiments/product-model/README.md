# NAPMS 2.0 — эксперимент графа знаний продукта

## Цель

Практически проверить, можно ли представить концептуальную модель NAPMS 2.0 одним типизированным графом Markdown/YAML и получать из него несколько обзорных представлений. Источник истины — заметки в `vault/knowledge/`; файлы в `vault/views/` являются навигационными проекциями и не добавляют фактов.

Эксперимент проверяет выразительность модели, а не проектирует заново NAPMS и не реализует отсутствующие продуктовые возможности.

## Статус

**Baseline v0.1 зафиксирован.** Сохранены исходная кандидатная метамодель, знания и проекции. После baseline проведены семантический аудит и функциональная детализация J01 для Application Communication и Business Connectivity; они описаны в [semantic-audit.md](reports/semantic-audit.md) и [functional-detailing.md](reports/functional-detailing.md). Изменения после baseline не подменяют исходные статические показатели ниже.

## Гипотезы

1. `Function` подходит для функциональной декомпозиции; Leaf Function определяется отсутствием дочерних функций.
2. Leaf Function можно переиспользовать в нескольких `Functional Chain`, если определения функций отделены от контекстных участий.
3. `Functional Exchange` как самостоятельный узел хранит источник, получателя и передаваемую информацию без смешения с порядком выполнения.
4. Логические функции можно распределить между `Logical Component`, не приравнивая компоненты к предметным сущностям, областям карты или программным модулям.
5. Контекстные узлы цепочки и сценария выражают локальный порядок и вариации поведения, не устанавливая глобальный порядок между определениями функций.
6. Одна каноническая модель поддерживает проекции возможностей, деятельности, функций, цепочек, логической архитектуры, домена и межуровневой трассировки.

## Границы и правила

- Обзорный охват всего продукта важнее глубины одной области. Все 38 возможностей текущей Capability Map включены как отдельные узлы.
- ARCADIA используется как источник понятий и различения уровней: operational need, system need и logical solution. Эта кандидатная метамодель не является эквивалентом Capella.
- Knowledge Skeleton Lab используется только как образец устройства Markdown/YAML Vault, типизированных направленных отношений, K-Plex, Bases и Canvas. Его данные, Harness и код не копируются.
- Названия областей Capability Map хранятся как свойство `area`. Они не превращаются автоматически в `Capability`, `Logical Component` или Bounded Context.
- Предметный `Component` NAPMS и архитектурный `Logical Component` — разные заметки и референты. То же правило применяется к `Interaction`/`Functional Exchange`, `BusinessProcess`/`Operational Process` и `Application`/NAPMS system.
- В каждой заметке хранится один референт. Wikilinks в YAML задают направленные типизированные отношения; обратные связи вычисляются Obsidian и не дублируются.
- Для каждого узла указаны `epistemic` (`fact`, `interpretation` или `hypothesis`) и `sources`. Статус принятия области и свидетельство реализации возможности хранятся отдельно.
- `code_test_evidence` означает, что в текущем checkout найдены код и/или тестовые файлы по возможности. Тесты в этом эксперименте не запускались, а такое свидетельство не доказывает полноту пользовательского сценария.
- `not_assessed` означает отсутствие достаточной проверки реализации; `not_found_in_scoped_scan` — отсутствие совпадений в просмотренном коде и тестах по заявленной функции, а не доказательство невозможности или отсутствия всякого поведения.
- Связь `realizes` описывает концептуальную трассировку внутри модели, а не факт поставленной реализации.
- Не создавать узлы или отношения только ради заполнения словаря. Не менять продуктовый код, OpenSpec, существующую документацию и Knowledge Skeleton Lab.

## Содержимое Vault

Откройте `vault/` как самостоятельное хранилище Obsidian. Установите community plugin K-Plex версии `0.3.1` отдельно; код плагина и локальные настройки Obsidian в эксперимент не включены. После установки плагина закройте Obsidian и из `experiments/product-model/` восстановите настройки:

```sh
cp k-plex-config.json vault/.obsidian/plugins/k-plex/data.json
```

Затем снова откройте Vault. Файл содержит настройки типов, отношений, цветов и фильтров, но не историю навигации или состояние рабочего окна.

| Проекция | Файл / способ открытия |
|---|---|
| Product Capability Map | `views/Product Capability Map.base` — все 38 возможностей, группировка по области |
| Operational Model | `views/Operational Model.canvas` |
| Functional Breakdown | `views/Functional Breakdown.canvas` и `views/Functional Breakdown.base` |
| Functional Chains | `views/Functional Chains.canvas` |
| Logical Architecture | `views/Logical Architecture.canvas` |
| Domain Model | `views/Domain Model.canvas` и `views/Domain Model.base` |
| Cross-level Traceability | `views/Cross-level Traceability.canvas` |
| K-Plex | открыть узел `NAPMS system mission` в K-Plex и пройти по типизированным отношениям; K-Plex — динамическая навигация, отдельный файл графа ему не нужен |
| Model Node Inventory | `views/Model Node Inventory.base` — узлы с группировкой по типу |

Canvas и Bases показывают выбранные срезы знаний. Отношения следует проверять по YAML канонических заметок.

## Статическая оценка

Повторная статическая проверка Baseline v0.1 завершилась успешно. Она проверила frontmatter и обязательные свойства заметок, разрешение Wikilinks, применённые сигнатуры предикатов, дубли и самоссылки, обязательные концы обменов и участий, локальность/ацикличность `precedes`, ссылки Canvas на существующие файлы, Canvas edge endpoints, синтаксис Bases, конфигурацию K-Plex и наличие требуемых проекций.

| Показатель | Результат |
|---|---|
| Области Capability Map | 12 |
| Возможности Capability Map | 38: A — 14, C — 15, O — 9; у каждой есть раздельный `implementation_status` |
| Все узлы `capability` | 39, включая отдельную capability самого NAPMS |
| Всего канонических узлов | 179 |
| Типы узлов | `activity` 6, `capability` 39, `component` 4, `constraint` 14, `domain_entity` 20, `exchange_involvement` 10, `exchange_item` 7, `function` 22, `function_involvement` 12, `functional_chain` 3, `functional_exchange` 10, `mission` 2, `operational_process` 1, `participant` 7, `problem` 1, `scenario` 4, `scenario_message` 10, `state` 7 |
| Типизированные отношения | 371: `addresses` 2, `allocated_to` 11, `constrains` 32, `conveys` 10, `part_of` 55, `participates_in` 15, `precedes` 15, `realizes` 78, `references` 102, `source` 21, `specializes` 2, `state_of` 7, `target` 21 |
| Проекции | 4 Bases и 6 Canvas; все Canvas содержат ссылки на узлы и типизированные по смыслу локальные рёбра |
| Переиспользование функции | `Resolve deployment Resource identity` входит в `Submit access request` и `Export effective policy` через два разных `Function Involvement`; определение одно |
| GUI Obsidian / K-Plex | `PARTIAL`; человек проверил K-Plex на связанных фрагментах. Canvas, Bases, семантическая корректность всего графа и полнота модели не проверялись; см. [протокол](reports/pilot-validation.md) |

Счётчик отношений учитывает YAML-свойства графа один раз в направлении от источника к цели; обратные ссылки Obsidian в него не включены. Проверка не исполняла продуктовые тесты и не подтверждала полноту реальной реализации.

### Итог проверки гипотез

- Гипотезы 1–3 и 5 выразимы выбранными узлами и связями: функции декомпозируются, обмены самостоятельны, участие переиспользуется, а порядок локален для цепочки или сценария.
- Гипотеза 4 представлена на логическом уровне через `allocated_to`; получившееся разбиение — архитектурная интерпретация для эксперимента, не утверждённое устройство продукта.
- Гипотеза 6 подтверждена статически: из одного набора заметок подготовлены независимые Bases и Canvas. Визуальный просмотр подтвердил отображение отдельных фрагментов K-Plex; Bases, Canvas, семантическая корректность и полнота всего графа остаются непроверенными.

## Ограничения, обнаруженные в эксперименте

Исходный набор предикатов не содержал прямой связи миссии/возможности с адресуемой проблемой и способа привязать предметное состояние к сущности. Добавлены узкие `addresses` и `state_of`; это экспериментальные расширения, а не утверждение о полноте набора связей ARCADIA/Capella.

Выбранное представление оставляет несколько существенных аспектов только частично выраженными:

- `precedes` задаёт частичный порядок контекстных участий и сообщений, но не задаёт формальную семантику ветвления, синхронизации, guards или повторов функциональной цепочки.
- Узлы `state` фиксируют состояния предметных сущностей, но переходы, события, их условия и временные инварианты не моделируются отдельными типизированными связями.
- `references` имеет широкую сигнатуру для контекстных и предметных ссылок. Это удобно для навигации, но при дальнейшем углублении некоторые случаи потребуют более предметных отношений.
- Canvas — выбранные статические срезы. Они не являются автоматически вычисляемыми диаграммами и могут устареть при правке YAML; источник истины остаётся в заметках.
- Модель не прошла импорт или формальную проверку в Capella и не претендует на эквивалентность полной метамодели ARCADIA.

## Результат GUI-проверки

Визуальное ревью K-Plex выполнено человеком на фрагментах Govern Network Access, Evaluate Authority, Check Decision Authority, Function Involvement и Decide an Access Request. Проверялись распознавание типов и отношений, функциональная декомпозиция, межуровневая навигация, логическая ответственность, цепочки и фильтры; выразительность ветвлений оценена как `PARTIAL`. Canvas и Bases в этом ревью не оценивались. Успешное отображение выбранных фрагментов не подтверждает полноту или семантическую корректность всего графа. На момент этого ревью семантический аудит не запускался; его последующий результат приведён в [отчёте](reports/semantic-audit.md).

## Пост-baseline функциональная детализация

В новом срезе раскрыты `Manage communication contracts` и `Maintain business justification` до пяти Logical Functions, собрана отдельная Functional Chain для J01 и обновлены соответствующие Canvas. Подробности контрактов, повторного использования, статуса реализации и текущих ограничений приведены в [отчёте функциональной детализации](reports/functional-detailing.md). Реализация не выводится из `realizes`; для каждого поведения отдельно указаны найденные код и тестовые сценарии.

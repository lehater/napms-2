# Отчёт: Macro-Level Functional Model

## Цель и чёрный ящик

NAPMS принимает сведения о стабильных ресурсах и их текущих сетевых адресах, повторно используемой семантике коммуникаций, размещении ролей компонентов и бизнес-потребностях; проверяет authority субъектов при отдельных защищённых действиях; фиксирует заявки и независимые решения; формирует объяснимый срез текущей желаемой политики.

Внешние участники: куратор каталога, инициатор доступа, уполномоченный принимающий решение и оператор/потребитель policy export. Внешние сведения включают описания ресурсов и адресов, application/component/interaction, deployment, BusinessProcess/ConnectivityNeed, полномочия и выбранный scope экспорта. Основной результат — vendor-neutral READY/INCOMPLETE policy с устойчивыми идентификаторами, traffic semantics, provenance и временем оценки.

NAPMS отвечает за доменную желаемую политику и её объяснение. Он не подтверждает фактическое состояние firewall, не вычисляет placement сети и не применяет/исправляет сетевые конфигурации.

## Функциональная декомпозиция

```text
NAPMS (black box)
  +-- F1 EstablishConnectivityContext
  |      catalog + deployment + business need
  +-- F2 AdmitAccessRequest
  |      context + exact request + source authority -> PENDING request/evidence
  +-- F3 DecideAndMaintainPolicy
  |      PENDING request + independent decision authority -> decision / optional Rule
  +-- F4 EvaluateDesiredPolicy
         selected effective policy + export authority -> READY/INCOMPLETE rows
```

Четыре функции — макроуровневый минимум, который объясняет происхождение основного результата и не раскрывает элементарные проверки. F1 охватывает несколько независимых каталоговых операций; её наличие не означает, что они выполняются одним процессом. C13 (поиск кандидатов) включён как аспект выбора/подготовки контекста, но capability map уточняет, что это не универсальный API discovery.

## Типизированные зависимости

- **Композиция:** четыре action usage сгруппированы в `NAPMSMacroFunctions`.
- **Данные:** `ConnectivityContext` переходит из F1 в F2; AccessRequest — вход F3; существующий `EffectivePolicy` независимо подаётся на вход F4. Он не связан с выходом F3 в той же композиции. На решение и экспорт подаются отдельные типизированные authority evidence.
- **Классификация capability:** Cxx распределены по функциям в function catalog и traceability; классификация не создаёт зависимости выполнения.
- **Порядок выполнения:** ни линейный сценарий, ни полный граф всех продуктовых операций модель не задаёт. Admission не является permission. Экспорт — чтение effective state и может быть выполнен позднее отдельно от решения.

## Статусы знаний

- **Подтверждённое состояние:** конкретные доменные смыслы и OpenSpec требования перечислены в traceability; use cases и тесты текущего checkout подтверждают соответствующие реализованные backend-пути. Это не равнозначно подтверждению полноты интерфейса/production эксплуатации.
- **Принятые, но не полностью подтверждённые требования:** OpenSpec контракт может содержать принятый результат, выходящий за фактический объем UI или текущего deployment. Каждую функцию следует читать с этим различием.
- **Целевое состояние:** F1–F4 представляют концептуальный продуктовый результат; полнота C01–C18 в каждом интерфейсе здесь не обещается.
- **Неизвестно:** точный уровень завершённости каждого C01–C18 end-to-end; будущая production идентификация; политика истории/отзыва beyond current specs; внешняя фактическая сетевая реализация. A/C/O в Capability Map показывает scope-классификацию, не реализацию.

## Ограничения модели

- Граница концептуальная, не API/database/software architecture.
- Идентификаторы в переиспользованных пилотных типах строковые; связи на полноценные типы текущей доменной модели не выдумывались. Пилотная `AccessRequestData` недостаточно богата, чтобы заменить полный контракт запроса; ConnectivityContext передаётся отдельно.
- SysML статически проверяет грамматику и часть ссылочной/типовой согласованности. Он не исполняет action definitions, не доказывает authority policy, транзакционность или бизнес-инварианты.
- Capability coverage — классификация областей и трассировка, а не оценка зрелости.
- V4 HTML относится к прежнему пилотному срезу, сохранён как воспроизводимый артефакт; он не визуализирует эту модель.

```text
  experiments/product-model/macro-functional-model/model.sysml

```

Статический PASS не подтверждает семантическую истинность отношений сверх типов и явных bind. Отдельных продуктовых тестов не запускалось: продуктовый код не менялся.

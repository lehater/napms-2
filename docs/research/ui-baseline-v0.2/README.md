# NAPMS 2.0 — UI/IA Baseline v0.2: от бизнес-контекста до экспорта политики

**Решение владельца:** 2026-11-09. **Статус:** согласованная целевая структура интерфейса; принятие в `main` — через review этого Draft PR. **Область:** навигация, семантика списков и карточек, композиция. Не означает готовность всех API или UI.

## 1. Пользовательская цель

От бизнес-потребности установить участников коммуникации и развёрнутые компоненты, создать заявку, принять решение ALLOWED/DENIED, просмотреть авторитетное правило и выгрузить вычисленную эффективную политику в пределах допустимых полномочий.

**Порядок групп отражает пользовательский смысл, а не зависимости хранения:** бизнес-контекст → каталоги → управление доступом. Из каждой коллекции доступна детализация объекта; вложенные объекты и отношения находятся на предметных вкладках.

## 2. Sidebar — три группы, семь коллекций

| Группа (порядок фиксирован) | Пункты (порядок фиксирован) | Основные доменные понятия |
| --- | --- | --- |
| **1. Бизнес-контекст** | Бизнес-процессы; Потребности в коммуникациях | BusinessProcess; ConnectivityNeed |
| **2. Каталоги** | Ресурсы; Профили приложений; Развёрнутые компоненты | Resource (+ ResourceEndpoint); Application (+ Component, Interaction, InteractionRevision); ComponentDeployment |
| **3. Управление доступом** | Заявки на доступ; Правила политики | AccessRequest (+ AccessSubject, AccessDecision); PolicyRule (+ provenance) |

Это **семь пользовательских коллекций**, не семь доменных агрегатов и не перечень всех элементов ERD.

В Sidebar текущего целевого среза **нет** разделов Network Evidence, NST, Required/Configured, Reconciliation, сетевых операций или «Каталога модели». Существующие определения, прототипные маршруты и контракты этих областей не удаляются; они вне текущего фокуса.

### Терминология

- **Application — «Профиль приложения»**: повторно используемый профиль сетевой коммуникации с ролями Component и направленными Interaction; не инсталляция ПО.
- **Component — «Компонент»**: роль внутри Application.
- **ComponentDeployment — «Развёрнутый компонент»**: конкретный экземпляр Component на Resource, независимо от IP; не именовать «Размещением» в пользовательском меню.
- **ResourceEndpoint — «Endpoint» ресурса**: вложенный объект с устойчивой identity; адрес может меняться.

## 3. Единый паттерн Collection → Object Detail

**Каждый пункт Sidebar** открывает коллекцию с типовыми действиями чтения: поиск/фильтрация, предметная таблица, переход по строке к карточке, пагинация по имеющимся данным. Для mock это локальная демонстрация; real UI соблюдает принятые серверные контракты без фиктивных фильтров.

**Каждая карточка:** breadcrumbs → тип, имя и назначение → вкладка «Обзор» → только применимые предметные вкладки с вложенными коллекциями и связанными объектами. Отношения, история, версии и provenance не сваливаются в последовательные панели на странице и не выводятся строками, разнесёнными по противоположным краям широкого окна.

| Коллекция | Одна строка списка | Детализация (предметные вкладки, если есть данные) |
| --- | --- | --- |
| Ресурсы | **Один Resource**; scope/site/ответственность; Endpoints компактным списком в ячейке (не строка на каждый Endpoint) | Обзор; Endpoints; Развёрнутые компоненты; История |
| Профили приложений | **Один Application**; компоненты многострочно в одной колонке; число/краткое описание коммуникаций (не динамическая колонка на Component) | Обзор; Компоненты; Коммуникации; у Interaction — Revision |
| Развёрнутые компоненты | **Один ComponentDeployment**; Component, Application, Resource | Обзор; Компонент и профиль; Resource; применимые коммуникации |
| Бизнес-процессы | Один BusinessProcess; назначение, ответственность, связанные потребности | Обзор; Потребности |
| Потребности в коммуникациях | Один ConnectivityNeed; процесс, Interaction, участник | Обзор; Коммуникация; Заявки |
| Заявки на доступ | Один AccessRequest; предмет, заявитель, время, PENDING/ALLOWED/DENIED | Обзор; Предмет доступа; Решение и evidence; Бизнес-основание |
| Правила политики | Один PolicyRule; точный AccessSubject, ACTIVE/INACTIVE, provenance | Обзор; Предмет доступа; Основания разрешения; История при наличии данных |

Названия вкладок — базовый ориентир композиции; вкладка появляется только при осмысленном содержимом. Component, Interaction, Revision, Endpoint и evidence доступны через подчинённые коллекции/Detail, **без обязательных отдельных пунктов Sidebar**. Связи в UI не создают новых постоянных ERD/SQL связей.

## 4. Управление доступом и экспорт

- ConnectivityNeed обосновывает необходимость, но **не** предоставляет разрешение.
- AccessRequest, AccessDecision, PolicyRule — различные понятия с независимыми состояниями. DENIED не создаёт и не отзывает PolicyRule.
- ALLOWED для exact AccessSubject создаёт либо переиспользует **одно** каноническое PolicyRule; повторное ALLOWED не активирует INACTIVE автоматически.
- «Создать политику» в рамках принятой N2 модели означает заявка → авторизованное решение ALLOWED → Rule. Прямой CRUD PolicyRule не вводится.
- **«Экспортировать политику»** — действие в контексте «Правила политики», использующее принятый `GET /policy/export` с серверной авторизацией и READY/INCOMPLETE. **Effective Policy — вычисляемая проекция**, не самостоятельная таблица, отдельный workspace или пункт Sidebar.
- Текущие real заявки `/access-requests` и mock `/prototype/requests` имеют независимые наборы данных и полномочия. Новая навигация не должна выдавать mock за real; интеграция пользовательского пути с реальным backend — отдельный этап.

## 5. Визуальная и инженерная границы

- Визуальный источник: [UI Baseline v0.1](../ui-baseline-v0.1/README.md) и [интерактивный reference.html](../ui-baseline-v0.1/reference.html): регулируемый контрастный Sidebar, fluid workspace, предметные таблицы и горизонтальные вкладки.
- При широком экране сохранять удобную читаемость свойств и связанных строк: не раздвигать label и ссылку по краям всей рабочей области. Различать основное содержимое, вторичные атрибуты и связи; обеспечить читаемый контраст и плотность.
- Прежние **восемь разделов UX-0** и `docs/contracts/ux-0-semantic-boundaries.json` отражают **текущую реализацию v0.1**, а не целевую IA v0.2. Изменять их атомарно с последующей реализацией, обновлением semantic gate и Playwright; не ломать проверки до внедрения.
- Не изменять ERD, OpenSpec, backend, fixtures и UI только от фиксации документа. Сначала целостная навигация и read-only mock представления; затем отдельные продуктовые вертикальные срезы.

## 6. Приёмка реализации

1. Sidebar показывает **именно три группы в указанном порядке** и семь соответствующих коллекций; нет misleading пунктов незавершённых технических областей.
2. Из списка каждого типа открывается правильная карточка; вложенные таблицы/переходы доступны без знания URL.
3. Resource не дублируется по Endpoint; Application не дублируется по Component. В карточке Application видны компоненты и направленные коммуникации; у Interaction доступна Revision.
4. От BusinessProcess и Need можно проследить путь к Request → Decision → Rule → export; неподдерживаемые real переходы честно обозначены.
5. Для всех реализованных карточек действует композиция вкладок и проверенный читаемый контраст по reference.html при широком и узком экране.
6. DOM/E2E проверяют **поиск сущностей из Sidebar**, Collection → Detail → вкладки → related object, семантические различия и изоляцию MOCK/REAL.

**Не является результатом текущего этапа:** реальное сетевое обнаружение/сбор трафика, NST, конфигурирование устройств, вычисление Reconciliation и новый доменный CRUD.

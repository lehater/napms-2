# NAPMS 2.0 — UI Baseline v0.1

**Решение:** первая приближённая версия UI/UX согласована владельцем для продолжения исследовательской работы с mock-данными.

**Дата фиксации:** 2026-11-08  
**Статус:** `APPROVED AS INITIAL DESIGN REFERENCE` — согласовано направление и компоновка; это **не** окончательная дизайн-система, не приёмка интерфейса в коде и не утверждение новых продуктовых функций.  
**Рабочий референс:** [reference.html](reference.html) — интерактивный самостоятельный прототип; он является главным визуальным источником для проверки компоновки.  
**Базовый viewport для визуального сравнения:** 1920 × 1080; проверочные: 1440 × 900, 2560 × 1440.

## 1. Обязательные принципы

1. **Полноэкранное корпоративное приложение.** Светлая рабочая область, контрастный тёмный Sidebar, компактная иерархия информации. Не устанавливать глобальный `max-width` для рабочей области.
2. **Fluid Layout.** Sidebar регулируется в пределах ориентировочно **200–360 px** (начальное значение **264 px**); контент занимает оставшееся пространство. Эти числа — стартовые UI-параметры, а не неизменяемые продуктовые ограничения. Перетаскивание, клавиатурное управление и сохранение ширины продемонстрированы референсом.
3. **Два базовых вида.** `Collection View` — список сущностей; `Object Detail` — детализация выбранной сущности. Переход к Detail доступен из строки/имени объекта; обратный переход возвращает к списку.
4. **Collection View:** заголовок коллекции → поиск и фильтры → таблица по всей доступной области → пагинация. Колонки определяются типом сущности, не унифицируются искусственно. При расширении окна появляется полезная информация, а не пустые поля.
5. **Object Detail:** breadcrumbs → заголовок объекта (тип, имя, назначение) → горизонтальные **предметные вкладки**. Вкладка **«Обзор»** содержит основное предметное представление и ключевые свойства.
6. **Подчинённые, связанные объекты, версии и история** показываются **на отдельных применимых вкладках с таблицами**, а не последовательными списками на «Обзоре». Названия и наличие вкладок определяются конкретной доменной сущностью. Не создавать фиктивные пустые вкладки.
7. **Вложенная Collection View:** те же таблица, поиск, фильтры и пагинация, но в фиксированном контексте родителя. При открытии полной коллекции сохранять контекст выбора.
8. **Доменная семантика:** структурное подчинение, самостоятельные связи, версии и исторические факты отличаются; визуальные переходы сами по себе не означают постоянные связи хранения. Не добавлять выдуманные статусы, данные или операции.
9. **Режимы данных:** исследовательские `RESEARCH / MOCK` и настоящий `REAL API` явно разделены. Mock не подтверждает сетевых интеграций, вычислений, состояние настоящих устройств или существование API.
10. **Историческая навигация v0.1:** восемь разделов в референсе отражают прежний UX-0. Реализация Issue #34 использует принятую [IA v0.2](../ui-baseline-v0.2/README.md): три группы и семь коллекций. Визуальные принципы этого референса сохраняются.

## 2. Использование в следующей итерации

- Продолжить UI-прототип на **существующем фиктивном наборе NAPMS**; сначала реализовать/проверить Collection View и Object Detail со вкладками.
- Для нового типа сущности сначала определить: колонки списка, содержание «Обзора», применимые вкладки, происхождение каждого поля/связи.
- На каждом этапе обеспечивать читаемость, контекст родителя, рабочую фильтрацию/пагинацию (в границах mock) и отсутствие горизонтального переполнения страницы.
- Проверять минимум три контрольных размера, а также минимальную и максимальную ширину Sidebar.
- Экран Reconciliation и возможный Diff Viewer **отложены** как специализированный вычислительный сценарий, не часть общего Object Detail.

## 3. Что сознательно не утверждается

- Окончательные цвета, шрифты, размеры, дизайн-токены и пиксельное соответствие каждой детали.
- Любые кнопки или действия, представленные на иллюстрациях, но не подтверждённые текущими требованиями.
- Изменения доменной модели, SQL, backend, OpenSpec или настоящего API.
- Полная продуктовая информационная архитектура сверх текущих исследовательских восьми разделов.
- Универсальный Diff Viewer, редактор политик, реальное исполнение сетевых операций.

## 4. Критерии пересмотра

Улучшать оформление **итерационно, по наблюдаемым недостаткам**: потеря контекста, смешение семантики, непонятные переходы, недостаточная плотность или читаемость, переполнение, сложности с фильтрацией больших наборов, неудобство при появлении реальных данных. Не расширять дизайн-систему ради полноты до появления подтверждённой пользы.

## 5. Артефакты и воспроизводимость

- [**Интерактивный HTML-референс**](reference.html) — исходная согласованная композиция Fluid Layout, регулируемого Sidebar, Collection View и вкладок Object Detail. Файл автономный; откройте его локально в браузере после скачивания из GitHub.
- [**Геометрические проверки**](geometry-check.json) — измерения при 1440 × 900, 1920 × 1080, 2560 × 1440 и проверка крайних размеров Sidebar. Это результаты проверки дизайна, а не автоматические тесты приложения.
- Контрольные PNG (9 изображений) были созданы вместе с исходным baseline и полезны как контрольные кадры, однако **в данном Draft PR бинарные PNG не загружены**: доступный GitHub-коннектор принимает текстовое содержимое, а не байты локальных изображений. Основной визуальный референс сохранён полностью в HTML. PNG можно добавить отдельным обычным Git-коммитом, если они понадобятся для визуальной регрессии.

ZIP-архивы в репозитории не хранятся: Markdown, HTML и результаты проверок версионируются как самостоятельные исходные артефакты.

**Источники предметных данных:** актуальный `main`, [логическая ERD](../persistent-state-erd.md), [информационная архитектура](../ux-information-architecture.md), `web/src/prototype/data.ts`. Визуальный референс не создаёт новых доменных фактов. PR #27 на момент фиксации был Draft и не считался частью `main`.

**Критерий завершения текущего дизайнерского этапа:** согласована первая композиция; далее работа продолжается на mock-данных и подтверждённых UX-дефектах, без полного перепроектирования.

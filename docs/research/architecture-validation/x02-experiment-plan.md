# X02 — ограниченный эксперимент по проверке архитектурных изменений

**Статус** — план исследования. Результаты этого эксперимента ещё не получены.

**Решение, которое должен принять координатор** — оправдан ли структурированный сценарный разбор ALMA для следующего архитектурного изменения NAPMS 2.0.

## Вход и границы

- Нормативная база — [NAPMS 2.0 main 9713c89](https://github.com/lehater/napms-2/commit/9713c89bada6573bda2f60c97fb45deda48f5909). В будущем прогоне закрепить фактический SHA. Если он изменился, проверить актуальность сценария и ключа оценки до запуска.
- X02 — открытый вопрос материализации адресов и выбора Endpoint при нескольких Endpoint у одного Resource. Его постановка взята из [исследования PR #21](https://github.com/lehater/napms-2/blob/d4cb755550df6cda2d737fa2d6cfac4946aa28d0/docs/research/product-discovery-gaps.md#L29-L45). Для текущего среза ограничение на один Endpoint видно в [SQLite](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/src/napms/storage.py#L6-L9), а выбор одной записи — в [экспорте](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/src/napms/use_cases.py#L124-L142). [Принятый контракт экспорта](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/specs/policy-export/spec.md#L20-L47) задаёт сохранение идентичности и различие READY/INCOMPLETE.
- Метод — [Architecture-Level Modifiability Analysis](https://research.vu.nl/en/publications/architecture-level-modifiability-analysis-alma/). Использовать его пять шагов на одном сценарии, с существующими документами и исходниками. Ревью предназначено для оценки решения до его реализации.

## Порядок прогона

1. **Подготовить два коротких черновика.** В обоих меняется допустимая кардинальность, один Resource имеет Endpoint с адресом и Endpoint без адреса, существует один ACTIVE PolicyRule. В дефектном черновике меняется хранение, а выбор Endpoint и последствия для экспорта остаются несогласованными. В контрольном черновике задана однозначная политика выбора и согласованы хранение, чтение, число строк, READY/INCOMPLETE, provenance и нужные проверки. Выбранная политика действует только как вход эксперимента.
2. **Подготовить ключ оценки.** До запуска координатор фиксирует ожидаемые дефекты, допустимые вопросы и пункты, которые контрольный черновик закрывает. В ключе отделить действующие контракты от гипотез PR #21. Matching учитывается как возможное последствие для исследуемого направления, его отсутствие в реализации первого среза само по себе не является дефектом.
3. **Сравнить два режима.** Для каждого черновика выполнить обычное архитектурное ревью и ревью по ALMA. Четыре коротких прогона в свежих сессиях, с одинаковой моделью, бюджетом, доступом к источникам и форматом ответа. Чередовать порядок режимов. Скрыть от исполнителя метки черновиков, ключ и уже опубликованный разбор. Черновики остаются входами исследования вне OpenSpec changes.
4. **Сохранить наблюдения.** Для каждого замечания записать вариант, режим, приоритет, затронутое решение, ссылку на источник, последствия и проверяемый контрпример. Для ALMA зафиксировать цель, описанную архитектуру, сценарий, оценку и интерпретацию. Координатор сверяет ответы с ключом и отмечает обнаруженные и пропущенные дефекты, ложные срабатывания и время проверки.

## Критерии и затраты

| Что измеряем | Правило оценки |
|---|---|
| Обнаружение дефекта | ALMA выявляет конкретное несогласованное последствие с опорой на источник и объясняет, как оно проявится. Общая фраза о риске не считается. |
| Качество контроля | Контрольный черновик не получает ложных P0/P1. Историческое решение и исследовательский matching учитываются с их собственным статусом. |
| Польза относительно обычного ревью | Для продолжения требуется хотя бы один дополнительный подтверждённый P0/P1 либо сопоставимый результат при меньшем общем времени работы. Один сценарий даёт основание для следующего решения, статистическую оценку качества из него не выводим. |
| Время и ручной труд | Записать минуты подготовки, каждого прогона и проверки результата владельцем. Суммарный предел — 60 минут. Отдельно отметить ручной перенос или дублирование фактов и токены, если инструмент их показывает. Предел — рабочее допущение для этого пилота. |

**Условие остановки.** Завершить эксперимент без развития подхода, если пропущен существенный дефект, на контрольном варианте есть ложный P0/P1, ALMA не даёт преимущества над обычным ревью, превышен бюджет или для устойчивого результата потребовалась ручная параллельная модель. Если входы или режимы оказались несопоставимы, результат отмечается как недостоверный и не служит основанием для внедрения. В любом исходе достаточно короткой записи наблюдений с причинами и затратами.

# NAPMS 2.0 — готовые методы проверки архитектурных решений

Исследование для координатора · 7 ноября 2026 года

## Рекомендация

**Сначала применить ALMA к одному изменению в текущих документах.** ALMA (Architecture-Level Modifiability Analysis) — опубликованный метод оценки изменяемости архитектуры по конкретным сценариям. Вход — действующие решения и предполагаемое изменение. Выход — перечень затронутых частей архитектуры и последствий. Для NAPMS наиболее показательный первый сценарий — несколько Endpoint на одном Resource. Codex помогает собрать ссылки и пройти по сценарию. Решение о том, какие последствия принять, остаётся за владельцем. [Метод ALMA](https://research.vu.nl/en/publications/architecture-level-modifiability-analysis-alma/)

Первоначальный отчёт поставил OPA и CUE слишком высоко. Оба запускают правила, написанные специально для NAPMS, и требуют поддерживать проекцию решений. Их опыт сохранён в приложении как измерение этой цены. Приоритет этой редакции — опубликованные процедуры и поставляемые проверки.

Исходная база — [NAPMS 2.0 main 9713c89](https://github.com/lehater/napms-2/commit/9713c89bada6573bda2f60c97fb45deda48f5909). [NAPMS 1.0 main 4248157](https://github.com/lehater/napms/commit/42481577fab7f795cf3a2118b7b6f1c3c075d066) и [исследовательский PR #21](https://github.com/lehater/napms-2/pull/21) используются для сравнения и проверки кандидатов.

## 2. Практическое применение готовой методики

### ALMA, один change scenario для Endpoint

| Шаг ALMA | Результат по NAPMS |
|---|---|
| **Цель** | Выявить, где допущение «у ресурса один Endpoint» влияет на решение до расширения кардинальности. |
| **Описание архитектуры** | В принятом срезе SQLite допускает не более одного Endpoint на Resource. При экспорте `use_cases.py` выбирает по одному Endpoint на каждую сторону. OpenSpec требует сохранять идентичность и provenance и выдавать INCOMPLETE при недостающем адресе. |
| **Сценарий изменения** | Один Resource получил два Endpoint. У одного есть адрес, у второго нет. Существует один ACTIVE PolicyRule. Нужно определить, какие Endpoint попадают в export, как обозначить готовность и зависит ли выбор от стороны и трафика. |
| **Оценка изменения** | Хранение — `UNIQUE(resource_id)` отклонит второй Endpoint. Экспорт — при снятии ограничения `fetchone()` всё ещё вернёт одну запись без выраженного правила выбора. Контракт — нужно уточнить число строк, READY/INCOMPLETE и provenance при частичных данных. Matching — зависимый кандидат из PR #21, пока отдельное направление. |
| **Интерпретация** | Смена кардинальности требует согласованного решения о выборе Endpoint и форме результата. Одного изменения схемы недостаточно. До реализации есть две найденные точки в коде и одно открытое решение в контракте. Оценка трудоёмкости не проводилась. |

Источники — [SQLite](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/src/napms/storage.py#L6-L9), [экспорт в use cases](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/src/napms/use_cases.py#L124-L142), [принятый контракт](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/specs/policy-export/spec.md#L20-L47), [материалы PR #21](https://github.com/lehater/napms-2/pull/21).

### Сценарное review по ARID, один пример для authority

Актор с действующим source grant для `access.request` может подать заявку при отсутствии destination grant для этой операции. Актор с действующим source grant для `policy.export` при отсутствии destination grant для экспорта получит отказ. Это различие следует из двух принятых контрактов. Если в предложении общую фразу «проверить обе стороны» распространяют и на admission, тот же вход даёт другой результат. Такой witness пригоден для review без собственного движка. Это демонстрация шага walkthrough, полный ARID с заинтересованными участниками не проводился. [Admission AC-05](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/specs/access-requests/spec.md#L20-L29) · [Export AC-06](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/specs/policy-export/spec.md#L9-L18)

## 3. Запуск готового валидатора

Проверен дистрибутив **Context Mapper CLI 6.12.0** из Maven Central на OpenJDK 21. Запускался штатный `cm validate -i <file.cml>`, без расширений и авторских правил. В демонстрационной модели два контекста, по одному агрегату в каждом и одно направленное отношение.

| Контроль | Вывод stock CLI 6.12.0 |
|---|---|
| Resource Catalogue предоставляет свой агрегат downstream-потребителю | «validated without errors», exit 0 |
| Вместо агрегата upstream подставлен агрегат downstream | «validated without errors», exit 0 |
| Отношение использует контекст, исключённый из Context Map | «validated without errors», exit 0 |
| Ссылка на неизвестный агрегат | «validated without errors», exit 0 |
| Одинаковое имя поля в двух отдельных контекстах | «validated without errors», exit 0 |
| Ошибочный токен внутри Context Map | Сообщение о синтаксической ошибке, exit 0 |
| Текст без CML-модели | исключение `ResourceIsNoCMLModelException`, exit 1 |
| Указанный файл отсутствует | сообщение `ERROR`, exit 0 |

Правило принадлежности агрегата описано в документации и присутствует в коде DSL. **Поставка CLI 6.12.0 в проверенном окружении не дала ожидаемую диагностику на этой мутации.** Следовательно, для NAPMS ценность Context Mapper пока подтверждена как готовая нотация, а использование этой команды как CI gate откладывается до воспроизведения в другом поддерживаемом способе запуска. Код выпуска CLI читает ошибки ресурса. Эквивалентность этой операции полному семантическому прогону DSL не подтверждена. Диагностика и exit code в выпуске расходятся даже на синтаксической ошибке внутри Context Map. [Документация проверки](https://contextmapper.org/docs/context-map/#exposed-aggregates) · [Валидатор DSL v6.12.0](https://github.com/ContextMapper/context-mapper-dsl/blob/v6.12.0/org.contextmapper.dsl/src/org/contextmapper/dsl/validation/ContextMapSemanticsValidator.java) · [Дистрибутив CLI](https://repo.maven.apache.org/maven2/org/contextmapper/context-mapper-cli/6.12.0/context-mapper-cli-6.12.0.tar)

Минимальный воспроизводимый вход `context-ok.cml`.

```cml
ContextMap {
  contains ResourceCatalogue, PolicyMaterialization
  PolicyMaterialization [D,ACL]<-[U,OHS,PL] ResourceCatalogue {
    exposedAggregates = ResourceEndpoint
  }
}

BoundedContext ResourceCatalogue {
  Aggregate ResourceEndpoint {
    Entity Endpoint {
      String currentAddress
    }
  }
}

BoundedContext PolicyMaterialization {
  Aggregate MaterializedPolicy {
    Entity PolicyRow {
      String address
    }
  }
}
```

```sh
sed 's/exposedAggregates = ResourceEndpoint/exposedAggregates = MaterializedPolicy/' \
  context-ok.cml > context-wrong-upstream.cml
cm validate -i context-ok.cml
cm validate -i context-wrong-upstream.cml
```

**Проверка кода дала другой результат.** Готовый тип контракта `forbidden` Import Linter 2.6 на закреплённом `main` прошёл с exit 0 и поймал внесённый импорт `domain → http` с exit 1. Он также показал транзитивное нарушение до `storage`. Это практический кандидат для CI на уровне кода. [D1](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/changes/archive/2026-11-07-first-access-policy-slice/design.md#d1--small-three-layer-python-service)

## 4. Выбор и граница эксперимента

1. **Для изменения принятого решения — ALMA на OpenSpec proposal/design и `main`.** Зафиксировать один change scenario и оценить последствия. Для случая B дополнить явной ссылкой на предыдущее решение, как в готовом ADR-процессе. Для случая D провести контрсценарий до реализации. Выход — проверяемые замечания к предлагаемому дизайну.
2. **Для границ и ответственности — Domain Storytelling или EventStorming Process Modelling.** Взять один процесс и записать, кто меняет факт и кто использует его дальше. При появлении постоянной потребности в Context Map оценить CML как формат на одном примере, учитывая результат stock CLI.
3. **Для соответствия кода архитектуре — Import Linter.** Запустить один готовый контракт D1 в отдельном техническом опыте и сравнить исходный и отрицательный контроли. Для API взять oasdiff, когда появится реальный случай изменения публичной схемы.

| Приоритет | Риск для выбранного подхода | Практический контроль |
|---|---|---|
| **P0** | Историческое решение N1 получает силу действующего N2. | Развести редакции и профиль. Проверить ссылки на принятый OpenSpec и действующий код. |
| **P0** | Положительный exit code воспринимается как доказательство валидности. | Для любого CI-кандидата до принятия прогнать заведомо ошибочный вход и отсутствующий вход. |
| **P1** | Создаётся параллельная авторская модель и требуется постоянная синхронизация. | Первый опыт провести по существующим артефактам. Новую нотацию оценивать только при необходимости регулярно обновлять представление. |
| **P1** | Участники пропускают затронутую часть. | Проверять исходный сценарий и последствия по принятым контрактам, наблюдаемой реализации и тестам. Сомнения фиксировать отдельно от подтверждённых дефектов. |
| **P2** | Полноразмерный workshop или отдельная платформа стоят больше, чем сэкономленный review. | Ограничить первый опыт одним change scenario и проверить, какой конкретный пробел найден. |
| **P3** | Разный формат вывода затрудняет чтение отчёта. | Сохранять вход и исходный результат команды рядом с итогом review. |

**Передача локальному Codex.** На отдельной ветке взять case C и сделать один ALMA-проход по существующему дизайну и коду. Для контроля дать тот же сценарий с уже согласованной политикой выбора Endpoint. Выход для Draft PR — найденные последствия, точные источники, контрольный результат и время разбора. Критерий пользы — конкретное пропущенное последствие найдено до реализации, а согласованный контроль проходит. Начальный опыт выполняется по существующим файлам и опубликованному методу.

## Приложение A. Результаты раннего прототипа

CUE и OPA в этом приложении показывают, что происходит после написания специализированных правил. Эти проверки сохраняются как сравнительные измерения. Они не входят в предложенный первый эксперимент.


Числа в таблице — количество диагностик CUE / OPA. A–E прогонялись на минимальных проекциях, собранных вручную. Для проверки импортов использованы шесть файлов из зафиксированного `main`, сверенные по Git blob SHA.

| Кейс | Действующие факты и модель мутации | Измеренный результат и смысл |
|---|---|---|
| **A. Ownership** | В N1 Resource Catalogue управляет Endpoint и его адресной реализацией, materialization использует owner-defined факты. Для эксперимента второй контекст объявлен владельцем того же `resource.endpoint.current-address`. Имена контекстов — метки из исследуемой предметной области, конфликт — инъекция, поскольку N2 не утвердил унаследованное разбиение. [N1 system rules](https://github.com/lehater/napms/blob/42481577fab7f795cf3a2118b7b6f1c3c075d066/docs/architecture/mvp-system-rules.yaml#L13-L27) · [N2 D1](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/changes/archive/2026-11-07-first-access-policy-slice/design.md#d1--small-three-layer-python-service) | **1 / 1** `A_OWNER_CONFLICT`. Владелец + читатель и владельцы двух разных фактов дают **0 / 0**. Совпадение ID формализовано вручную. Семантическое пересечение фактов под разными именами остаётся за review. В реальной модели ключ также учитывает область полномочий владельца. |

### Воспроизводимость и пределы измерения

- Linux x86_64, Python 3.12.14, CUE 0.14.2, OPA 1.9.0, Import Linter 2.6 / Grimp 3.13. Эти версии фиксируют опыт. Артефакт содержит исходные проверки, 16 входов, `verify.py`, JSON-диагностику и журнал Python. Примеры запуска приведены в README комплекта.

Сбор фактов из Markdown, корректность полноценной проекции, доля обнаружения агентом, шум, стоимость и CI на GitHub Actions не измерены. Двухшаговый предел CUE — свойство примера.

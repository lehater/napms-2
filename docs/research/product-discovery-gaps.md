# NAPMS Product Discovery — пробелы, противоречия и уверенность

**Статус:** PARTIAL / Research handoff, не Product/UX acceptance. Закреплённые main: NAPMS 1.0 `42481577fab7f795cf3a2118b7b6f1c3c075d066`, NAPMS 2.0 `9713c89bada6573bda2f60c97fb45deda48f5909`.

## Измеренная полнота и границы доказательств

- Из 659 файлов дерева N1 инвентаризированы **180 текстовых документов** в 14 целевых каталогах. **180/180 имеют результат содержательной проверки либо обоснованное исключение**: 72 из исходного PR + 108 дополнительно прочитаны; **0 indexed-only**. Дополнительный [реестр решений](primary-source-content-audit.md) фиксирует outcome каждого из 108. Ещё осмотрено 10 runtime/UI/test файлов и root/meta. Полный перечень с индивидуальным уровнем проверки — [inventory](product-capability-inventory.md).
- Восстановлены **38 возможных capability**, **46 атомарных требований принятых для N1 first MVP** и **68 пунктов полноширинной реконструкции** (**56 CURRENT, 12 EXTENSION**, но все 68 non-canonical CANDIDATE). Сформировано **8 сквозных user journeys** и **19 candidate UI workspaces**. Это **не** оценка, что 38 функций реализованы или приняты в N2.
- Проверена структура и содержание актуальной документации N1, значимые исторические требования/дизайн, Web навигация, выбранные backend HTTP endpoints и E2E; в N2 — `docs/product.md`, `docs/domain.md`, `docs/first-slice.md`, действующие OpenSpec specs и 2 архива изменений. Исходные коды всей 1.0, все тесты и история всех PR **не прочитаны полностью**; это ограничивает силу отрицательных выводов («не обнаружено», а не «никогда не было»).
- Правило источника: [docs/README.md](https://github.com/lehater/napms/blob/42481577fab7f795cf3a2118b7b6f1c3c075d066/docs/README.md) — только `docs/**` canonical; [docs-legacy/README.md](https://github.com/lehater/napms/blob/42481577fab7f795cf3a2118b7b6f1c3c075d066/docs-legacy/README.md) — `RETIRED`, его внутренние исторические ссылки на `docs-v2` не отменяют текущую `docs/README`; [docs/horizontal/source-ledger.md](https://github.com/lehater/napms/blob/42481577fab7f795cf3a2118b7b6f1c3c075d066/docs/horizontal/source-ledger.md) и [docs/horizontal/s1/capability-requirements.md](https://github.com/lehater/napms/blob/42481577fab7f795cf3a2118b7b6f1c3c075d066/docs/horizontal/s1/capability-requirements.md) — полноширинная неканоническая реконструкция; [docs/requirements/first-mvp-policy-export.yaml](https://github.com/lehater/napms/blob/42481577fab7f795cf3a2118b7b6f1c3c075d066/docs/requirements/first-mvp-policy-export.yaml) — `SUPERSEDED`.

## Граница принятия после независимого review

- **Будущая принятая модель/backend:** X01/X03 (lifecycle, смена traffic revision, отдельная задача «Запросить прекращение доступа») и X02 (general-purpose Endpoint/address materialization) остаются решениями владельца продукта. Exact-subject Rule, source-only request и оба scope для export уже приняты N2; Discovery не переоткрывает и не заменяет эти контракты. QREQ-CONS не вводят дедупликацию новых POST или TTL/exportId.
- **Ограничения UX-0:** один Endpoint на Resource, host-only fixture, одна revision, current-only Checker; неподдерживаемая история — `Unknown` / `Historical data unavailable`. Сетевые данные/интеграции — MOCK, операции — SIMULATED; нет исполняемого revoke или переключения revision существующего Rule. Эти ограничения позволяют маркированный mock без предварительного разрешения X01/X02/X03 и не являются ограничениями всей будущей модели.
- **Гипотезы пользовательской проверки:** resource-first/request-first entrypoint, 9 групп/19 workspaces, выбор согласующих, будущий lifecycle и историческая композиция. Они не становятся Accepted от наличия mock или документационной трассировки. Решения владельца и проверка пользовательской полезности остаются отдельными шагами.

Основание: принятые N2 [requests](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/specs/access-requests/spec.md), [decisions](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/specs/access-decisions/spec.md), [export](https://github.com/lehater/napms-2/blob/9713c89bada6573bda2f60c97fb45deda48f5909/openspec/specs/policy-export/spec.md); временная граница и candidate provenance — [J06](user-journeys.md#j06-начать-со-своего-resource-или-с-технического-tuple-connectivity--checker), различия CONS — [traceability](product-requirements-traceability.md#уточнения-qreq-cons-для-будущей-спецификации).

## Решения владельца перед UX-acceptance

1. **P0** Правило и ревизия: какой устойчивый объект видит пользователь, как менять traffic contract при существующей разрешённой связи?
2. **P0** Resource/Endpoint/address cardinality и правила materialization (особенно несколько IP и неполные данные).
3. **P0** Какая часть 38 возможностей считается продуктовой целью N2 и какая остаётся только исследовательской гипотезой? Достаточно утвердить baseline границы, не все экраны.
4. **P1** Основной UX entrypoint: scoped Connectivity → запрос либо request workqueue → выбор source? Кто подтверждает owner/source mapping?
5. **P1** Объём первой демонстрации реальности: чистый mock future flows vs hybrid с работающей заявкой (не смешивать по статусу).
6. **P1** Можно ли считать собранный `ConfiguredEffectivePolicySnapshot` достоверным/полным и кто несёт ответственность за его качество в future requirements?
7. **P2** Какие отчёты/внешние системы реально нужны, а какие отложены без интерфейсного пункта?

## Передача координатору / проверка перед следующим этапом

**Рекомендация:** принять этот Draft PR как **исследовательский PARTIAL baseline**, а не продуктовую спецификацию. На отдельном review согласовать P0-01/02 и status для будущих capabilities. Далее можно строить широкий read-only UX mock по [IA](ux-information-architecture.md), сохраняя TBD/Unknown/SIMULATED. Content audit 108 оставшихся файлов и прежних решений о lifecycle завершён. До утверждения final UX остаются продуктовые решения и проверка пользователей; backend tests по старым subsystem, исторические Checker snapshots и real-device behavior остаются вне доказанного покрытия. Новый backend, frontend и OpenSpec сейчас не изменять.

## Минимальная единица оценки

Использовать общий интерфейс #151–#155 из [интеграционного ревью](https://github.com/lehater/napms-2/issues/150#issuecomment-7043459327): #151 отвечает за полномочия/инициацию, #152 — за доступ и read-back источника, #153 — за семантику Finding, #154 — за канонические ссылки/dedup, #155 — за оценку эффекта. В рамках #155 измеряется только заранее выбранный критерий Problem→Decision/мера; не переопределяются Finding и доступ к traces.

Вести одну оценку эффекта на canonical Problem и конкретное принятое Decision/меру. Канонический Problem — существующий GitHub Issue по самостоятельному вопросу; Decision и оценка эффекта хранятся в комментарии этого Problem Issue под отдельным стабильным `decision_key`. Повторный read/import идемпотентен для уже известной связи, но все новые уникальные evidence refs сохраняются; новые наблюдения могут поддержать существующий или новый distinct Finding. Evidence ref — locator записи источника; `finding_id` — стабильный локальный ключ аналитического Finding, не ID источника. `finding_ref` — canonical URL GitHub комментария/записи + ключ, если записей несколько; Finding↔Evidence допускает many-to-many. Если Problem уже существует, canonical Finding — комментарий на его Issue; иначе запись остаётся в существующем Issue/PR с execution context. При последующем появлении Problem сохранить первоначальный finding_ref/ссылку и связать записи, не копировать Finding. Повтор одного симптома обновляет evidence/ту же assessment и не создаёт автоматически новый Problem; если утверждение семантически отдельное, допустим distinct Finding, связанный с тем же Problem. Доставка меры и её эффект независимы: `delivery=merged` может сосуществовать с `effect_status=unknown`.

Для каждой оценки достаточно короткой записи:

Выбирать только относящиеся к исходной Problem/Decision метрики. Для дефекта handoff первичны правильность runtime/session boundary и полнота сохранённых фактов; для лишнего CI ожидания — повторные чтения того же завершённого run на неизменном HEAD и корректность финальной проверки; для потери качества — воспроизводимый outcome или независимое экспертное решение. Время, retries и вмешательства полезны, если предполагалось их изменение или они показывают цену исправления. Токены/расчётная стоимость полезны только при полном и сопоставимом учёте и конкретном вопросе о ресурсах. Общий usage, cached tokens, оценка USD в Langfuse и кэширование сами по себе не доказывают экономию подписочных лимитов или улучшение качества.

Источниками служат GitHub Issues/PR, точные commits и workflow runs, существующие тесты и review, а при наличии безопасного доступа — допустимые агрегированные оценки или трассы. CI доказывает только свойства, реально проверяемые соответствующими jobs; успешный CI не измеряет частоту дефекта в обычной работе. Экспертная оценка должна называть критерий и проверенные случаи. Показатель, который не собирался, остаётся неизвестным.

## Инициация, выборка и интерпретация

Coordinator инициирует read-only оценку при обычном handoff/разборе результата или завершении/прерывании существующей попытки; сам читает в пределах полномочий либо передаёт Refiner с нужным capability. Project Operator выполняет только отдельно разрешённые записи с independent read-back. Это существующая ответственность Coordinator, не новая роль/расписание. До чтения Coordinator фиксирует в существующем handoff критерий, окно/границу, определение eligible population, размер и правило выбора. Первый кандидат — одна уже завершённая обычная задача. Последующая ограниченная выборка может включать завершённые и/или прерванные attempts только если это предусмотрено заранее заданным критерием; не выбирать случаи постфактум по их исходу.

Для каждой выборки сохранять отдельные числа/списки `eligible`, `selected`, `checked_with_sufficient_coverage`, а также unknown/partial, исключения и причины. Допустимые причины исключения из проверенного покрытия фиксируются до чтения и включают выход за окно/критерий, прерванную попытку при заранее ограниченной выборке только завершённых задач, отсутствие требуемого read-only доступа или недоступный source. Выход за критерий может быть исключён из eligible с причиной; прерванные и недоступные случаи нельзя молча удалять: если они соответствуют eligible population, сохранять их в eligible, а если отобраны — также в selected, но не в checked_with_sufficient_coverage. Указать количество/ссылки, причину, `source_availability=unavailable|unknown` и `evidence_status=unverified`; результат для них `unknown`, а не `normal`. Отсутствующий доступ не превращать в отсутствие evidence.

Для каждой выбранной единицы результат по заранее названному критерию — `normal`, `finding` или `unknown`. `normal` означает достаточное покрытие именно для этого критерия и отсутствие Finding в проверенном покрытии; отсутствие Finding при неполном/недоступном источнике — `unknown`. Не трактовать `unknown` как норму. Если `finding` подтверждён и относится к той же Problem/мере, он становится evidence для оценки regression; если это самостоятельное утверждение, сохранить как distinct Finding, не создавая автоматически новую Problem. Неизвестный полный eligible знаменатель запрещает публиковать долю эффекта по eligible population. Если есть проверенные checkpoints, можно дать только ограниченную описательную долю `finding / checked_with_sufficient_coverage`, явно назвать checked subset, окно, покрытие/пропуски и ограничения; она не заменяет eligible метрику и не экстраполируется на невыбранные задачи или будущую работу. При пилотном n=1 вывод остаётся на уровне этой задачи/критерия, без вывода о частоте, точности или общем эффекте. В существующем handoff записываются GitHub outcome, evidence/capability gaps, результат `normal|finding|unknown`, coverage и next step со ссылкой на canonical assessment comment. Это процедура для будущего разрешённого обычного handoff; данная работа не запускала live pilot и не добавляла сбор данных.

Attempt — `(repository, primary issueId, runId)`; task — `(repository, issueId)`. `sourceSha` — только версия исходника/инструкций; CI run IDs и attempts хранятся отдельно. При повторном анализе идемпотентно распознавать прежние `finding_ref`/evidence refs, сохранять новые уникальные evidence refs, учитывать независимость attempts/tasks отдельно и при необходимости заводить новый distinct Finding под тем же Problem. Источники остаются raw-data source; не экспортировать raw traces/payload в GitHub.

## Решение по статусу эффекта

Не смешивать состояние Problem/Issue, решение о смягчении, доставку меры и результат проверки эффекта. `MITIGATED` означает, что мера принята/внедрена для воздействия на проблему; само по себе это не значение effect status и не подтверждение результата. Issue может быть закрыта, мера внедрена, а effect status оставаться `unknown`. Для одного Problem и связанного Decision/меры обновлять одну assessment-запись и накапливать в ней все новые уникальные evidence refs; повторная обработка уже известной ссылки идемпотентна, но не удаляет evidence и не запрещает отдельный distinct Finding при новом самостоятельном утверждении. Значения итоговой проверки эффекта:

- **Неизвестно:** post-change observations отсутствуют или их охват/полнота не позволяют ответить, либо случаи нельзя осмысленно сопоставить. Указать конкретный недостающий источник/знаменатель. Отсутствие зарегистрированного события не является нулём событий.
- **Подтверждено в оговорённых условиях:** post-change обычные случаи покрывают релевантные условия и показывают ожидаемый outcome по заранее названному критерию; известны объём, полнота и существенные смешивающие факторы; независимый review принимает интерпретацию. Формулировать узко — для наблюдавшейся категории и условий.
- **Регрессия / возврат к RCA:** воспроизведён исходный дефект или надёжно ухудшился связанный outcome. Сохранить ссылки и условия, вновь локализовать причину по Quality Escape protocol. Один неясный случай — сигнал для разбора, но не автоматическое доказательство регрессии.

Таким образом, для HE-001/004/005/009/011 допустимо сохранить `Problem/measure status=MITIGATED` и одновременно `effect status=unknown` до достаточных наблюдений. Per-criterion `normal` — результат проверенной единицы/выборки, не глобальное доказательство устранения; итоговый `confirmed` требует достаточного и сопоставимого покрытия по заранее заданному критерию.

Универсального численного порога и обязательного числа прогонов нет. До начала наблюдения владелец/ревьюер фиксирует, какое свидетельство будет достаточно именно для данного дефекта. Если дефект редкий или новые обычные случаи его не покрывают, оставить вывод неизвестным либо предложить владельцу ограниченный regression case с обоснованием риска и стабильным критерием. Такой сценарий требует отдельного решения, не заменяет обычное post-change evidence и не должен становиться произвольным A/B или набором повторов. Не делать причинный вывод из простой разницы «до/после»: меняются задачи, модели, люди и условия. При существенных различиях описывать ассоциацию и альтернативы.

Для #146 единица подсчёта — **eligible checkpoint**: обычная точка принятия решения по PR, где нужно определить следующий шаг по CI (использовать результат или ждать/передать), и Verify run для текущего неизменившегося PR head и конкретного attempt уже завершён. Первая проверка результата тоже eligible, но необходимое первое чтение не является avoidable reread. Checkpoint помечается как затронутый avoidable reread, только если в этой точке перечитали/повторно ждали тот же run/attempt при том же head, хотя результат уже прочитан и сохранён для текущего task и с последнего read-back не было нового run/attempt/head, изменения требуемого check или иного существенного события/вопроса. Полная метрика — количество затронутых eligible checkpoints / все eligible checkpoints за заранее определённое окно; несколько дублей в одном checkpoint дают один затронутый checkpoint. Количество лишних read/watch операций отдельно считается как события и не заменяет эту метрику.

Новый head, attempt или завершившийся после предыдущего read run создаёт новый eligible checkpoint, если в обычном ходе работы нужно принять решение по этому новому результату; чтение нового результата необходимо, не считать его avoidable. Изменение нужного blocking check или новый вопрос проверки также обосновывают чтение, даже когда SHA/run не изменились. Один PR/task может включать несколько checkpoints, поэтому рядом с их числом указывать число независимых задач/PR. Несколько checkpoints одной задачи отражают отдельные решения по CI, а не несколько независимых задач. Повторное событие по тому же Problem обновляет одну оценку, но не становится новым независимым affected task. Retries/resumes одной задачи и несколько CI attempts не считать независимыми задачами; попытки и дубли чтения перечислять отдельно как события с явной связью с исходной задачей согласно разграничению Finding/Problem/independent runs в [#154](https://github.com/lehater/napms-2/issues/154). Для каждого checkpoint записывать SHA версии инструкции, применённой в момент работы (в частности, `.agents/skills/execute-task/SKILL.md`), а также PR head SHA, run ID/attempt и основание для нового read.

Для documented сценария PR #149 run [44734789327](https://github.com/lehater/napms-2/actions/runs/44734789327) остаётся доступным в GitHub как completed/success на PR #148 head `91f80f4f31684444ae96b7eb03f48fc921f6fd7b`, attempt 1; это проверяемое retained CI evidence и оно подтверждает только корректную привязку/обработку существующего run при реализации. В PR #149 итоговый SHA принятых инструкций — `fec8fc4a01434aa9962793969abfb2cb4bf3fa2a` (merge commit `5c5a0fb765fe87305c11553facbdb4a20bd6596c`); запись о ручной проверке не фиксирует промежуточный checkout SHA в момент команды точнее, поэтому это граница атрибуции версии. Этот checkpoint был частью проверки реализации #146, поэтому исключён из обычной post-change выборки. В просмотренных записях #146 и PR #149 нет зарегистрированного 404; отсутствие записи не доказывает, что 404 никогда не случались. Полный eligible знаменатель и число обычных post-change checkpoints с достаточным покрытием неизвестны; поэтому долю эффекта для eligible population и описательную долю среди checked обычных checkpoints не приводим. Если последующая выборка даст checked checkpoints, допустима только явно ограниченная `finding / checked_with_sufficient_coverage` доля с раскрытием `eligible/selected/checked/unknown` coverage; она не заменяет eligible метрику и не даёт экстраполяции. Публичных task-level данных о качестве, времени, token usage, стоимости, retries, вмешательствах и handoff completeness в проверенных источниках недостаточно для сравнения. Закрытые Langfuse traces не проверялись: в среде исследования не обнаружены CLI или настроенные Langfuse environment variables, а доступ к self-hosted проекту и разрешённым агрегатам не был подтверждён. Это ограничение доступа, а не свидетельство отсутствия данных.

## Каноническая assessment запись и жизненный цикл

Единственная canonical assessment запись — комментарий на существующем Problem Issue с постоянным `decision_key`; assessment URL плюс ключ позволяют найти и обновить запись. Все последующие наблюдения дописывают уникальные `evidence_ref`/`finding_ref` в эту запись (повтор уже имеющейся ссылки идемпотентен), не создавая параллельную копию. При merge Action PR меняется только `measure_delivery`; комментарий Problem Issue сохраняется и продолжает связывать Decision с оценкой. Action Issue/PR содержит обратные ссылки на Problem Issue и `decision_key`. Раздельно обновляются: `measure_delivery` (например, accepted/merged), `problem_rca_status` (например, hypothesized/confirmed/open) и `effect_status` (unknown/confirmed/regression). Ни merge, ни закрытие Action Issue автоматически не меняют RCA/effect status.

Пример адреса для разбираемой меры HE-005: [Problem Issue #146](https://github.com/lehater/napms-2/issues/146) + `decision_key=HE-005/PR-149`; связанная мера — [PR #149](https://github.com/lehater/napms-2/pull/149). Assessment-комментарий с этим ключом должен быть canonical местом дальнейших обновлений; в проверенных записях такой отдельный комментарий пока не найден и этой документационной работой не создавался. Это явный gap сохранения истории, не свидетельство отсутствия evidence в других источниках.

## Langfuse и регрессионные проверки

Официальная документация Langfuse описывает Scores как записи числовой, категориальной, булевой или текстовой оценки для trace/observation/session/experiment; значения могут добавлять люди, код или LLM-judge ([Scores](https://langfuse.com/docs/evaluation/scores/overview)). Datasets могут хранить input/expected output и версии; Experiments запускают приложение и оценивают результат. Сравнение требует одной версии набора и evaluator definitions, но фиксированный dataset не делает ответы модели детерминированными ([Datasets](https://langfuse.com/docs/evaluation/experiments/datasets), [Compare experiments](https://langfuse.com/docs/evaluation/experiments/compare-experiments), [Experiments SDK](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk)). Score analytics полезны только при наличии осмысленных и полно собранных scores. Наличие функции не гарантирует корректность, privacy или репрезентативность данных проекта.

Для NAPMS практический порядок такой:

1. Обычное post-change evidence из релевантных Issues/PR/reviews/CI — путь по умолчанию, если дефект наблюдаем и задачи можно сопоставить.
2. Существующий deterministic test/regression case — сильное доказательство узкого инварианта, если он воспроизводит исходный дефект и проверяет corrected case. Это согласуется с Quality Escape protocol; тест доказывает контракт, а не полевую частоту дефекта.
3. Langfuse Scores — необязательный источник для конкретного показателя только при подтверждённых доступе и политике данных, стабильном определении score и известном покрытии. Использовать агрегаты и минимально необходимые поля; приватные traces/payload не переносить в публичный отчёт.
4. Dataset experiment — отдельно обоснованный ограниченный regression case, например для редкого, дорогого или воспроизводимого семантического дефекта без достаточной обычной экспозиции. Зафиксировать dataset/version, application/evaluator versions, критерий и ограничения judge; безопасный набор проверить до использования. Это возможность платформы, не обязательный lifecycle этап и не автоматическое доказательство production эффекта.

## Компактный отчёт владельцу

```text
Каноническая Problem / исходный дефект / ожидаемый outcome:
Canonical assessment: Problem Issue URL + stable decision_key + comment URL/key:
Linked Action Issue/PR (backlink to Problem + decision_key):
Measure delivery / Problem-RCA status / measured effect status (separate fields):
Criterion and window/boundary, eligible population, selection size and rule (fixed before read):
Counts: eligible / selected / checked with sufficient coverage / unknown or partial:
Exclusions and permitted reason per case; source_availability by source:
Per-criterion result: normal / finding / unknown; evidence_status and claim-specific confidence:
Baseline and post-change source refs; evidence_ref ↔ finding_ref (preserve unique refs):
Attempt (repository, primary issueId, runId) / task (repository, issueId) / sourceSha / CI run+attempt separately:
Comparability, applied instructions version, gaps and uncertainty:
If eligible denominator unknown: no eligible rate; optional checked-only descriptive share + coverage disclosure:
Interpretation, limits (no extrapolation), next action or stop:
```

Если поля отсутствуют, показать их как unknown/неполные и остановить вывод на достигнутом уровне. Не запускать новые прогоны автоматически: запросить только тот следующий обычный случай, стабильный regression case или доступ, без которого решение владельца невозможно. Не менять состояние Issue только по эффект-статусу: принятие Harness change, lifecycle Issue и подтверждение результата — разные решения.

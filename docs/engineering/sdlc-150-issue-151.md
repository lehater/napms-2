## Матрица ответственности

Роль — ответственность, Skill — метод, runtime — среда, capability — фактически доступные инструменты/права. Одна среда может нести несколько ролей, если для каждой у неё есть требуемые capabilities; имя роли само их не подразумевает. Аналитический контур — поток доказательств в управляющий контур, а не дополнительная роль или authority.

| Ответственность и источник | Вход → выход | Полномочия | Capability и критерий полноты | Стоп / передача |
|---|---|---|---|---|
| **Coordinator** — `workflow.yaml`, `decompose` | Ограниченный набор канонических Issues, состояние Project, принятые решения и evidence → выбранный outcome, приоритет/эскалация, одобренный желаемый state и portable handoff | Выбирает bounded scope, принимает рутинные решения в пределах политики, одобряет native изменения и сериализует конфликтующие операции; owner-level и irreversible решения эскалирует | Доступ к актуальным GitHub данным и нужному runtime/capability. Lifecycle состояния не являются метрикой подтверждённого эффекта. Подробности см. ## Пример нормализации входа в существующий handoff

Это иллюстрация применения текущего `refinement.handoff`, не новая форма или обязательный этап. Предположим, в чат поступает сообщение «#146 закрыта, но проект показывает Review — завершено ли это?». Тот же вопрос может прийти как GitHub Issue/комментарий или как автоматический Finding. Каждый источник сначала сохраняется как ссылка/идентификатор и утверждение, а не как подтверждённый факт. Для документированного случая #146 уже доступны независимые GitHub свидетельства: #150 сообщает о закрытии Issue после merge #149 при оставшемся `Review`; PR #149 указывает merge и Verify run `44737042797`, attempt 1, success на SHA `fec8fc4a01434aa9962793969abfb2cb4bf3fa2a`. Автоматический сигнал «Verify passed» подтверждает только результат CI для этого SHA, не Project Status или завершение всей задачи.

В существующий handoff Coordinator/Refiner нормализует этот набор так: **объект** `lehater/napms-2#146`; **утверждение/вопрос** — возможное расхождение статуса Issue и Project после PR #149; **источники** — чат-сообщение как исходная ссылка, [Issue #150](https://github.com/lehater/napms-2/issues/150), [PR #149](https://github.com/lehater/napms-2/pull/149), [Verify run #44737042797](https://github.com/lehater/napms-2/actions/runs/44737042797); **зафиксированные факты** — merge, `headRefOid`, run attempt/conclusion и ранее сообщённое значение `Review`; **неизвестное** — текущее значение Project Status; **следующее разрешённое действие** — перечитать state, а не считать CI сигнал доказательством Done. Источники чата, GitHub и автоматизированного анализа тем самым приводятся к уже существующим Issue/PR URLs, версии, принятому решению/вопросу, evidence, capability и следующему действию.

Перед выводом или native изменением повторно прочитать из GitHub поля, относящиеся к утверждению: для Issue — `state`, `stateReason`, `body`, `updatedAt`, labels/assignees и при необходимости issue type/field values; для PR — `state`, `isDraft`, `mergedAt`, `headRefOid`, `baseRefName`, `mergeStateStatus` и closing issue references; для CI — run ID, `head_sha`, `run_attempt`, `status`, `conclusion` и нужные check/job результаты; для Project — membership/item ID и `Status`, `Priority`, `Workstream`; для зависимости — полный native parent/sub-issue и `blocked_by` список со state/reason зависимостей. Это перечитывание выбирается по операции: CI Finding не требует Project write, но заявление о Done требует актуального Project read-back. Сопоставить свежие значения с версией/source SHA из handoff; при изменившемся `updatedAt`, PR head или run attempt обновить baseline до продолжения. Проверить доступ именно к нужному чтению/записи; authority на изменение берётся из сохранённого одобрения/контракта, а не из сообщения или имени роли.

Если обязательное поле или read-back недоступны, несовместимы по версии либо отсутствует право/одобрение, остановить только зависящий от них вывод и действие: не утверждать Done, не мутировать Project, записать проверенное частичное состояние, точное недостающее поле/разрешение и bounded next operation для runtime с нужной capability. Само Finding при этом сохраняет источник и известные факты. Такая остановка из-за недоступной capability или authority — не отклонение исполнения; отчёт о завершении шага, который был обязателен, разрешён и проверяемо пропущен, уже устанавливает отклонение.

Доступные записи — handoff-сводки, не полная история каждого действия. В рамках этого аудита не анализировались приватные payload или raw traces; отсутствуют независимые session/trace/telemetry данные, способные восстановить последовательность всех попыток или стоимость. Это ограничивает RCA и baseline, но не мешает выводам о документированных GitHub state. #8 запрещает выводить agent-cost/внутренние причины из одних CI данных; #10 требует отделять подтверждённую причину от гипотезы и допускает решение не менять Harness. Draft [PR #138](https://github.com/lehater/napms-2/pull/138) — исследовательский материал, не источник принятых правил.

## Покрытие цикла и варианты

Схематичный цикл #150 — Finding → Problem → исследование → решение → фиксация → подготовка → реализация → проверка эффекта — раскладывается на существующие ответственности: evidence и Problem фиксируются в каноническом GitHub Issue/PR; Coordinator ограничивает scope и решение/эскалацию; Refiner исследует и предлагает контракт; Coordinator одобряет; Project Operator применяет и перечитывает native state; Worker выполняет только Ready-контракт после R1–R7; Reviewer независимо оценивает diff/evidence; owner принимает/отказывает; последующая обычная работа сравнивает outcome с исходным Problem. Качество и эффективность Harness идут одним evidence-first управленческим путём, но сохраняют различие природы наблюдения. Аналитический поток может передать Finding с источником и ограничениями; он не принимает решение и не создаёт новую authority.

| Альтернатива | Оценка |
|---|---|
| Создать отдельную роль, Skill, реестр, gate или client-specific ChatGPT→Codex handoff | Не подтверждена: роли и portable GitHub handoff уже определены; нет evidence, что новая сущность устранит установленную причину. Увеличит дублирование/процесс без измеренного эффекта. |
| Считать #127 достаточным и ничего не наблюдать | Нормативно достаточно, но недостаточно для ответа на вопрос об операционной эффективности: #150 фиксирует повторные поручения и рассогласование state. |
| Сохранить контракт и проверять конкретные условия в следующих обычных handoff; при каждом доказанном пропуске фиксировать отклонение, затем отдельно оценивать причину и обоснование узкого изменения | Рекомендуется: соответствует #10 и roadmap, не требует повторения для признания факта отклонения, но и не выводит системную причину из единичного случая; отличает отсутствие capability/authority от невыполнения доступного действия и не ослабляет admission/review. |

## Рекомендация и проверка результата

Сохранить действующие `workflow.yaml`, Skills, роли, R1–R7, Project lifecycle и GitHub как source of truth. Нормативные инструкции этим исследовательским PR не менять; реализация Harness не авторизована. На следующих обычных native Project/PR handoff оценивать имеющуюся запись по четырём вопросам: (1) известны ли цель, версия источника, ожидаемый выход и граница задачи; (2) проверены ли необходимые runtime capabilities и mutation authority; (3) отделены ли предложенные, одобренные, выполненные и read-back операции, с точными остатками при остановке; (4) различены ли Ready/admission, Review/acceptance, Done и подтверждённый эффект.

Для каждого примера фиксировать канонический Issue/PR/run, exact source/head, принятый выход, native read-back, неразрешённые операции и причину остановки, если она сообщена. Один верифицированный шаг, требуемый контрактом и разрешённый действующим одобрением, но не выполненный/не проверенный, достаточен для регистрации deviation; повторные поручения, повторные операции и время описывают масштаб/влияние, но не являются условием этого факта. Независимый Reviewer проверяет конкретное требование, authority, доступность capability и evidence пропуска на правильном HEAD. Отдельно исследуются ближайшая причина, связь с системным правилом, повторяемость и воздействие. Отсутствие capability/authority — корректная остановка и bounded handoff, не deviation.

Каждый верифицированный пропуск сначала записывается как отклонение с точным требованием, authority, источником и read-back; затем исследуется ближайшая причина и проверяется, есть ли системный дефект текущего правила/метода. Повторяемость усиливает аргумент и помогает оценить влияние, но не является обязательным порогом: единичный случай может оправдать изменение при доказанной предотвращаемой причине и существенном воздействии; без установленной причины, повторяемости или значимого риска достаточно сохранить evidence и наблюдать, не меняя Harness. Для отдельного evidence-based Issue зафиксировать точный пример → локализованный шаг потери → причины и альтернативы → ожидаемый риск/пользу → минимальный вариант → способ проверки обычной работой → owner review. Если это корректная граница возможностей или нет обоснованной пользы изменения, оставить Harness без изменения. После любого принятого исправления отдельно проверить эффект на последующих обычных задачах; merge и зелёный CI доказывают интеграцию, не устранение проблемы. Такой подход следует [Quality Escape Handling](https://github.com/lehater/napms-2/blob/2fdd3c9a7b32db891fdd3216ee1d55f85e8d06c4/docs/engineering/quality-escape-protocol.md) и [SDLC roadmap](https://github.com/lehater/napms-2/blob/2fdd3c9a7b32db891fdd3216ee1d55f85e8d06c4/docs/engineering/sdlc-improvement-roadmap.md).

## Матрица ответственности

Роль — ответственность, Skill — метод, runtime — среда, capability — фактически доступные инструменты/права. Одна среда может нести несколько ролей, если для каждой у неё есть требуемые capabilities; имя роли само их не подразумевает. Аналитический контур — поток доказательств в управляющий контур, а не дополнительная роль или authority.

| Ответственность и источник | Вход → выход | Полномочия | Capability и критерий полноты | Стоп / передача |
|---|---|---|---|---|
| **Coordinator** — `workflow.yaml`, `decompose` | Ограниченный набор канонических Issues, состояние Project, принятые решения и evidence → выбранный outcome, приоритет/эскалация, одобренный желаемый state и portable handoff | Выбирает bounded scope, принимает рутинные решения в пределах политики, одобряет native изменения и сериализует конфликтующие операции; owner-level и irreversible решения эскалирует | Доступ к актуальным GitHub данным и нужному runtime/capability. Полнота: зафиксированы источник/версия, цель, необходимые операции, права, выбранная среда/режим и граница сессии | Неясный продуктовый приоритет, права, существенная неопределённость или отсутствующая capability → сохранить Preparing/вернуть точные следующие операции; не заявлять, что операция выполнена |
| **Refiner** — `decompose` Skill, решение #127 | Исходные/кандидатные Issues, открытая и закрытая история, проектные данные и доказательства → предложение reuse/decompose по D1–D8, классификация/приоритет и один проверяемый контракт на executable Issue | Исследует и предлагает; не утверждает, что GitHub изменения сохранены | GitHub/repo/OpenSpec чтение по необходимости; для исполнения не требует фиксированной модели или среды. Полнота: проверены дубликаты, предыдущие решения, native blockers и scope; критерии, verification, capabilities и escalation записаны | Неясность/конфликт/непроверенные данные → минимальный вопрос/доказательство, оставить Preparing; native запись передать Project Operator |
| **Project Operator** — `workflow.yaml`, шаги 8–10 `decompose` | Одобренный план с baseline и ожидаемыми native значениями → применённые операции, ID, независимый read-back и различия | Только одобренные GitHub CLI/API записи; не принимает бизнес-решения и не заменяет native relations Markdown-ссылками | Фактические права на каждый ресурс/endpoint, чтение и пагинация. Полнота: перечитан каждый затронутый Issue, Project item/field, parent/sub-issue, blocker и Status; успешный write-response сам по себе не доказательство | Stale baseline, partial write, unknown option, отказ/недоступность API → остановить зависимые операции, записать проверенную частичную state и остаток; не отмечать Ready |
| **Worker** — `execute-task`, R1–R7 | Open + Ready Issue, свежий достаточный контракт, доступные инструменты и unblocked scope → результат в собственной ветке/PR и воспроизводимые проверки | Исполняет только принятый контракт; существенное изменение scope/решения возвращает к подготовке | Repo/CI/runtime capabilities под задачи. Полнота: выполнены acceptance и применимые проверки; в handoff указан exact PR head и соответствующий CI/ограничения | R1–R7 не выполнены, контекст устарел, неизвестное решение или capability недоступна → остановить/вернуть в Preparing либо bounded handoff; не маскировать отсутствие права как агентскую ошибку |
| **Reviewer** — независимость закреплена `workflow.yaml`, #127, roadmap и quality-escape protocol | PR, требования, результат и evidence → независимое заключение об acceptance/изменениях и решение owner на интеграцию | Независимое review; не подменяет owner acceptance/merge | Доступ к исходному контракту, diff, проверкам и их точному HEAD. Полнота: verdict привязан к поведению и evidence; CI, mergeability и owner acceptance различены | Неполное evidence/другой HEAD/неразрешённое решение → запрос исправления или эскалация; не считать зелёный CI доказательством эффекта |

D1–D8 задают границы декомпозиции; R1–R7 — admission. Существующие workflow `desired_state`, `handoff`, routing и lifecycle уже определяют source of truth (GitHub Issue, native Project state и связанный PR), версионирование, read-back, идемпотентность, остановку при частичных сбоях и повторную передачу. Lifecycle состояния не являются метрикой подтверждённого эффекта. Подробности см. [workflow policy](https://github.com/lehater/napms-2/blob/2fdd3c9a7b32db891fdd3216ee1d55f85e8d06c4/.ai/workflow.yaml) и [Issue #127](https://github.com/lehater/napms-2/issues/127).

**Гипотезы, не установленные причины:** недостаточно заметные критерии завершения поручения; неоднозначность mutation authority; пропуск capability discovery; непоследовательное применение read-back; смешение рабочего статуса, назначения и acceptance; ограничение runtime/контекста. Все эти варианты требуют наблюдения конкретного перехода и его сохранённого handoff. Нельзя выбрать один только по числу поручений.

Доступные записи — handoff-сводки, не полная история каждого действия. В рамках этого аудита не анализировались приватные payload или raw traces; отсутствуют независимые session/trace/telemetry данные, способные восстановить последовательность всех попыток или стоимость. Это ограничивает RCA и baseline, но не мешает выводам о документированных GitHub state. #8 запрещает выводить agent-cost/внутренние причины из одних CI данных; #10 требует отделять подтверждённую причину от гипотезы и допускает решение не менять Harness. ## Покрытие цикла и варианты

Схематичный цикл #150 — Finding → Problem → исследование → решение → фиксация → подготовка → реализация → проверка эффекта — раскладывается на существующие ответственности: evidence и Problem фиксируются в каноническом GitHub Issue/PR; Coordinator ограничивает scope и решение/эскалацию; Refiner исследует и предлагает контракт; Coordinator одобряет; Project Operator применяет и перечитывает native state; Worker выполняет только Ready-контракт после R1–R7; Reviewer независимо оценивает diff/evidence; owner принимает/отказывает; последующая обычная работа сравнивает outcome с исходным Problem. Качество и эффективность Harness идут одним evidence-first управленческим путём, но сохраняют различие природы наблюдения. Аналитический поток может передать Finding с источником и ограничениями; он не принимает решение и не создаёт новую authority.

| Альтернатива | Оценка |
|---|---|
| Создать отдельную роль, Skill, реестр, gate или client-specific ChatGPT→Codex handoff | Не подтверждена: роли и portable GitHub handoff уже определены; нет evidence, что новая сущность устранит установленную причину. Увеличит дублирование/процесс без измеренного эффекта. |
| Считать #127 достаточным и ничего не наблюдать | Нормативно достаточно, но недостаточно для ответа на вопрос об операционной эффективности: #150 фиксирует повторные поручения и рассогласование state. |
| Сохранить контракт и проверить конкретные условия в следующих обычных handoff; при повторении локализовать разрыв и отдельно согласовать узкое изменение | Рекомендуется: соответствует #10 и roadmap, не предрешает RCA, позволяет отличить отсутствие capability/authority от невыполнения доступного действия и не ослабляет admission/review. |

## Рекомендация и проверка результата

Сохранить действующие `workflow.yaml`, Skills, роли, R1–R7, Project lifecycle и GitHub как source of truth. Нормативные инструкции этим исследовательским PR не менять; реализация Harness не авторизована. На следующих обычных native Project/PR handoff оценивать имеющуюся запись по четырём вопросам: (1) известны ли цель, версия источника, ожидаемый выход и граница задачи; (2) проверены ли необходимые runtime capabilities и mutation authority; (3) отделены ли предложенные, одобренные, выполненные и read-back операции, с точными остатками при остановке; (4) различены ли Ready/admission, Review/acceptance, Done и подтверждённый эффект.

Для каждого примера фиксировать канонический Issue/PR/run, exact source/head, принятый выход, native read-back, неразрешённые операции и причину остановки, если она сообщена. Считать повторные поручения, повторное чтение/изменение ресурсов и время только если эти данные доступны из обычной записи; не реконструировать скрытые причины или стоимость. Независимый Reviewer проверяет, что оценка относится к требуемому выходу и правильному HEAD. Наблюдаемое отсутствие capability/authority — корректная остановка и bounded handoff; дефект подтверждается лишь если доступное и разрешённое действие преждевременно объявлено завершённым или повторно теряется при ясном контракте.

Повторяемый разрыв между текущим критерием и фактическим результатом следует оформить отдельным evidence-based Issue: точный пример → локализованный шаг потери → минимальный вариант/альтернатива → воспроизводимый способ проверки обычной работой → owner review. Если разрыв не повторяется или причина — корректная граница возможностей, оставить Harness без изменения. После любого принятого исправления отдельно проверить эффект на последующих обычных задачах; merge и зелёный CI доказывают интеграцию, не устранение проблемы. Такой подход следует [Quality Escape Handling](https://github.com/lehater/napms-2/blob/2fdd3c9a7b32db891fdd3216ee1d55f85e8d06c4/docs/engineering/quality-escape-protocol.md) и [SDLC roadmap](https://github.com/lehater/napms-2/blob/2fdd3c9a7b32db891fdd3216ee1d55f85e8d06c4/docs/engineering/sdlc-improvement-roadmap.md).

**Ограничения вывода:** проведён документальный аудит принятых и текущих GitHub записей, не длительное наблюдение операционной выборки. Причинность и частота сбоев не установлены; влияние #147–#149 на обычные handoff ещё не измерено. Отчёт является исследовательским результатом #151, не согласованием нового обязательного процесса и не разрешением на изменение Harness.

# SDLC-03 — проверка готовых схем оценки coding-агентов

**Issue:** [#9](https://github.com/lehater/napms-2/issues/9) · **Дата исследования:** 2026-11-07 · **Статус:** research / проект решения, не внедрение.  
**Контекст:** `OpenSpec → Codex CLI → GitHub PR → Actions → review`. Цель — проверить добавленную ценность оценки агента, не создавать новый Harness.

## 1. Что подтверждено первичными источниками

| Подход | Подтверждённый механизм | Применимость / граница |
| --- | --- | --- |
| **Простой Codex CLI + JSONL + тесты** | [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode): `codex exec --json` отдаёт JSONL событий и при наличии token usage. | Уже совместим с нашим workflow, без нового eval-инструмента. Требует ручной организации фикстур и повторений. |
| **Promptfoo + Codex SDK** | [Специализированный provider](https://www.promptfoo.dev/docs/providers/openai-codex-sdk/): Codex SDK, workspace/sandbox, streaming events, token usage, traces, проверочные assertions; есть [гайд по coding agents](https://www.promptfoo.dev/docs/guides/evaluate-coding-agents/). Документирован повторный вход через существующую авторизацию Codex/ChatGPT без API key. | **Главный кандидат на минимальный pilot интеграции.** Для файловых задач необходимо отдельно проверять результат на диске: обычный `response.output` — только финальный текст Codex, не доказательство корректности кода. Проверять версии Promptfoo/SDK/CLI; не считать API-оценку стоимости реальными расходами подписки. |
| **Inspect AI + Inspect SWE** | [Inspect tutorial](https://inspect.aisi.org.uk/tutorial.html) и [Inspect SWE Codex CLI](https://meridianlabs-ai.github.io/inspect_swe/codex_cli.html): агент как solver, фикстуры, scorers, Docker sandbox и log viewer. | Сильный вариант для систематических воспроизводимых экспериментов. В Inspect SWE запросы к модели проксируются через модельный provider Inspect; совместимость с нашей локальной ChatGPT-авторизацией **не подтверждена** — не предполагать нулевую стоимость. |
| **Harbor / Terminal-Bench / SWE-bench** | [Harbor](https://github.com/harbor-framework/harbor) запускает coding agents в контейнерах; [SWE-bench](https://github.com/SWE-bench/SWE-bench/blob/main/docs/reference/harness.md) оценивает патчи в Docker с тестовым оракулом. | Проверенные **принципы** оценки реального результата; как инфраструктура для одной малой задачи — избыточны. Рассматривать при расширении собственного датасета до серии задач. |
| **DeepEval + GEval** | [DeepEval](https://deepeval.com/docs/introduction) оценивает конечные outputs или инструментированные агентные трассы, [trajectory evaluation](https://deepeval.com/docs/evaluation-trajectory-based-llm-evals) требует tracing. [Ollama](https://deepeval.com/integrations/models/ollama) поддерживается. | Подходит для **дополнительного** LLM-judge: неоднозначное соблюдение инструкций, качество объяснения. Не заменяет исполняемые тесты; Codex JSONL не является native DeepEval trace. |
| **Референсный improvement loop** | [OpenAI Cookbook, май 2026](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop): traces → human/model feedback → Promptfoo evals → проверяемая гипотеза улучшения → Codex handoff. | Методика применима. В примере исходный агент построен на Agents SDK, а не нашем Codex CLI: переносить принцип, **не** копировать всю интеграцию. |

**Оговорка о зрелости:** общая зрелость Promptfoo/Inspect не доказывает зрелость каждой свежей интеграции. Документация Promptfoo Codex SDK обновлена 2026-11-05 — проверить именно связку с текущей локальной версией Codex в ограниченном эксперименте, прежде чем внедрять её в процесс.

## 2. Архитектурный принцип, общий для проверенных схем

```
Фиксированный task + контракт + исходный commit
    → изолированный рабочий каталог
    → coding agent (Codex)
    → реальный diff / изменённые файлы + проверенные события
    → независимые tests / oracle / review
    → факультативный LLM judge (только если даёт новый сигнал)
    → сохранённый результат + управляемое изменение Harness
```

Основной критерий — **фактическое состояние файлов и исполняемые проверки**, а не правдоподобие последнего сообщения агента. Не передавать агенту скрытый oracle до завершения выполнения. Хранить versions, исходный SHA, seed/temperature там, где доступны, условия sandbox и идентификаторы запусков; не делать вид, будто LLM-трасса детерминирована. Количество токенов — измерение использования, но не доказательство денежной стоимости при подписочной авторизации.

[OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) рекомендуют task-specific dataset, objective metrics и калибровку model graders по экспертной разметке. На одном положительном и одном отрицательном кейсе нельзя утверждать валидность LLM judge; это только техническая проверка гипотезы.

## 3. Ревью текущего проекта PR #15

- **P1 — цель/метод смешаны.** В [исходном протоколе](sdlc-03-deepeval-spike.md) DeepEval назначен до сравнения существующих платформ. Исправление: считать его одним из кандидатов, не обязательным компонентом.
- **P1 — источник истины для code correctness.** `GEval` над **текстом Python-файла** не должен решать, верна ли реализация, если это можно проверить исполняемыми тестами. Добавить независимый contract-oracle для требований, отсутствующих в `check_public.py`; затем сравнить, дал ли LLM-judge *новое* замечание и сколько ложных тревог.
- **P1 — сохранность измерения.** Данные одного шага Codex CLI можно сравнивать только при фиксированном исходном commit и чистом workspace. `Promptfoo copy_working_dir` или Docker — будущие средства автоматизации, не предпосылка первого ручного smoke-test.
- **P2 — репрезентативность.** Синтетический CSV-контракт полезен для проверки интеграции, но не отражает сложность OpenSpec/архитектурных изменений NAPMS. Не переносить выводы на качество всего Harness.
- **P2 — расходы.** Promptfoo SDK может использовать существующий Codex sign-in, однако backend model и API-оценка cost должны быть зафиксированы отдельно. Ни Promptfoo, ни DeepEval не считать «бесплатными по подписке» для LLM-judge без подтверждения конкретного способа запуска.

## 4. Предложенный порядок и gate на смену инструмента

1. **Baseline без дополнительного framework:** использовать уже подготовленную синтетическую задачу из `experiments/sdlc-03`; единственный Codex run + фактические файлы/JSONL + public tests + независимый contract-oracle. Это проверит саму измерительную методику.
2. **Узкий pilot Promptfoo:** на **той же** задаче проверить, что `openai:codex-sdk` действительно запускается с текущим ChatGPT login, работает из отдельного workspace, отдаёт доступные события и результаты можно объективно сопоставить с пунктом 1. Сохранить версии, измеренные накладные расходы и ограничения. Предпочитать описанные конфигурационные параметры вместо собственных адаптеров.
3. **DeepEval / локальный Ollama:** только если тесты и экспертный review оставляют **семантическую** проблему, которую LLM-as-a-Judge способен проверить. Отрицательный контроль, повторяемые оценки, явно проверенная модель; без такого сигнала — **defer**, не устанавливать.
4. **Inspect SWE / Harbor:** исследовать дальше при появлении набора сопоставимых задач, потребности в многократных контейнерных запусках или системном сравнении моделей/агентов.

**Точка согласования:** прежде чем тратить запуск Codex на выбор инструмента, решить, принимаем ли изменение SDLC-03: *сравнить сначала bare Codex с direct Promptfoo/Codex SDK и оставить DeepEval optional*, сохранив текущую задачу/контракт. До согласования не менять Harness, CI, основной стек или статус PR #15. Любое решение adopt/defer/reject делать по реально полученным результатам, а не по заявленным возможностям.

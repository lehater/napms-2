# SDLC-03 — проект минимального эксперимента DeepEval

**Issue:** [#9](https://github.com/lehater/napms-2/issues/9) · **Статус:** подготовка; **реальный прогон Codex и DeepEval ещё не выполнен**.  
**Дата:** 2026-11-07. **Источник истины:** GitHub `main` и этот Draft PR.  
**Исходные сравнения:** [SDLC-01](quality-gates-baseline.md), [SDLC-02](sdlc-observability-baseline.md).

## Цель / гипотеза

Проверить, обнаружит ли DeepEval **хотя бы одно содержательное нарушение требований в результате работы Codex**, которое не выявлено ограниченными публичными тестами, и при этом не будет ошибочно отклонять корректный результат.

Это **feasibility spike**, не статистический benchmark. Даже положительный результат одной задачи **не доказывает**, что DeepEval улучшает Harness.

## Экспериментальная единица

- Одна фиксированная задача на реализацию `render_policy_csv` из [контракта](../../experiments/sdlc-03/contract.md).
- Агент изменяет только `experiments/sdlc-03/policy_csv.py` из исходной заглушки; остальные файлы не меняет. Никаких продуктовых изменений и новых OpenSpec changes.
- **Вход**: текст контракта, неизменяемые `check_public.py` и [Codex task](../../experiments/sdlc-03/codex-task.md), head commit эксперимента.
- **Выход**: фактический diff и полный итоговый файл, exit code публичных тестов, финальное сообщение Codex, только доступные машинные события `codex exec --json`.
- Публичные проверки охватывают только пустой экспорт, сортировку и quoting; независимое ревью должно отдельно проверить остальные требования (валидацию, отсутствие чувствительных полей, защиту от формул и неизменность входа).
- Сценарии приемки формулируются как *WHEN* поступает пустой список *THEN* только заголовок; *WHEN* есть записи в разном порядке *THEN* они сортируются; *WHEN* в поле есть формула/невалидный decision *THEN* действует соответствующее ограничение из контракта. Это исследовательский контракт, **не принятие новой продуктовой OpenSpec-спецификации**.

## Наблюдаемые данные Codex

Официальный `codex exec --json` выдаёт JSONL-события `thread.started`, `turn.*`, `item.*`; `turn.completed.usage` может содержать счётчики токенов. Это **не** готовая DeepEval trace. Наличие и фактические поля подтвердить на единственном локальном прогоне.

Нельзя утверждать: число внутренних reasoning-шагов, стоимость в валюте, точную агентную траекторию или корректность tool calls только по финальному ответу. Raw JSONL хранить локально, публично публиковать лишь проверенную на отсутствие секретов сводку + идентификатор commit. Не коммитить `~/.codex`, токены, приватные трассы, дампы окружения.

## Исполнимость и контроль затрат до запуска агента

Важное ограничение: управляющий чат **не имеет доступа к пользовательскому WSL2** и не может подтвердить наличие конкретной локальной модели. До запуска Codex необходимо проверить `ollama list`, доступность сервера `http://127.0.0.1:11434/api/version`, `codex --version` и чистоту checkout. Если подходящей локальной модели нет, **не тратить единственный прогон Codex только на этот пилот**: зафиксировать blocker и выбрать дальнейший вариант с владельцем.

DeepEval eval-runner: [`experiments/sdlc-03/run_geval.py`](../../experiments/sdlc-03/run_geval.py). Для повторения пилота выбран `deepeval==4.3.3` (доступная опубликованная версия на 2026-11-07); устанавливать **только** в отдельный временный venv, после проверки модели. Runner принимает путь к фактическому результату Codex, путь к **отдельно помеченному отрицательному контролю**, необязательный подтверждённо корректный reference, имя существующей Ollama-модели, путь к локальному JSON-выводу. Никаких API-ключей и новых зависимостей продукта.

Для каждого образца runner делает 3 последовательных независимых вызова `GEval.measure()`, запрашивает оценку по фиксированным критериям, записывает баллы/обоснования/ошибки и SHA-256 исходного кода; кэширование результатов не используется. Само наличие выводов по одному заданию **не доказывает** устойчивость оценщика. Если Codex-реализация не проходит полный oracle, для проверки **ложных отклонений** нужен третий, отдельно маркированный исправный reference — иначе нельзя объявлять Codex результат положительным контролем.

Независимый oracle из 12 дополнительных проверок удерживается **вне ветки, доступной Codex**, до первого запуска; он уже отдельно проверен на заведомо корректной и дефектной реализациях (12/12 PASS и 1/12 FAIL соответственно), тогда как дефектная реализация проходит публичные 2/2 теста. После запуска агентного кода координатор должен выполнить oracle против точного head SHA. Это методологическая проверка тестов, **не результат Codex и не DeepEval score**.

## Выполнение — только после проверки исполнимости

**Шаг 1 — локальный Codex (делегируется; однократно):** только после preflight модели на выделенной ветке и исходной заглушке проверить `codex --version`, `python --version`, исходный head SHA и отсутствие локальных изменений; запустить без расширенных прав:

```bash
# В уже существующем /home/alex/projects/napms-2; ветку не пересоздавать
git fetch origin
git switch research/sdlc-03-deepeval-spike
git pull --ff-only
# git status --porcelain должен показать пустой вывод
codex --version
python --version
ollama list
curl --noproxy "*" -fsS http://127.0.0.1:11434/api/version
codex exec --sandbox workspace-write --json \
  "$(cat experiments/sdlc-03/codex-task.md)" \
  > /tmp/napms-sdlc-03-codex.jsonl
codex_exit=$?; printf "Codex exit code: %s\\n" "$codex_exit"
python -m unittest discover -s experiments/sdlc-03 -p 'check_public.py' -v
git diff --check
git diff -- experiments/sdlc-03/policy_csv.py
```

Сохранить код завершения команды и факт наличия `turn.completed`. Если `codex exec` не завершился успешно, это результат эксперимента — не исправлять его вторым неучтённым запуском. Перед `git push` коммитить только изменённый `policy_csv.py`; повторно использовать эту же ветку/PR. Содержание JSONL проверять локально перед любым публичным переносом.

**Шаг 2 — контрольный результат (управляющий чат):** после push провести ручное contract-review по полному файлу и выполнить независимые дополнительные проверки по всем пунктам контракта. Сохранить бинарный статус публичных тестов, количество пропущенных контрактных пунктов и идентификатор commit. Создать один **явно маркированный** отрицательный контроль в *отдельной локальной копии*: код должен проходить public checks, но нарушать одну существенную оговорку контракта. Контроль **не выдавать за вывод Codex** и не переносить в продукт. Не использовать отрицательный пример в промпте агента.

**Шаг 3 — DeepEval (локальное изолированное окружение, только если есть подходящая модель):** проверить `ollama list` и доступность локального сервера. При отсутствии установленной модели остановиться и записать блокер; не скачивать большие модели и не подключать платные API без отдельного решения.

Использовать **`deepeval==4.3.3`** в отдельном venv; `GEval` с фиксированными `evaluation_steps` и `SingleTurnParams.INPUT, ACTUAL_OUTPUT, EXPECTED_OUTPUT`. Фактический `actual_output` — **полный код итогового файла**, не самоотчёт агента; `input` — неизменный контракт; `expected_output` — критерии приёмки. Оценивать корректный кандидат и негативный контроль по **3 раза каждый** одной моделью, temperature 0, без кэша; сохранять каждый score и объяснение, включая ошибки API/JSON. Не заменять отсутствующие оценки нулями.

В отдельном процессе перед импортом DeepEval включить `DEEPEVAL_DISABLE_DOTENV=1` и `DEEPEVAL_TELEMETRY_OPT_OUT=1`; не вызывать `deepeval login`, не использовать `CONFIDENT_API_KEY`. Использовать локальный `OllamaModel(model=<installed>, base_url="http://localhost:11434", temperature=0)`, а не неявную модель по умолчанию. Никаких новых CI gates.

После реализации кода и независимого oracle координатор предоставляет путь к проверенному локальному отрицательному контролю, при необходимости — к положительному. Команды для запуска оценщика (в WSL2; `<installed-model>` заменить на точное имя из `ollama list`):

```bash
python -m venv /tmp/napms-sdlc03-venv
/tmp/napms-sdlc03-venv/bin/python -m pip install 'deepeval==4.3.3'
DEEPEVAL_DISABLE_DOTENV=1 DEEPEVAL_TELEMETRY_OPT_OUT=1 \
  /tmp/napms-sdlc03-venv/bin/python experiments/sdlc-03/run_geval.py \
    --candidate experiments/sdlc-03/policy_csv.py \
    --negative /tmp/napms-sdlc03-negative.py \
    --model '<installed-model>' \
    --out /tmp/napms-sdlc03-geval.json
```

`--reference /tmp/napms-sdlc03-reference.py` указывать только при наличии отдельно проверенной корректной реализации. Не запускать без контролей и не публиковать сырые Codex-трассы или JSON с чувствительными данными. Устанавливать зависимости **только после preflight**, и не делегировать Codex исследования/выбор метрик.

## Протокол сравнения / решение

| Источник | Что проверяет | Выход |
| --- | --- | --- |
| Публичный `unittest` | Базовые детерминированные случаи | PASS/FAIL |
| Ручное ревью + дополнительные контрактные проверки | Полный контракт и фактический код | По каждому требованию PASS/FAIL + подтверждение |
| DeepEval `GEval` | Семантическое соответствие кода контракту | Все 3 оценки + обоснования для каждого из двух образцов |
| Codex JSONL | Доступные события и usage; без домыслов | Версии, exit code, доступные token counts |

Отдельно перечислить: **false positive** (дефектный код оценён как хороший), **false negative** (корректный код оценён как плохой), расхождения между тремя повторами; отсутствие результата — `unknown`. Ручное ревью не заменять мнением судьи.

Решение:
- **Adopt для более широкого эксперимента**, только если модель корректно различает оба образца по содержательным причинам и демонстрирует дополнительный сигнал относительно public checks. Не означает автоматического включения в CI.
- **Defer**, если нет подходящей локальной модели, данные/стоимость/вариативность не позволяют оценку либо нужен более широкий эксперимент.
- **Reject для данного сценария**, если оценщик стабильно выдаёт некорректные/неинформативные результаты или не даёт сигнала сверх обычных проверок при той же стоимости.

Дата: 2026-11-20. Статус: исследование и рекомендуемые решения для review; **не реализация**.
Источник проблем и измерений: [реестр](harness-efficiency-register.md), [Draft PR #138](https://github.com/lehater/napms-2/pull/138).
Проверенный baseline: [main 9ce93c5](https://github.com/lehater/napms-2/tree/9ce93c5760643407e0ccd0f7bcaa24b583cdb363). Прочитаны AGENTS.md, .ai/workflow.yaml, .ai/codex-task-tracing.md, decompose/execute-task, schema/template и SDLC roadmap. Исторические #10, #87, #88, #93, #94, #119, #121, #129–#131 проверены; они закрыты, не возобновляются автоматически. #127 касается refinement pipeline, а не общего устранения потерь. ## Методика и сила доказательств

Разделяем (1) наблюдение и RCA, (2) исследование вариантов и решение, (3) Issue реализации, (4) PR/приёмку, (5) оценку эффекта. Исследование сохраняется в этой ветке; реализация начинается от свежего main по отдельному принятому контракту. Для выбора: подтверждённая локальная причина, применимость существующей практики, стоимость сопровождения, риск качества, обратимость и наблюдаемая приёмка. Допустимый результат — ничего не менять. Не создавать статусную систему сверх .ai/workflow.yaml.

**Эмпирическое основание, не прогноз для NAPMS:** NeurIPS 2024, [SWE-agent, таблицы 1 и 3](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf): на SWE-bench Lite GPT-4 Turbo shell-only 11% решённых задач при средней стоимости $1,46, ACI 18% при $1,67; история последних пяти наблюдений 18% против 15% с полной историей. Это аргумент за качество интерфейса и селективный контекст, не свидетельство, что любой справочник или сброс сессии снижает стоимость. [OpenAI Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform) сообщает на ARC-AGI-3 рост результата 13,3%→38,3% и сокращение output tokens в шесть раз при **сочетании** retained reasoning и compaction. Это другой benchmark, не выделенный эффект сброса сессии. Для NAPMS причинные эффекты не измерены. Сильнее всего применимы факты нашего архива и официальные контракты инструментов; рекомендации поставщиков не считаются экспериментальным доказательством экономии.

## HE-009 — изменяемые контракты GitHub CLI/API

**Подтверждение:** в архиве непосредственно видны Unknown JSON field для parent, closingIssuesReferences, baseRefOid, ошибки jq на массив/объект и неизвестный флаг --stat. Текущий [gh pr view manual](https://cli.github.com/manual/gh_pr_view) уже перечисляет closingIssuesReferences/baseRefOid. Значит, это несовпадение с возможностями установленной версии, а не вечный запрет этих полей. decompose step 4 уже требует discovery actual field IDs/options; step 7 уже содержит таблицу native operations. Проблема не в отсутствии источника бизнес-политики.

| Альтернатива | Оценка |
|---|---|
| Вписать поля, ID, полный набор команд в SKILL.md | Быстро, но дублирует меняющуюся схему, увеличивает контекст и обслуживание. Отклонено. |
| Каждый раз заново исследовать CLI | Актуально, но фактически уже приводит к повторным ошибкам. Использовать только при неизвестном/изменившемся контракте. |
| Общий версионируемый операционный справочник, читаемый по требованию, плюс native discovery | Минимально, сохраняет свежесть и повторное использование. Выбрано. |
| Собственный wrapper/MCP или генератор схем | Потенциально надёжнее при больших объёмах, сейчас нет доказанной необходимости; дополнительный код/тесты/совместимость. Отложено. |

[OpenAI — Build skills](https://developers.openai.com/plugins/build/skills) и [Iterating Development Workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex) разделяют workflow и подгружаемые references, прямо рекомендуют не дублировать. Справочник должен обслуживать несколько Skills и не зависеть от одного runtime, поэтому предлагается **.ai/github-operations.md** рядом с канонической .ai/workflow.yaml, вместо ещё одного Skill или отдельного регламента бизнес-политики. Если на свежем main уже появится эквивалент, расширить его.

- .ai/workflow.yaml — требования к классификации, жизненному циклу, native relationships и read-back.
- SKILL.md — когда и какую процедуру применять; ссылки на нужный раздел справочника.
- .ai/github-operations.md — минимальные проверенные примеры запросов, известные ограничения, диагностика совместимости; версия gh и дата проверки примеров. Никаких зеркал всего API, статических IDs/options или копии политики.
- GitHub API/фактический Project — источник актуальных полей, вариантов, идентификаторов, отношений. Установленный gh --help и список JSON fields — источник доступных параметров CLI. Смена версии/ошибка совместимости — адресная перепроверка, не обязательный универсальный preflight. Если поддерживаемый API доступен, применить его; неизвестное поле не угадывать многократно.
- Для .fields/.items показать реальные формы, пагинацию и извлечение нужных полей; сначала один read-only запрос для соответствующего ресурса, затем использовать снимок до мутации/признака drift, после записи — независимый read-back. Для native parent использовать [REST sub-issues](https://docs.github.com/en/rest/issues/sub-issues); актуальные поля PR проверять локально; поддерживаемый REST/GraphQL fallback. При ошибке/неполном read-back не выдавать Ready.

Проектные поля могут измениться без редактирования Skill, пока не меняется сам порядок процесса. Если изменятся **бизнес-правила**, меняется workflow.yaml и при необходимости Skill — это осознанная смена контракта, не техническая синхронизация всех файлов. Источники: [gh field-list](https://cli.github.com/manual/gh_project_field-list), [item-list](https://cli.github.com/manual/gh_project_item-list), [issue view](https://cli.github.com/manual/gh_issue_view). Приёмка: read-only проверка примеров на установленном gh с записью версии; структура и ссылки, отсутствие статических IDs; regression известных ошибочных команд не повторяется в следующем релевантном рабочем запуске. Не создавать/изменять реальные Issue для искусственного теста.

## HE-010 — scope и права GitHub

Конкретный 403 user/issue-fields указал read:user, авторизация восстановлена. Варианты: обязательный auth preflight при каждом задании (лишние вызовы, конфликт с #121); расширять токен заранее всеми scopes (лишние права); адресная диагностика конкретного отказа (выбрано). В тот же справочник HE-009 добавить случай: проверить активную учётку, требуемый endpoint и минимальный scope, различить scope и фактические права, с согласия владельца обновить credential, повторно прочитать ресурс. Не делать auto-refresh, не менять токен без разрешения, не раскрывать секреты. Ветка решения уже MITIGATED; отдельной задачи настройки авторизации нет.

## HE-005 — ожидание GitHub Actions

Причина: модель повторяет чтение законченного run, хотя HEAD прежний, или ждёт CI при другом blocker (например BEHIND). Не весь polling лишний; новая запись/новый SHA требуют проверки. В execute-task / AGENTS.md уже требуются final HEAD, CI, owner acceptance; не менять эти требования. #93 касается локального FAST/FULL, не повторного опроса удалённого CI.

| Альтернатива | Оценка |
|---|---|
| Повторные gh calls/sleep в LLM-цикле | Уже наблюдались лишние действия. Отклонено. |
| Штатный gh run watch RUN_ID --exit-status с разумным интервалом; сохранить результат до изменения состояния | Выбрано для случаев, когда необходимо дождаться именно этого run. Это polling внутри CLI, не отсутствие polling. |
| Event stream / собственный webhook / daemon | События могут снизить опрос, но доступность текущего gh не доказана, требуется initial read и обработка пропущенных событий. Не вводить инфраструктуру. |
| Завершить handoff и ждать вне агента | Выбрано, если по правилам не требуется синхронное ожидание (owner decision, draft, длительный CI); не выдавать незавершённую проверку за PASS. |

[gh run watch](https://cli.github.com/manual/gh_run_watch) поддерживает run ID, интервал, exit status; есть ограничения auth. [REST workflow runs](https://docs.github.com/en/rest/actions/workflow-runs) позволяет сопоставить head_sha, run и attempt. Перед watch определить PR HEAD/нужный run/attempt, статус Draft/Ready и актуальные blocking checks; после completion прочитать результат и HEAD, при изменении HEAD/run/attempt или новом relevant событии повторить целевую проверку. Не читать успешный старый run только потому, что PR BEHIND. Не объединять ожидание CI и исправление mergeability. При таймауте/нет auth — сохранить факты и handoff, не зациклиться. В runtime без watch (connector) bounded read и handoff, а не обязательный CLI. Реализовать минимально в существующем execute-task/операционном справочнике, без изменения CI/gates. Приёмка на существующем завершённом run read-only: точный SHA, статус и exit semantics; сценарий изменённого HEAD разобрать по записи, не триггерить CI искусственно.

## HE-004 — граница сессии

В архиве независимая административная операция унаследовала ~237–241k контекста; рост и наследование подтверждены, экономия и вред качества не измерены. #87 решал ненужное чтение документов внутри задания, не наследование разных заданий. .ai/codex-task-tracing.md уже различает attempt/runId и предупреждает про плохую атрибуцию нескольких независимых Issues.

| Альтернатива | Оценка |
|---|---|
| Одна длинная сессия для всех задач | Сохраняет память, но переносит нерелевантную историю и ухудшает атрибуцию. |
| Новый session при каждом turn / произвольном лимите токенов | Теряет полезное состояние, требует лишнего bootstrap. Отклонено. |
| Отдельная сессия для независимого задания, resume для того же связного outcome | Выбрано. Использовать существующий GitHub handoff, без новой памяти/регистра. Bounded refinement batch — одно задание по согласованному scope, а не обязательная сессия на каждое child Issue. |
| Native compaction для длительной связной задачи | Допустимая штатная альтернатива по необходимости; без принудительного порога или кастомного summarizer. Не заменяет границу независимых задач. |

[Anthropic context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) — on-demand retrieval, compaction и сохранение компактного рабочего состояния; [OpenAI Codex prompting](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide) — штатный /compact. Предлагается уточнить **существующую ответственность Coordinator/launcher** в .ai/workflow.yaml (orchestration) и связанный маршрут в документах, не создавать gate. При смене независимого outcome закончить handoff, определить новый scope, стартовать отдельную сессию; при продолжении/ревью того же outcome сохранить подходящий контекст и идентичность attempt. Новая попытка — новый runId по уже принятой процедуре; session ID и run ID не одно и то же. При включённом tracing — подготовка до запуска, не подменять историю метками. Приёмка: сценарии независимой задачи, продолжения одной задачи, bounded batch, новой попытки; в следующей обычной работе сравнить context per generation, total uncached/cached input, время и принятое качество, не обещать экономию.

## HE-011 — маршрутизация до запуска

Архив показал значительную долю расчётной стоимости диагностических Sol-вызовов, а также настройку сервиса из среды без самого сервиса. Это стоимость, не автоматически устранимая потеря. Roadmap уже содержит подходящее разделение: управляющий чат с connector, исследовательский чат, CLI, CI, владелец. .ai/workflow.yaml уже разделяет role / skill / model / runtime / capability, R5 проверяет способность исполнителя, режим human-assisted. #88 уже упростил роли простых задач. Новой архитектуры не требуется.

Варианты: оставить всё на памяти владельца (подтверждённый риск); создать автоматический router/оркестратор (не соответствует human-assisted и #121, нет доказанной пользы); сделать существующее решение о маршруте конкретным в момент handoff (выбрано). Coordinator перед выдачей задачи задаёт outcome, источник истины, минимальный требуемый доступ, подходящий runtime, существующий критерий Reasoning/Effort и границу сессии. Не отдельная форма или обязательный технический preflight: часть уже имеющегося Issue/PR handoff и R5. Если нет нужного доступа, использовать подходящую среду или вернуть ограниченный handoff, не поручать широкий поиск CLI. Исправить устаревшее описание WSL2 в roadmap на runtime с нужным доступом (текущая гостевая среда для разработки, хостовые сервисы требуют соответствующего доступа); не публиковать подробности конфиденциальной инфраструктуры. [Anthropic Building effective agents](https://www.anthropic.com/research/building-effective-agents) описывает routing по категориям и выбор минимальной сложности. Решение — операционное улучшение уже принятой политики, не новая роль/автоматизация. Приёмка: три сценария (GitHub-only, код+локальные тесты, хостовая инфраструктура) дают различный подходящий маршрут и достаточный handoff. Фактическое соблюдение оценивается при обычной работе.

## HE-006 — Reasoning / Effort

Причина дорогих режимов не доказана на сопоставимых задачах. Существующее поле Reasoning классифицирует сложность решений, Effort — объём работы; их нельзя отождествлять с названием модели/параметром reasoning_effort. Варианты: глобально снизить xhigh (риск качества), фиксировать жёсткую таблицу model IDs (быстро устаревает), выбирать минимально достаточную модель/режим на задачу по текущей классификации и требованиям (выбрано). Детерминированная команда по возможности без LLM. [OpenAI model selection](https://developers.openai.com/api/docs/guides/model-selection) и [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist) рекомендуют сравнение representative tasks по качеству/latency/cost перед снижением reasoning. Никаких новых A/B запусков без отдельного решения владельца (#10/#94); использовать естественные сопоставимые задачи, не выдавать наблюдательное сравнение за causal. HE-006 остаётся OPEN для оценки сложных задач; нет отдельной реализации конфигурации. Критерий выбора исполнителя включить в HE-011 без статических model names.

## План реализации и проверка

Предлагаются три ограниченных outcome (не три исследования заново):
1. HE-009 + HE-010 — общий операционный справочник GitHub, ссылки из существующих Skills; P1 как относительный приоритет исследования, Project priority отдельно проверить.
2. HE-004 + HE-011 (+ HE-006 без изменений модели) — один согласованный launcher/handoff lifecycle в существующей policy и roadmap; связанные решения принимаются перед одним запуском, D2. P1 кандидат.
3. HE-005 — bounded CI wait/read-back без изменений CI; P2 кандидат, повторно использовать справочник если он уже принят.

Для всех — текущие R1–R7, native links/read-back, валидный execution contract, ветка от принятого main, независимый review, no changes to product. Ссылки на исследования — evidence, не dependency сами по себе. Не назначать исполнителя и не устанавливать Ready без необходимой классификации, реальных Project fields и проверки. Реализация завершена только после принятого PR. Эффект проверяем отдельно: success/accepted result, число известных ошибок, ненужные запросы, затраты и время по сопоставимым обычным задачам; точная стоимость подписки неизвестна, пропуски telemetry раскрываются. Нет доказанного процента экономии.

# Ретроспективный обзор исторических выполнений Harness

**Issue:** [#169](https://github.com/lehater/napms-2/issues/169), дочерняя задача [#150](https://github.com/lehater/napms-2/issues/150).
**База crosswalk:** `main@aaee5674c13f3722e494ae62b502f60c74a65695` (2026-11-21).
**Вывод:** в заранее ограниченной группе из десяти принятых выполнений найден один кандидат на необычно длинный хвост длительности observations (#155). Его существенность низкая, причина не установлена. Новых подтверждённых поведенческих дефектов или ошибок уровня ERROR/WARNING в наблюдаемом наборе нет. Измерения не представляют все выполнения NAPMS и не доказывают причинность.

## Объём и доказательства

Проверена только известная группа принятых outcomes: Issues #126, #151–156, #165, #166 и #168. Для каждой попытки использованы ранее известные `repository`, `issueId`, `runId` и ожидаемый `sourceSha` из существующих handoff. #165 и #168 включены как принятые comment-only outcomes; наличие PR не использовалось как общее условие eligibility. Каждый точный запрос вернул одну страницу без cursor; совпали repository, issueId, runId и sourceSha во всех десяти случаях. В выборке 1,568 уникальных observations; пропусков, повторов и неатрибутированных строк нет.

Чтение выполнялось существующим Langfuse Public API с HTTP Basic Auth и параметрами из глобального `~/.codex/langfuse.json`. Фактический capability GET к `/api/public/v2/observations?limit=1&fields=core` вернул HTTP 200, подтвердив доступ на чтение в этом runtime. Health и projects также вернули HTTP 200. Конфигурационные значения и endpoint host не сохранялись в отчёте. Запросов на запись не было.

Период ограниченного запроса: `[2026-11-18T00:00:00Z, 2026-11-22T00:00:00Z)`. Десять per-run GET фильтровались по точным repository/issueId/runId, запрашивали `limit=1000` и группы `core,basic,time,metadata,usage,metrics`. Счётчик этой попытки: **15/15 GET** — три preflight-запроса, два запроса по некорректной фильтрации и десять точных запросов. Первый вариант фильтра передал `metadata` как строку и получил HTTP 400; диагностический GET вернул фактическую ошибку API: для `metadata` требуется filter type `stringObject`. Параметр исправили, десять целевых запросов завершились HTTP 200. Ошибка была в параметре запроса, а не признаком недоступности сервиса. Лимит исчерпан; повторных запросов не выполнялось.

Сохранились длительности только для отдельных групп: три preflight GET заняли 0.04 секунды, десять точных per-run GET — 0.51 секунды. Длительности двух отклонённых запросов отдельно не сохранились, поэтому полное active time в минутах **unknown**; приведённые групповые времена не являются wall-clock временем всей работы.

Использовалась фиксированная целевая выборка, а не полный inventory. Содержательный разбор HE-005 и ранее выполненная инвентаризация корпуса не повторялись. Из запроса исключены `io`, prompts, model parameters и свободный trace context; raw observation/trace IDs, произвольная metadata и свободный текст не выводились и не сохранялись.

### Неизвестное и ограничения вывода

- **Token usage и cache:** API-группа `usage` запрашивалась, но локальная безопасная проекция искала несовпадающие имена полей и не сохранила агрегаты. Поэтому usage, cache и cost — **unknown**, не нулевые. Лимит GET исчерпан; повторно читать данные в рамках этой проверки нельзя.
- **Повторы действий:** группа `io` исключена; число повторных tool calls, retries и необходимость конкретных read-back неизвестны. Объёмы TOOL observations не доказывают растрату или дублирование.
- **Длительность выполнения:** распределения `duration` по observations нельзя трактовать как полное время задачи. Причина хвоста #155 не установлена.
- **Представительность:** это десять заранее известных принятых результатов, не случайная выборка всех запусков. Ни общий rate отклонений, ни финансовый эффект не вычисляются.

**Возможный следующий вопрос, без новой задачи или запроса сейчас:** повторяется ли хвост #155 у сравнимых будущих выполнений? Ответ считать подтверждённым только при наблюдении аналогичного elevated `duration p95` ещё как минимум в двух выполнениях того же типа и связанной измеримой задержке outcome; иначе оставить одиночным низкоприоритетным случаем. Для этого потребуется отдельное разрешённое окно чтения.

## Capability gap и последующее исправление

Предыдущие проверки capability искали Langfuse CLI/MCP или переменные `LANGFUSE_*` и по их отсутствию делали вывод, что query route недоступен. Они не проверяли уже используемый глобальный `~/.codex/langfuse.json`. Проверка в текущем runtime подтвердила HTTP 200 на чтение observations API; значит, прежнее утверждение об отсутствии доступа было неподтверждённым, а проблема состояла в discovery-процедуре и точности отчёта об ошибке.

Дочерняя задача [#171](https://github.com/lehater/napms-2/issues/171) оформляет минимальное документальное исправление существующих Harness-инструкций: разделяет отправку и чтение telemetry, описывает существующий источник подключения и обязательный авторизованный capability GET. Изменение не добавляет инструментов, конфигураций или инфраструктуры. Этот отчёт не меняет Harness.

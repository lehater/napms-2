## Текущая проверяемая граница

- Сохранённая группа остаётся фиксированной: принятые outcomes #126, #151–156, #165, #166 и #168. Их точные runId и GitHub acceptance содержатся в исходных Issue handoffs. #165 и #168 являются валидными comment-only outcomes; наличие PR не требуется универсально.
- Исторические сведения из #166/#168 могут использоваться для дедупликации и покрытия уже исследованных полей. Новые выводы требуют фактических точечных query по известным runId в назначенном runtime.
- Текущий handoff описывает runtime без подтверждённого Langfuse query capability. Наличие доступа в другом ранее использованном runtime не подтверждает доступ здесь. Поэтому admission не пройден и новый telemetry анализ не выполнялся.
- В этой попытке новые Langfuse GET: **0**; active telemetry minutes: **0**. Task-level длительность, usage/cache, ошибки/retries и последовательности для запрошенного обзора остаются **unknown**, а не равными нулю.

## Finding и ранжирование

На этом этапе **новых исторических отклонений не подтверждено**: нет нового per-run evidence, по которому можно было бы сравнить существенность и частоту. Ранжировать повторные status reads, стоимость или эффективность из #168 повторно нельзя. Предыдущие гипотезы сохраняются только как уже известный контекст для дедупликации, без нового ранга или вывода об эффекте.

## Обязательный admission gate и следующий шаг

До назначения исполнитель должен подтвердить в выбранном runtime owner-authorized read-only Langfuse Viewer/query доступ, совместимую версию API и безопасную локальную минимизацию. Проверка включает health/version и ограниченный telemetry GET по одному заранее известному runId. Обычный `scripts/check-task-admission` `ALLOW` не заменяет это подтверждение. Пока проверка не пройдена, Issue #169 остаётся в `Preparing`; запросы к другим host/secret, использование tracing/export credentials и завершение по пересказам запрещены.

После допуска выполнить ограниченный проход по известным runId: сначала структурные time/usage/metrics/tool signals и coverage; запросы расширять только если это может изменить ранжирование, в пределах 15 GET и 15 активных минут. Затем обновить доказательное ранжирование, Issue handoff и PR #170, связав результат с точным PR head и соответствующим Verify.

**Harness не менялся.** В текущей среде нет законченного telemetry результата, позволяющего принять PR #170 как итог #169.

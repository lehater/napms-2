# Ретроспективный обзор аномалий Harness

**Issue:** [#169](https://github.com/lehater/napms-2/issues/169), дочерняя задача [#150](https://github.com/lehater/napms-2/issues/150).
**Срез источника:** `main@aaee5674c13f3722e089e6b4bc279f39700a133be` (2026-11-21).
**Результат:** один сильный, но пока неподтверждённый кандидат на лишние CI-запросы; одна подтверждённая и уже исправленная рассинхронизация Project; ограничения полноты/сопоставимости, не позволяющие оценить общий эффект Harness. Новое изменение Harness по этим данным не обосновано.

## Метод и границы

Заранее заданная группа принятых результатов: #126, #151–156, #165, #166 и #168. Учитывались только уже записанные Issue/PR/Verify evidence и минимизированные сводки; новые задачи, полный повтор инвентаризации или повторное чтение traces не запускались. Для чтения из Langfuse в этой сессии прямого разрешённого маршрута не было: runtime — KVM guest без Langfuse query CLI или `LANGFUSE_*` query configuration. Trace/export config не использовался для чтения. Поэтому новые observations API GET — **0**; недостающие per-run поля остаются `unknown`.

В принятых отчётах имеются per-run структурные сводки для восьми выполнений: #126, #151–156 и #166. Они охватывают **1,430 observations**: #126 — 470, #151–156 — 822, #166 — 138. У #151–156 сохранена точная корреляция runId с merged PR и успешным Verify на соответствующем PR head; #126 и #166 также имеют точный Issue/PR/Verify crosswalk. По #165 и собственному выполнению #168 доступны принятые issue outcomes и metadata/handoff, но не сохранённая здесь per-run поведенческая проекция. Эти восемь случаев — целевая группа, а не репрезентативная случайная выборка NAPMS.

Методика следует принятым правилам #152–155: attempt = repository + issueId + runId; `sourceSha` — версия, не ID попытки; считать `eligible`, `selected`, `checked` и `unknown` отдельно; не выводить причинность, стоимость подписки или эффект из наличия записи, успешного PR либо закрытия Issue. Подробный исходный паспорт корпуса — [#166](sdlc-150-issue-166.md); ограниченный разбор #166 и контроль S08 — [итог #168](https://github.com/lehater/napms-2/issues/168#issuecomment-7068443662), его eligibility crosswalk — [комментарий #7068470134](https://github.com/lehater/napms-2/issues/168#issuecomment-7068470134).

## Рекомендуемые следующие исследования

1. **Реконструировать 18 status-read observations #166.** Вопрос: какие уникальные GitHub действия они представляли и что агент уже знал перед каждым действием? Данные: точная последовательность из существующего host read-only Langfuse API, Verify run/head/attempt и GitHub timeline для PR #167; только минимизированные категории/время/terminal/new-event сигналы. Подтверждение: хотя бы один уникальный запрос повторяет уже известный terminal result на неизменном head без нового события или обязательного независимого read-back; отдельно посчитать только такие подтверждённые вызовы и их измеримое время. Если условие не выполняется, закрыть candidate как штатные проверки.
2. **Проверить population rule на #165 и snapshot delta.** Вопрос: учитывает ли критерий завершённости принятый no-PR outcome, когда контракт предписывает comment/report, и можно ли объяснить +124 rows без повторения всего корпуса? Данные: контракт и owner acceptance #165, #168 crosswalk, issue/project states, сохранённые handoff/page ledger и только при доступе — точная строка по уже известному runId. Подтверждение: правило корректно принимает каждый завершённый outcome согласно его контракту; все строки одного зафиксированного окна дедуплицированы и распределены между exact repo / unknown / other без неразрешённого count drift.
3. **Оценить task-level usage/context/cache на заранее фиксированной группе.** Вопрос: можно ли связать input/output/cached usage и latency с результатом без смешения разных задач и неизвестных cost? Данные: exact-run `usage/time/metrics` из уже разрешённого API и существующий PR/Verify outcome для восьми ранее спроецированных attempts; никаких payload/model parameters. Подтверждение: coverage каждого поля и знаменатель опубликованы по попыткам; cache/context доступны отдельно либо помечены unknown; сравнение ресурсов делается только между сопоставимыми типами задач, без USD/подписочных claims.

**Рекомендация:** первой выполнять диагностику №1: у неё самое прямое наблюдаемое поведение и наибольшая потенциальная практическая польза, хотя текущие данные ещё не подтверждают растрату. На этом основании Harness не менялся.

# Issue #152 — доступ к Langfuse и корреляция с GitHub

**Состояние исследования:** документационные возможности проверены 2026-11-20; live read-back Langfuse и корреляция конкретной задачи не выполнены. Это ограничение доступной capability, а не свидетельство отсутствия данных. Исходный checkout: `2fdd3c9a7b32db891fdd3216ee1d55f85e8d06c4`.

## Вывод

Для первого пилота не добавлять инфраструктуру. Если владелец предоставляет уже существующий локальный read-only доступ к Langfuse, предпочесть Langfuse CLI с официальным Agent Skill для узкой выборки через Observations API v2 (self-hosted v4+). Для self-hosted v3 документация указывает legacy Observations API v1, но этот endpoint возвращает полные строки, включая `input`/`output`, и не даёт селектора `fields`; значит, фильтрацию чувствительного содержимого надо выполнять внутри уже разрешённой защищённой среды до любого экспорта или передачи. Если такой локальный отбор/минимизацию нельзя безопасно подтвердить, остановить проверку v1 и не экспортировать полные ответы. В v1 `sessionId` может отсутствовать в API-представлении; считать session неизвестной, пока она независимо не подтверждена. Если CLI/shell не подходит в будущем runtime, MCP — альтернатива только с read-only allowlist: сервер по умолчанию содержит write tools. Metrics API v2 нужен отдельно лишь для агрегатных вопросов, а не для связывания единичной попытки.

В текущем запуске безопасный конкретный маршрут к инстансу неизвестен: handoff подтвердил Git/GitHub, но не предоставил Langfuse endpoint, сведения о self-hosted версии, read-only ключ либо проверенную Langfuse CLI/MCP capability. Секреты, конфигурации, сетевые маршруты и другие локальные среды не исследовались. Это не блокирует документационную приёмку данного отчёта; это обязательная предпосылка будущего живого on-demand пилота. Пока фактическая версия, разрешённый локальный read-only маршрут, безопасная минимизация и привязка выбранной обычной задачи к GitHub outcome не подтверждены, live pilot blocked: никаких запросов, чтения I/O, изменений конфигурации или установки новых инструментов. Ограниченный handoff координатору/владельцу должен назвать недостающую capability, ответственного оператора и следующее действие; оператор подтверждает версию/тип инстанса и выполняет запрос только в уже авторизованной среде, передавая безопасную сводку полей и покрытия. Сырые traces не публиковать.

## Каноническая единица и чтение

Принятая цепочка остаётся: **repository + primary issueId + attempt runId → один или несколько Codex sessionId → traceId → observationId → outcome из GitHub**. `runId` — UUID одной попытки, повторные сессии той же попытки сохраняют его; новая попытка получает новый. Начальный `sourceSha` привязывает попытку только к исходной версии кода, не определяет уникальную попытку и сам по себе не устанавливает branch, PR или outcome. Уже принятые поля и правила зафиксированы в [workflow observability](../../.ai/workflow.yaml), [процедуре task tracing](../../.ai/codex-task-tracing.md), PR [#135](https://github.com/lehater/napms-2/pull/135) и [#137](https://github.com/lehater/napms-2/pull/137); второй execution ID не нужен.

Для v2 observations выбирать по метаданным `repository`, `issueId`, `runId` и ограниченному временному интервалу; `sourceSha` — дополнительная проверка исходного кода, не ключ попытки. Запрашивать только нужные группы полей (`core,basic,metadata`, при необходимости выборочные usage/model/time) и не запрашивать группу `io` без отдельного обоснования. Для v1 нельзя применять рекомендации о фильтре `fields`/выборочных группах: API возвращает полные observation rows с I/O. Если версия требует v1, извлечение и минимизация должны происходить внутри авторизованной защищённой среды до сохранения/экспорта; полные ответы, промпты или архивы не пересылать. Если безопасную локальную фильтрацию подтвердить нельзя, остановиться и запросить оператора с безопасным способом доступа. После безопасного отбора хранить только необходимые `id`, `traceId`, подтверждённый `sessionId` (если есть), время, тип/имя, parent, status, допустимые model/usage поля и минимальные metadata. Группировать строки по `traceId`, дерево — по `parentObservationId`; session — только по отдельно проверенному `sessionId`. Не трактовать отсутствие строки как доказательство отсутствия хода, пока не учтены задержка поступления и границы выборки. Повторное чтение для маленького ручного пилота безопаснее автоматического checkpoint; при автоматизации нужно сохранить курсор, повторно читать перекрывающееся окно и дедуплицировать по стабильному observation `id`, потому что возможны поздние обновления. Это кандидат на будущее, не основание сейчас строить collector.

Branch, PR/head SHA, CI и review outcome устанавливаются только явным Issue/PR handoff и GitHub read-back. `sourceSha` указывает исходную версию кода; он не доказывает уникальность run, branch, PR или результата. Например, #151–#153 показывают одинаковый `sourceSha` при разных `runId`/ветках. Если handoff и GitHub read-back не дают однозначной связи, соответствующую идентичность оставлять неизвестной. Значения, восстановленные по косвенным признакам, маркировать как реконструкцию. `sessionId` не равно попытке и не равно Issue: одна попытка может продолжаться в новой сессии; batch, охватывающий несколько Issue, нельзя надёжно делить по per-Issue затратам только по факту общей сессии. Незаполненный `issueId`/`runId` и неоднозначные записи оставлять неизвестной атрибуцией, не угадывать.

Проверять начало/конец можно только относительно полного обычного run: tracing работает Stop Hook после хода; первый экспорт зависит от включения до сессии, а последний ход завершается последующим вызовом hook. Реализация заявляет sidecar для дедупликации при resume, но это не доказывает отсутствие пропусков конкретного self-hosted набора. Для одного реального кейса сопоставить `repository + issueId + runId` из handoff с native observations; проверять `sourceSha` только как исходную версию, а branch/head/PR, CI и review — отдельным GitHub read-back. В v1 `sessionId` считать неизвестным, если оно не подтверждено независимо. В этой задаче такая live-проверка недоступна и не заявляется.

## Граница интерфейса предложенного пилота

Этот интерфейс следует интеграционному ревью [#150](https://github.com/lehater/napms-2/issues/150#issuecomment-7043459327) и не переносит на #152 ответственность других задач: #151 задаёт полномочия/инициацию, #153 владеет семантикой Finding, #154 — каноническими ссылками и dedup, #155 — оценкой эффекта. До любого будущего чтения координатор действует в рамках уже принятого handoff и ответственности #151; он инициирует bounded выборку при обычной передаче/разборе результата либо завершении/прерывании существующей попытки, сам читает только при наличии capability или поручает этот read-only шаг Refiner, которому она подтверждена. До чтения фиксируются критерий, временное окно/граница, размер выборки и правило отбора. Первый кандидат — одна уже завершённая обычная задача; дальнейшая ограниченная выборка может включать завершённые/прерванные попытки по заранее заданному критерию с сохранением причин исключений и пропусков.

Вход к Langfuse и единица попытки — **repository + primary issueId + runId**; task identity — **repository + issueId**. `sourceSha` — только начальная версия исходного кода, CI run IDs хранятся отдельно. Для выбранной попытки #152 выполняет доступ и read-back: проверяет безопасный минимум observations/coverage, сверяет attempt metadata и выдаёт #153 только минимизированную сводку и ссылку на источник. `evidence_ref` — ID/локатор исходной записи (например traceId/observationId), не Finding ID; сырые данные остаются в Langfuse. В сводке указываются `evidence_status=verified|partial|unverified` (неизвестная проверенность — `unverified`), `source_availability=available|unavailable|unknown` отдельно для каждого источника и coverage/late/missing сведения. `confidence` — отдельная качественная оценка конкретного утверждения, не RCA. Evidence↔Finding может быть many-to-many. Стабильный локальный Finding ID не является ID исходной записи; `finding_ref` — канонический URL комментария/записи GitHub плюс ключ записи, если их несколько. Эти ключи и каноническое место записи принадлежат #153/#154, не создаются #152.

Канонический Problem — существующий GitHub Issue соответствующего самостоятельного вопроса. Finding сохраняется в комментарии этого Problem Issue, если он уже найден; иначе — в существующем Issue/PR с контекстом исполнения. При появлении Problem сохраняют исходную ссылку и не копируют запись. Decision и оценка эффекта остаются в комментарии Problem Issue с отдельным стабильным ключом решения; связанный Action Issue/PR сохраняет обратную ссылку. #152 предоставляет безопасные evidence refs/coverage и не выбирает Problem, не создаёт Finding/Decision и не переносит сырые данные из источника.

Исход GitHub (Issue/PR handoff, branch/head, CI IDs, review/outcome) подтверждается отдельным GitHub read-back; `sourceSha` не заменяет эту связь. Координатор сохраняет в существующем handoff итог `normal | finding | unknown`, evidence refs, coverage/gaps и следующий шаг. `normal` применим только при достаточном покрытии заранее заданного критерия; отсутствие Finding при неполном покрытии означает `unknown`, а не норму, точность или эффект. При отсутствии permission, известной версии, безопасного фильтра или однозначной task↔attempt↔GitHub связи live pilot остаётся `blocked`; handoff ограничен тремя пунктами: недостающая capability, владелец/оператор, следующее разрешённое действие. Никаких конфигурационных изменений, I/O чтения/экспорта либо новых инструментов для обхода блока.

## Решение

Сохранить текущий optional runId tracing без изменений Harness. Документационная приёмка этого отчёта не зависит от live-доступа; live on-demand пилот blocked до выполнения предпосылок и bounded handoff выше. При разблокировке кандидат — одна завершённая обычная задача: `repository + issueId + runId` → минимизированные observations/evidence refs + coverage → результат `normal|finding|unknown` от анализа #153 → GitHub read-back branch/head/PR/CI/review outcome. `sourceSha` остаётся только исходной версией; ambiguous identity — unknown. Для v1 сначала подтвердить безопасную локальную фильтрацию полных rows, иначе остановиться без экспорта payload. Только доказанная регулярная трудоёмкость/неполнота может обосновать отдельный Issue по автоматизации. Не создавать сейчас Collector, Normalizer, MCP-конфигурацию, storage или новый идентификатор.

# Issue #152 — доступ к Langfuse и корреляция с GitHub

**Состояние исследования:** документационные возможности проверены 2026-11-20; live read-back Langfuse и корреляция конкретной задачи не выполнены. Это ограничение доступной capability, а не свидетельство отсутствия данных. Исходный checkout: `2fdd3c9a7b32db891fdd3216ee1d55f85e8d06c4`.

## Вывод

Для первого пилота не добавлять инфраструктуру. Если владелец предоставляет уже существующий локальный read-only доступ к Langfuse, использовать Langfuse CLI с официальным Agent Skill для узкой выборки через Observations API v2 (self-hosted v4+) либо документированный совместимый API v1 (self-hosted v3). CLI/Skill подходят этой shell-среде и позволяют отфильтровать данные до передачи в контекст. Если подходящий CLI не установлен или shell недопустим в будущем runtime, MCP — альтернатива, но только с read-only allowlist: сервер по умолчанию содержит write tools. Metrics API v2 нужен отдельно лишь для агрегатных вопросов, а не для связывания единичной попытки.

В текущем запуске безопасный конкретный маршрут к инстансу неизвестен: handoff подтвердил Git/GitHub, но не предоставил Langfuse endpoint, сведения о self-hosted версии, read-only ключ либо проверенную Langfuse CLI/MCP capability. Секреты, конфигурации, сетевые маршруты и другие локальные среды не исследовались. Следовательно, не подтверждены ни версия сервера, ни доступность конкретной задачи, ни полнота наблюдений. Минимальное продолжение — оператор с уже разрешённым доступом сообщает версию/тип инстанса и выполняет read-only запрос в нём, передавая только безопасную сводку полей и счётчиков; публикация traces не требуется.

## Каноническая единица и чтение

Принятая цепочка остаётся: **GitHub repository + primary issueId → attempt runId → один или несколько Codex sessionId → traceId → observationId → GitHub outcome**. `runId` — UUID одной попытки, повторные сессии той же попытки сохраняют его; новая попытка получает новый. Начальный `sourceSha` связывает попытку с кодом на старте. Эта схема уже зафиксирована в [workflow observability](../../.ai/workflow.yaml), [процедуре task tracing](../../.ai/codex-task-tracing.md), PR [#135](https://github.com/lehater/napms-2/pull/135) и [#137](https://github.com/lehater/napms-2/pull/137); второй execution ID не нужен.

При разрешённом чтении сначала выбирать observations по `metadata` (`repository`, `issueId`, `runId`, `sourceSha`) и ограниченному временному интервалу; сохранять только `id`, `traceId`, `sessionId`, время, тип/имя, parent, status, допустимые model/usage поля и нужные metadata. Запрашивать `input`/`output` только при отдельной необходимости и только в защищённой среде: Codex integration записывает prompt, системные инструкции, tool inputs/outputs и ответы целиком. Группировать строки по `traceId`, дерево — по `parentObservationId`; сессии — по `sessionId`. Не трактовать отсутствие строки как доказательство отсутствия хода, пока не учтены задержка поступления и границы выборки. Повторное чтение для маленького ручного пилота безопаснее автоматического checkpoint; при автоматизации нужно сохранить курсор, повторно читать перекрывающееся окно и дедуплицировать по стабильному observation `id`, потому что возможны поздние обновления. Это кандидат на будущее, не основание сейчас строить collector.

`sourceSha` позволяет найти ветку/PR и обычные GitHub metadata (branch, worktree, модель и прочее, если они действительно записаны). Состояния Issue, CI, review и результат берутся из GitHub, не выводятся из trace. Значения, восстановленные по косвенным признакам, маркируются как реконструкция. `sessionId` не равно попытке и не равно Issue: одна попытка может продолжаться в новой сессии; batch, охватывающий несколько Issue, нельзя надёжно делить по per-Issue затратам только по факту общей сессии. Незаполненный `issueId`/`runId` и неоднозначные записи оставлять неизвестной атрибуцией, не угадывать.

Проверять начало/конец можно только относительно полного обычного run: tracing работает Stop Hook после хода; первый экспорт зависит от включения до сессии, а последний ход завершается последующим вызовом hook. Реализация заявляет sidecar для дедупликации при resume, но это не доказывает отсутствие пропусков конкретного self-hosted набора. Для одного реального кейса сравнить handoff runId/sourceSha с native observations и известными session/trace IDs, затем независимо сверить PR, CI и review в GitHub. В этой задаче такая проверка недоступна и не заявляется.

## Варианты и ограничения

| Путь | Что позволяет | Доступность/версия | Пригодность и ограничения |
|---|---|---|---|
| Public API: Observations v2 | Строки observation, фильтры, курсорная пагинация, выбор полей; можно группировать по trace/session и связывать по metadata | Официально self-hosted v4+; v3 требует legacy/v1 API. Версия нашего инстанса неизвестна | Предпочтительный API-контракт для выборки; выбирать ограниченный диапазон и минимальные поля. Ответ — observation rows, не целый trace. Старые SDK/OTEL события могут отставать до 15 минут. |
| Metrics API v2 | Агрегаты cost/token/volume/latency/scores по dimensions/filters | Cloud и self-hosted v4+; self-hosted v3 — v1. Фактическая версия неизвестна | Для сводок, не первичной корреляции. Default row limit 100, настраиваемый максимум 1,000; high-cardinality группировки дороги. Не превращать Langfuse cost в стоимость подписки/списание бюджета; `0` или null не доказывают фактическое нулевое время/стоимость. |
| Python/JS SDK | Типизированная обёртка Public API, filters/pagination; observations/metrics в актуальных namespace | Официально есть SDK; локально пакет/совместимость не подтверждались | Работает поверх того же API, добавляет зависимость/код для разовой выборки. Не нужен без доказанной повторяемой задачи. |
| Langfuse CLI + Agent Skill | Skill даёт процедуру, CLI покрывает REST API и пригоден для shell, с предварительной фильтрацией | Документировано для совместимых coding agents; локальную установку/доступ не проверяли | Рекомендуемый минимальный интерфейс первого пилота при наличии уже разрешённой shell-capability. CLI не обходит версию/права инстанса. Skill/CLI поддерживают и операции записи: применять только явно read-only запросы. |
| Langfuse MCP | API-инструменты из клиента без shell | Доступен с API key и настроенным MCP; этого подключения в текущей сессии не предоставлено | Не рекомендован для данного CLI-runtime; read/write tools доступны по умолчанию, нужна allowlist read-only tools. Не публиковать локальный инстанс, не добавлять ключи в конфигурацию ради подключения. |
| Экспорт из UI | CSV/JSON экспорт из отфильтрованной таблицы, доступен ручной пакетный экспорт | Функция описана официально; права и UI инстанса не проверялись | Подходит разовой ручной выборке оператором, но экспорт включает все столбцы независимо от настроенной видимости колонок — риск лишних данных. Если выбран — защищённая среда, ограниченный фильтр, не пересылать архив в PR/чат. |
| Blob Storage export | Плановые файлы JSON/JSONL/CSV/Parquet; manifests, оконные выгрузки, повторная обработка | Self-hosted доступен; облачные тарифные ограничения зависят от плана. В данном инстансе неизвестно и не проверялось | Избыточен для пилота: требует конфигурации, storage и credentials; создаёт внешнюю копию данных. Не включать. Документация требует дедупликации по ID из-за inclusive границ и повторных доставок. |

Официальная документация сообщает, что Public API ключи project-scoped, но явные capabilities/least privilege для конкретного ключа должны быть подтверждены владельцем инстанса; не считать любой project key read-only. Для CLI/API запрашивать только разрешённые read endpoints и селективные поля. Для MCP исключить все write-инструменты. Не создавать внешний ingress, туннель или экспорт в чужое хранилище.

## Решение

Сохранить текущий optional runId tracing без изменений Harness. Для минимального пилота дождаться оператора с уже разрешённым локальным read-only доступом и сверить одну обычную задачу: metadata → observation/trace/session → sourceSha → PR/CI/review outcome. В текущей доступной сессии результат ограничен документационным исследованием; никаких недоказанных локальных возможностей не заявлено. Только если ручная выборка окажется регулярно трудоёмкой или неполной, подготовить отдельный Issue с конкретной доказанной потребностью в автоматизации. Не создавать сейчас Collector, Normalizer, MCP-конфигурацию, storage или новый идентификатор.

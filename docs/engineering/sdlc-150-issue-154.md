# Учёт Findings и Problems в цикле SDLC #150

Дата исследования: 2026-11-20. Область: минимальный маршрут от наблюдения до принятого решения и реализации, без внедрения новых компонентов.

## Краткий вывод

Рекомендую пока не вводить отдельную БД, registry, синхронизацию или новый статус GitHub Project. Использовать GitHub как каноническую запись для Findings, заслуживающих сохранения, Problems, принятых Decisions и Action Items; Langfuse оставить источником сырых traces и детализации отдельных событий. Issue #138 полезен как исследовательский указатель и источник исторических примеров, но остаётся Draft PR и не должен считаться нормативным реестром.

Операционный минимум для предложенного, отдельно согласуемого read-only пилота: Coordinator инициирует ограниченный разбор в обычном handoff/разборе результата либо при завершении/прерывании существующей попытки; сам делает read-only разбор в пределах ответственности или поручает Refiner с нужным capability. Normal или unknown остаются в существующем handoff и не требуют Finding или Problem. Finding записывается один раз в каноническом комментарии Problem Issue, если Problem уже найден, иначе в существующем Issue/PR исполнения; при последующем выделении Problem запись не копируется, сохраняется ссылка. Decision и оценка эффекта фиксируются раздельно в комментарии Problem Issue. Уровень confidence описывает конкретное утверждение, не RCA. Реализацию вести существующими Issues с native hierarchy/blocked_by и обычным workflow. Не превращать каждое событие или tool error в Issue.

Это рекомендация исследования, не утверждение о принятии владельцем. Автоматические записи, новые labels/views и отдельное хранилище требуют отдельного решения и демонстрации конкретного пробела.

## Источники истины и границы

| Объект | Канонический источник | Минимальное содержание и граница |
|---|---|---|
| Raw Trace / raw event | Langfuse | Исходные события и payload остаются там. В публичный Issue/PR не копировать trace contents, секреты и персональные данные; сохранять минимальную ссылку/идентификатор и нужный временной диапазон только при допустимом доступе. |
| Finding | Комментарий существующего Problem Issue; до выделения Problem — комментарий существующего Issue/PR исполнения | Один canonical Finding comment с `finding_id` (локальный ключ записи) и `finding_ref` (URL этого комментария; если комментарий содержит несколько записей — URL + ключ). Evidence остаётся ссылкой на источник. Не копировать Finding при появлении Problem. `evidence_status` (`verified | partial | unverified`) оценивает поддержку утверждения; `source_availability` (`available | unavailable | unknown`) отдельно описывает доступность источника. `confidence` — качественная оценка утверждения, не RCA. |
| Problem | Существующий canonical GitHub Issue для самостоятельного вопроса | Fingerprint Problem, ссылки на Findings, дедуп-счётчики evidence/attempt/task, severity отдельно от Priority, first/last seen и состояние RCA. Не заводить новый Issue, если подходящий уже существует; GitHub lifecycle не копировать. |
| Decision + effect | Один canonical комментарий в Problem Issue на конкретную пару Problem+Decision, с единым стабильным `decision_key` | В комментарии раздельные части Decision и effect evaluation, а также состояния delivery/RCA/effect: delivery сверяется с Action Issue/PR, RCA относится к Problem, effect отражает оценку покрытия/результата. Evidence остаётся в источниках. |
| Action Item | GitHub Issue с обычными Type/Area/Workstream/Priority/Status и native relations | Самостоятельный проверяемый outcome; создавать/переиспользовать через intake/refinement/decompose. Linked Action Issue/PR содержит обратную ссылку на canonical URL комментария Problem + `decision_key`. При необходимости это native child/sub-issue или отдельный Issue с реальной зависимостью. |

Типизированные связи представлять прямыми GitHub URL и номерами вместе с явной меткой отношения в тексте записи: `Finding —observed-in→ trace`, `Finding —supports→ Problem`, `Problem —decided-by→ Decision`, `Decision —implemented-by→ Issue/PR`, `Problem —effect-evidenced-by→ CI/PR/follow-up`. GitHub native parent/child и blocked_by применяются только к настоящей структуре результата/зависимостям; текстовая ссылка не выдаётся за native relation. Решение и ссылка остаются читаемыми без внешней базы. В текущем workflow уже закреплено, что Issue, native Project fields/relationships и linked PR — источники состояния, а handoff evidence сохраняется в соответствующем Issue/PR.

## Контракт Finding → Problem → Decision → Issue

1. **Finding (#153):** различать `evidence_ref` (ID/locator записи исходного evidence), `finding_id` (стабильный локальный ключ аналитической записи) и `finding_ref` (канонический URL комментария/записи GitHub + `finding_id`, когда записей несколько). Сохранять claim/утверждение, scope, criterion, expected/actual, attempt/role (допустимы `unknown`), `evidence_status` (`verified | partial | unverified`; неизвестная проверенность считается `unverified`), `source_availability` отдельно на каждый источник (`available | unavailable | unknown`), qualitative `confidence` для утверждения (не RCA), версию метода и раздельные fact/hypothesis. Доступность источника не означает, что он поддерживает утверждение. Evidence deduplicate по `evidence_ref`; Finding deduplicate по совпадающим claim, scope и criterion. Повторное чтение без нового утверждения идемпотентно. То же evidence может поддерживать отдельный Finding только при обоснованно отличающемся claim, scope или criterion; source event при этом остаётся одним. Связь evidence↔Finding — many-to-many.
2. **Ключи и Problem:** не смешивать `evidence_ref`, `finding_id`, `finding_ref`, attempt, task и Problem fingerprint. Attempt = `(repository, primary issueId, runId)`; task = `(repository, issueId)`; `sourceSha` только фиксирует исходную версию, CI IDs — отдельные идентификаторы. Существующий GitHub Issue становится canonical Problem, если он соответствует самостоятельному вопросу. Fingerprint служит поиску кандидатов, не ID записи и не автоматическим основанием объединения. Счётчики отдельно различают уникальные evidence records/events, attempts и tasks; повторы одной записи не увеличивают их. Неизвестные идентификаторы/независимость отмечать unknown, не восстанавливать их из числа событий.
3. **Canonical storage и Decision/effect (IR-04):** канонический Finding — комментарий Problem Issue, если он уже найден; иначе комментарий существующего execution Issue/PR. При выделении Problem сохранить исходную ссылку, не переносить/дублировать Finding. Сырые данные остаются в исходном источнике. Для каждой пары Problem+Decision поддерживать один authoritative комментарий Problem Issue с единым стабильным `decision_key` и раздельными частями Decision, effect evaluation и состояниями delivery/RCA/effect. Action Issue/PR ссылается обратно на canonical URL этого комментария + `decision_key`. После merge/closure искать и обновлять ту же запись по ключу и ссылкам; не создавать второй комментарий как новую authoritative запись. Delivery state сверяется с Action Issue/PR, RCA state относится к Problem, effect state описывает проверку покрытия/результата; не выводить одно из другого.
4. **Обычный handoff и запись:** если для заранее выбранного критерия достаточно evidence и отклонение не найдено, записать `normal` в существующий handoff; если покрытие неполное/неизвестное — `unknown`. Ни normal, ни unknown не требуют Finding/Problem; отсутствие Finding без достаточного покрытия не доказывает норму, точность или эффект. Создание/обновление GitHub записи выполняет только Project Operator в пределах разрешённых полномочий и с read-back.

Различать ключи и не подменять одну идентичность другой:

- **Evidence record identity (`evidence_ref`):** ID/locator записи исходного наблюдения, например trace/event/observation ID; он не является ID Finding. Один source event дедуплицируется по этому ключу.
- **Finding identity (`finding_id` / `finding_ref`):** стабильный локальный ключ аналитической записи и её канонический GitHub URL (URL комментария/записи + ключ, если записей несколько). Finding deduplicate по совпадающим claim, scope и criterion. Повторное чтение без нового утверждения идемпотентно; то же evidence может поддерживать отдельную Finding только при обоснованно отличающемся claim/scope/criterion. Evidence↔Finding many-to-many.
- **Execution attempt identity:** `(repository, primary issueId, runId)` по существующей task tracing схеме. Разные `runId` для одной Issue — разные попытки, но не независимые задачи. Если `runId` неизвестен, нельзя надёжно считать уникальные attempts по session ID или `sourceSha`.
- **Independent task identity:** `(repository, issueId)`. Несколько attempts и observations одной Issue считаются одной task. `sourceSha` фиксирует начальную версию кода попытки, CI IDs остаются отдельными evidence identifiers; сами по себе они не задают независимость задачи.
- **Problem identity:** существующий GitHub Issue и его fingerprint для поиска; fingerprint не заменяет Issue ID и не разрешает автоматический merge.

Подсчёт вести раздельно: source event учитывается один раз по `evidence_ref`; Finding учитывается один раз по `finding_id` после дедупа совпадающих claim/scope/criterion. Повторный импорт/проверка без нового утверждения не увеличивает ни event, ни Finding. Новое независимое evidence добавляется к подходящей Finding/Problem; то же evidence может быть связано с отдельной Finding только для обоснованно иного claim/scope/criterion, не создавая второй source event. Например, пять observations одного attempt дают пять evidence records/events, один attempt и одну task; три `runId` одной Issue дают три attempts, но одну task. Если identifiers отсутствуют, помечать count/независимость как `unknown` или нижнюю границу, не выводить их из числа событий. При известном repository+issueId task можно посчитать при отсутствующем runId; без primary issueId независимую task определить нельзя.

Для ручного поиска дублей fingerprint: `source/workstream + normalized symptom + affected surface + trigger/condition + relevant version`. Убирать динамические значения и персональные данные; хранить исходное описание рядом. Не включать root cause в ключ: причина часто неизвестна или меняется в ходе расследования. Совпадение fingerprint — повод сравнить evidence, не автоматическое доказательство дубля.

## Дедупликация, обновление и эскалация

| Ситуация | Предлагаемое действие |
|---|---|
| Единичное, низкой серьёзности наблюдение без повторяемого action | Оставить evidence в Issue/PR, CI или Langfuse annotation, если там уже ведётся ручной анализ. Отдельный Problem Issue не обязателен. При потере cross-task discoverability можно записать короткую ссылку в существующую подходящую GitHub запись. |
| Повторный симптом, но одна задача/run повторяет вызов | Дедуплицировать source events по `evidence_ref`, Findings — по совпадающим claim/scope/criterion; обновить найденные записи и счётчики. Одно событие может поддержать ещё один Finding только при обоснованно отличающемся claim/scope/criterion и остаётся одним event. Это не независимые затронутые задачи. |
| Повтор в независимой задаче/run | Найти canonical Problem по fingerprint и evidence; дополнить его существующими Findings, если claim/scope/criterion совпадают, либо связать обоснованно отдельный Finding с тем же evidence. Добавить новые уникальные evidence refs и счётчики, first/last seen; не создавать новый Issue или дублировать событие/Finding из-за повторного чтения. |
| Серьёзное/потенциально срочное событие | Немедленно уведомить владельца/ответственного через существующий GitHub Issue/PR или принятый incident-маршрут; зафиксировать severity отдельно от P0–P2 priority и продолжить проверку доказательств. Порог/матрица severity не заданы данным исследованием. |
| Уже есть открытый Issue того же outcome | Добавить evidence и уточнить scope/acceptance без дублирования. Новую задачу создавать только для distinct результата; native relationship — если зависимость реальна. |
| Похожий закрытый Issue | Найти и сохранить ссылку на историческую запись, проверить scope, решение и эффект; историю не переписывать и Issue автоматически не открывать. Если есть новый distinct outcome или evidence ставит acceptance под сомнение, Coordinator/Refiner проходит обычный workflow и при необходимости предлагает отдельный follow-up, связанный с закрытым Issue. |
| Симптом повторился после принятой меры | Пометить как candidate regression в существующей Problem/effect записи, связать с PR/CI/новыми traces, проверить версию и соблюдение меры. Не закрывать исходную проблему только фактом merge. |
| Дедуп ошибочен | Человек вручную split/merge: сохранить историю ссылок, объяснить критерий, назначить canonical Issue и обновить перекрёстные ссылки. Не терять исходные Finding/evidence при объединении. |

Ни число независимых задач, ни first/last seen не считать полными, если источники не дают надёжной корреляции. «3 независимые задачи» остаётся гипотезой для будущей калибровки. До накопления репрезентативных примеров применять экспертную эскалацию по серьёзности и контексту, а не фиксированный автоматический порог.

## Проверка кандидатов и примеры

**GitHub Issues/Projects.** Подходят для canonical Problem, принятого Decision и реализации: дают стабильные URL/номера, lifecycle, Project Type/Area/Workstream/Priority/Status, native Sub-issues и blockers, review и PR evidence. Проектная классификация уже задаёт Area (`area:sdlc`), Workstream (SDLC), Priority и Status (включая Preparing/Ready/Running/Review/Done). Не добавлять `Backlog`/`Triage` или новую Issue taxonomy для Finding. View — только сохранённое представление существующих полей после подтверждения потребности; оно не создаёт новый источник истины.

**Quality Escape Handling.** Уже имеет маршрут Register → Reproduce → Localize → Prevent → Improve Harness? → Accept и классификацию причин. Он требует воспроизводимого негативного случая и позитивного исправленного случая для подтверждённого escape. Поэтому этот протокол подходит для Finding, который уже представляет дефект, прошедший проверки; он не требует превращать обычный шум инструмента в escape или отдельное поручение.

**Langfuse scores/comments.** Актуальная документация описывает Scores для trace, observation, session и dataset run; доступны числовые, категориальные, boolean и text значения. Ручные annotations, comments и annotation queues подходят для локальной оценки trace и заметок; scores доступны в аналитике/API. Это подтверждает возможность фиксировать оценку события, но не подтверждает, что Langfuse в данной установке хранит cross-run canonical Problem, GitHub lifecycle/решения или гарантированную дедупликацию независимых задач. Использовать как evidence/annotation слой, а не backlog. Источники: [Scores overview](https://langfuse.com/docs/evaluation/scores/overview), [Scores data model](https://langfuse.com/docs/evaluation/scores/data-model), [Comments](https://langfuse.com/docs/observability/features/comments), [Annotation Queues](https://langfuse.com/docs/evaluation/evaluation-methods/annotation-queues).

**Отдельная БД.** SQLite/PostgreSQL могут индексировать Findings и агрегировать события, но добавят второй lifecycle, права, резервирование/retention, идентичность canonical записей, reconcile и поддержку split/merge. В доступном evidence нет подтверждения, что GitHub + ссылки на Langfuse не справляются с конкретным требованием. Поэтому отклонить на этом этапе; пересмотреть только при доказанном запросе (например, невозможность ручного поиска/подсчёта на реальном объёме) и отдельном owner decision.

**Пример #30 (Quality Escape).** В принятом RCA Issue #30 подтверждены `spec-gap` и `coverage-gap`; конкретная агентная причина осталась неизвестной без соответствующих traces. Отдельный Draft PR #32 был отрицательным probe и закрыт без merge: намеренная UI-мутация добавила AccessRequest в DOM каталога PolicyRule, fixture не менялась; быстрый validator прошёл, browser semantic check завершился ожидаемым FAIL (`expected 1, received 3`). Это подтверждено в [RCA PR #31](https://github.com/lehater/napms-2/pull/31), в частности [Verify #42519051142](https://github.com/lehater/napms-2/actions/runs/42519051142), и в [PR #32](https://github.com/lehater/napms-2/pull/32), чьё описание фиксирует неизменённую fixture. ## Проверяемый intake и обновление

1. Coordinator инициирует разбор в обычном handoff/разборе результата или при завершении/прерывании существующей попытки. До чтения фиксируются критерий, окно/граница, размер выборки и правило выбора. Первый предлагаемый кандидат — одна завершённая обычная задача; последующая ограниченная выборка может включать завершённые и прерванные попытки по заранее заданному критерию, с фиксацией причин исключений и пропусков. Это интерфейс для будущего согласованного пилота, не live pilot или обязательное расписание.
2. Coordinator выполняет read-only разбор в пределах своей ответственности либо поручает его Refiner с нужным capability. Project Operator выполняет только разрешённые GitHub записи и независимо читает результат обратно. В существующем handoff сохраняются GitHub outcome, evidence/capability gaps, результат критерия (`normal | finding | unknown`) и следующий шаг. `normal` допустим только при достаточном покрытии именно выбранного критерия; без покрытия результат `unknown`. Не выводить норму, точность или эффект из отсутствия Finding.
3. Для `finding` сохранить evidence reference, claim, scope, criterion, expected/actual, impact и факт отдельно от гипотезы; не включать raw trace payload. Дедуп source event по `evidence_ref`, Finding — по совпадающим claim/scope/criterion; повторное чтение без нового утверждения идемпотентно. Одно evidence может поддержать отдельный Finding только если отличается claim, scope или criterion с обоснованием.
4. До записи искать canonical evidence refs, Finding refs/keys и Problem fingerprints в open и closed Issues/PR, включая поиск после merge/закрытия. История закрытых записей сохраняется; HE draft — только индекс. Добавить новое evidence к подходящей записи, создать одну Finding запись в существующем Issue/PR, если соответствующего claim/scope/criterion ещё нет, связать её с Problem или предложить отдельный Problem/action через workflow. При появлении Problem сохранить ссылку на исходный Finding без копирования. Для closed Problem не выполнять автоматический reopen; follow-up — только через workflow.
5. Project Operator применяет только разрешённые GitHub записи с независимым read-back. Повторная операция сначала находит тот же canonical Issue/comment и native links, затем добавляет только отсутствующие связи/evidence. После merge/closure Decision/effect обновлять в том же canonical Problem comment по `decision_key`; не создавать второй authoritative комментарий.
6. В этом одном комментарии пары Problem+Decision отдельно поддерживать Decision rationale/outcome, delivery state (по linked Action Issue/PR), RCA state (по Problem) и effect evaluation/state (criterion, coverage, result или unknown, evidence refs). Для эффекта указать runs/tasks и период; неизвестную корреляцию или недостаточный baseline раскрывать. Статус Action Issue сам по себе не доказывает эффект. Реализация остаётся отдельным согласованным Action Item; этот report не назначает исполнителя и не меняет статусы.

## Ограничения и решение, требуемое от владельца

- Не исследовались закрытые payload, сырые traces или доступ к конкретной Langfuse-инсталляции. Возможности Langfuse выше установлены по опубликованной документации; наличие/настройка функций, scopes, retention и корреляция текущего self-hosted экземпляра не проверены.
- Реестр #138 прочитан через открытый Draft diff. Его полнота относительно всех research-веток не подтверждена; использовать его только как индекс/ссылки на историю, не как canonical Finding/Problem источник или нормативный источник.
- Доступные примеры не дают валидной выборки для порогов дедупликации/escalation, baseline частоты независимых задач, severity matrix или причинного измерения эффекта. Порог 3 не калиброван.
- Текущая Project taxonomy проверена по принятой workflow policy и живым Issue/Project handoff данным; предложения source/type/area labels и отдельный View не имеют доказанной необходимости. Не предлагается их добавлять.
- Рекомендация: принять описанный GitHub+Langfuse link-based подход без БД и синхронизации; canonical Finding — комментарий Problem Issue либо исходного execution Issue/PR, а Decision/effect для пары Problem+Decision — одна keyed запись в комментарии Problem Issue, обновляемая после merge/closure. HE вести только как индекс. Следующий шаг — отдельное решение о read-only выборке по этому интерфейсу; этот отчёт не проводит пилот и не добавляет сериализацию, gate, расписание или инфраструктуру.

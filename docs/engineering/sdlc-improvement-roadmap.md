# NAPMS 2.0 — SDLC Quality & Harness Improvement Roadmap

**Статус:** согласованный план следующих исследований и итераций, не реализован.
**Дата:** 2026-11-07.
**Источник истины:** GitHub `main` этого репозитория; актуальное состояние задач — GitHub Issues по ссылкам ниже.

## Назначение и критерий успеха

На следующем этапе **приоритет — инженерный процесс производства ПО (SDLC/Harness)**, а не расширение функций NAPMS. NAPMS используется как проверяемый испытательный продукт.

Цель: построить обратную связь **разработка → проверки → измерение → выявление причины → минимальная гипотеза улучшения → воспроизводимое сравнение → review**.

Разделять:
1. **Качество результата**: корректность кода, тесты, типизация, безопасность, соответствие OpenSpec.
2. **Качество процесса**: успешность PR/CI, длительность, повторные итерации, причины ошибок, эффективность работы Codex/Harness.
3. **Улучшение Harness**: изменение инструкций/Skills/workflow **только после** подтверждения полезности на повторяемом задании.

**Проверяемый результат программы:** хотя бы одно обоснованное изменение процесса прошло сравнение «до/после» и оформлено Draft PR; в случае отсутствия эффекта — зафиксирован отрицательный результат без изменения Harness.

## Методика минимального цикла

1. **Baseline:** сначала снять измерения из существующих тестов/CI и явно зафиксировать неполноту данных.
2. **Гипотеза:** указать конкретную проблему, предлагаемое изменение, ожидаемую метрику и риск регрессии.
3. **Контролируемый эксперимент:** одинаковые входные задания и проверки, зафиксированные условия и доступные трассы; не приписывать Codex несуществующие observability-данные.
4. **Сравнение:** детерминированные тесты и метрики первичны; LLM-as-a-Judge (например, DeepEval) — дополнительный источник сигнала, требующий оценки вариативности.
5. **Решение:** только отдельный Draft PR, CI, review и squash merge по подтверждённой пользе. Неудачные эксперименты также документировать.

## Архитектурные границы

- Используем существующий стек: **OpenSpec → Codex CLI → GitHub PR → CI → review → merge**.
- Проверки кода (Ruff/Pyright/pytest/coverage), оценки агента (DeepEval-кандидат) и измерение SDLC решают **разные задачи**; не смешивать их в единую «оценку качества».
- Не внедрять отдельный демон улучшения Harness, новую платформу телеметрии, orchestration framework, dashboard или обязательный LLM-judge gate до измеренной пользы.
- Не вводить произвольный порог coverage и не объявлять метрики агентных затрат, которые не собираются.
- Строго отделять экспериментальные ветки/сценарии от защищённого `main`; для изменений Harness необходим человек на review.
- Не копировать старый код или Harness из [NAPMS 1.0](https://github.com/lehater/napms).
- Проект публичный: исключить токены, секреты, пользовательские трассы с чувствительными данными.

## Инструкция для нового чата / агента

1. Открыть **актуальный GitHub `main`** и прочитать `AGENTS.md`, этот roadmap и связанные Issues. Не использовать историю чатов как источник истины.
2. Проверить открытые PR/Issues, выбрать первый ещё не реализованный шаг из таблицы. Не дублировать выполненное.
3. Изучить актуальные `openspec/specs/` и CI; для новой продуктовой функциональности использовать штатный OpenSpec workflow. Для исследования качества — оформить минимальный воспроизводимый эксперимент.
4. Работать в отдельной ветке, подготовить Draft PR с результатами проверок, ограничениями и сравнением с baseline. Не выполнять merge без согласования.

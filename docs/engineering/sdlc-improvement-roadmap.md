**Статус:** SDLC-01/02/03 завершены; SDLC-04 — исторические исследования сохранены, A/B-подготовка PR #17 закрыта без запуска. Текущий приоритет — реализация принятых продуктовых срезов и адресные Quality Escapes.

## Назначение и критерий успеха

Инженерный процесс NAPMS улучшается по подтверждённым проблемам реальных вертикальных срезов. Принятые продуктовые задачи остаются приоритетом; отдельные исследования или эксперименты не задерживают их без доказанной необходимости.

Цель: использовать цикл **разработка → проверка → обнаруженный дефект → анализ причины → минимальное исправление процесса или теста → review**.

Разделять:
1. **Качество результата**: корректность кода, тесты, типизация, безопасность, соответствие OpenSpec.
2. **Качество процесса**: успешность PR/CI, длительность, повторные итерации, причины ошибок, эффективность работы Codex/Harness.
3. **Улучшение Harness**: изменение инструкций/Skills/workflow **только при подтверждённой процессной причине**; по умолчанию опираться на доступные исследования и регрессионные проверки, а не новые A/B-прогоны.

**Проверяемый результат:** у предлагаемого изменения есть конкретный исходный дефект, подтверждение причины, минимальный объём, проверяемые критерии и независимое review. Отдельные A/B эксперименты с моделями не требуются; решение «не менять Harness» допустимо.

## Маршрутизация задач и стоимость исполнения

**Координатор выбирает исполнителя для каждой задачи до её делегирования.** Выбор определяется нужными инструментами, сложностью и расходом ограниченных ресурсов; не запускать Codex CLI по умолчанию.

| Исполнитель | Ответственность | Когда использовать |
|---|---|---|
| **Управляющий чат с GitHub-подключением** | Планирование, ревью diff и CI, критические решения, GitHub Issues, документация, PR и согласованный merge | Есть доступ к репозиторию и задачу можно завершить через GitHub без локального shell |
| **Отдельный исследовательский чат** | Глубокое исследование инструментов/методик, сравнения, проектирование метрик/evals, независимое второе мнение | Не требуется локальное выполнение; задача ограничена конкретным вопросом и результатом |
| **Codex CLI в WSL2** | Локальное программирование, запуск команд, воспроизводимых экспериментов, интеграционных тестов, работа с локальными артефактами | Необходимы локальные файлы/среда или фактическое исполнение; запуск строго ограниченным заданием |
| **GitHub Actions** | Детерминированные автоматические проверки, повторяемые измерения и результаты CI | После PR/push; не заменять на самоотчёт агента |
| **Владелец** | Продуктовые и архитектурные развилки, доступ к физической машине/Swagger, финальное решение при рисках | Только когда без человека нельзя подтвердить результат |

**Правила:** (1) не поручать Codex поиск по GitHub, общие рассуждения, написание промптов и ревью, которые выполняются через чат; (2) не переносить в Codex широкий неопределённый research — сначала сузить задачу в исследовательском чате; (3) не раздавать одно изменение нескольким исполнителям одновременно без непересекающихся веток/границ; (4) передавать через ссылку на Issue/PR, ожидаемый артефакт и критерий завершения; (5) результаты возвращать в GitHub, а не сохранять только в истории чата; (6) не утверждать измеренную стоимость агента, если её telemetry отсутствует.

Новый чат **не может автоматически продолжить работу соседнего чата или локального Codex**: координатор выдаёт копируемое задание, пользователь запускает отдельный чат/агента; затем координатор проверяет артефакт в GitHub.

Для [Issue #8](https://github.com/lehater/napms-2/issues/8) **сначала** использовать исследовательский/управляющий чат с GitHub API для выявления реально доступных метрик и небольшого baseline. **Только при необходимости** воспроизводимого CLI-скрипта или локального запуска делегировать Codex ограниченную реализацию.

## Эксплуатационный контроль семантических ошибок

Для случаев, когда успешный CI пропустил предметную ошибку, применять [Quality Escape Handling](quality-escape-protocol.md): зарегистрировать дефект, сопоставить Domain → OpenSpec → UI → Tests, получить детерминированный отрицательный regression case и усилить существующий PR gate. Первый принятый на рассмотрение пример — [UX-0 semantic quality escape](quality-escapes/ux-0-semantic-ui-2026-11-08.md) ([Issue #30](https://github.com/lehater/napms-2/issues/30), [Draft PR #31](https://github.com/lehater/napms-2/pull/31)). Проверка `semantic-contract` запускается в `Verify` автоматически на каждый PR; RCA и изменения Harness остаются под review. Новые типы ошибок требуют расширения контракта с подтверждённой семантикой.

## Методика минимального цикла

1. **Evidence:** зафиксировать реальную ошибку и её источник: PR/commit, поведение, результаты CI, отзыв пользователя.
2. **Root cause:** отделить подтверждённую причину от предположений, проверить действующие OpenSpec, тесты, AGENTS.md и Skills.
3. **Existing practice:** использовать готовые инженерные рекомендации и существующие проверки; не запускать собственные A/B моделей по умолчанию.
4. **Minimal prevention:** добавить конкретный регрессионный тест или уточнить существующие инструкции только при доказанном пробеле; не дублировать механизмы.
5. **Acceptance:** отдельный ограниченный PR, CI на финальном HEAD, независимое review и решение владельца. Допустим вывод «изменения не требуются».

## Архитектурные границы

- Используем существующий стек: **OpenSpec → Codex CLI → GitHub PR → CI → review → merge**.
- Проверки кода (Ruff/Pyright/pytest/coverage), оценки агента (DeepEval-кандидат) и измерение SDLC решают **разные задачи**; не смешивать их в единую «оценку качества».
- Не внедрять отдельный демон улучшения Harness, новую платформу телеметрии, orchestration framework, dashboard, обязательный LLM-judge gate или A/B-прогоны моделей без отдельного обоснованного решения владельца.
- Не вводить произвольный порог coverage и не объявлять метрики агентных затрат, которые не собираются.
- Строго отделять экспериментальные ветки/сценарии от защищённого `main`; для изменений Harness необходим человек на review.
- Не копировать старый код или Harness из [NAPMS 1.0](https://github.com/lehater/napms).
- Проект публичный: исключить токены, секреты, пользовательские трассы с чувствительными данными.

## Инструкция для нового чата / агента

1. Открыть **актуальный GitHub `main`** и прочитать `AGENTS.md`, этот roadmap и связанные Issues. Не использовать историю чатов как источник истины.
2. Проверить открытые PR/Issues и явное поручение владельца; не выбирать автоматически старую исследовательскую задачу по исторической очереди.
3. Изучить актуальные `openspec/specs/` и CI; для новой продуктовой функциональности использовать штатный OpenSpec workflow. Для проблем качества — доказательный RCA по истории ошибок и доступным отраслевым практикам.
4. До делегирования выбрать маршрут из раздела «Маршрутизация задач и стоимость исполнения»; не передавать всё Codex CLI.
5. Работать в отдельной ветке, подготовить Draft PR с проверенным HEAD, CI, замечаниями и ограничениями. Merge — после ревью, зелёного CI и требуемой приёмки.

# Методика анализа отклонений исполнения и Findings

**Дата исследования:** 2026-11-20

**Issue:** [#153](https://github.com/lehater/napms-2/issues/153), самостоятельный исследовательский результат в рамках [#150](https://github.com/lehater/napms-2/issues/150)

**Статус:** рекомендация для решения владельца; таксономия, evaluator и gate не вводятся.

## Краткий вывод

Рекомендуется начинать с ручного evidence-first разбора конкретного выполнения и детерминированных фактов, уже доступных в GitHub, CI и согласованных handoff. Сохранять проверяемое наблюдение как Finding с точной ссылкой на источник, а интерпретацию причины — отдельно как гипотезу. Временный набор группировок ниже использовать только как аналитические метки, допускающие несколько значений и `unknown`; не закреплять его как нормативную классификацию до проверки на размеченных случаях.

Нативные Langfuse scores, annotation queues и evaluators — доступные варианты реализации будущего пилота, но необходимость их применения здесь не доказана. Публичная документация описывает возможности продукта, однако доступ к проектному экземпляру и его версия не подтверждены этим исследованием. Локальный `.codex/langfuse.json` не читался; значения конфигурации и credentials не проверялись. Внешние traces не запрашивались и не передавались.

**Численная оценка false positives / false negatives невозможна:** в доступных privacy-safe источниках не найден набор отдельных сигналов с независимыми экспертными метками «отклонение / штатный шаг» и результатом проверяемого метода. В частности, HE-001–011 — отобранные case notes и выводы расследований, а не исчерпывающий корпус запусков. Поэтому частоты ложных срабатываний или пропусков не оцениваются и не выводятся из количества кейсов.

Это наилучший найденный privacy-safe корпус фактов для качественного разбора; это **не** независимо размеченная выборка уровня сигнала. Handoff, PR и CI дают проверяемые статусы, ссылки, SHA и результаты задач. Они не содержат полного потока событий исполнения, а публикация сырых traces/payload не требуется для данного результата. Наличие trace correlation само по себе не делает запись экспертом размеченной.

### Полные примеры по контракту Finding

Эти две записи применяют поля контракта к разным классам входа. Первая — наблюдённое рассогласование lifecycle. Вторая явно помечена как контрольный сценарий ожидаемой проверки, в котором нарушения не наблюдалось; успешный контроль полезен, чтобы не смешивать штатное действие с отклонением.

## Предлагаемый минимальный контракт Finding

Finding — проверяемая запись о наблюдении; его наличие не равнозначно дефекту или установленной причине. Для ручного разбора достаточно следующих полей:

| Поле | Минимальное содержание |
|---|---|
| `finding_id` | Стабильный ID записи или ссылка на Issue/PR; без идентификатора, раскрывающего секретные данные. |
| `source` | Ссылка и конкретный source ID: Issue/PR comment, commit SHA, workflow run + attempt/job, либо разрешённый observation/event ID. Указать, если источник агрегирован или неполон. |
| `run_or_task`, `role` | Issue и attempt/run ID, если доступны; затронутая ответственность (например Coordinator, Worker, Reviewer) либо `unknown`. Не отождествлять роль с моделью или инструментом. |
| `observation` | Краткое конкретное событие/состояние, без вывода о мотивах; ссылка позволяет его проверить. |
| `criterion`, `expected`, `actual` | Проверяемое правило и сравнение. Для намеренно неуспешного probe/TDD: ожидаемое поведение шага и результат должны быть указаны явно. Если oracle или ожидание не определены — `unknown`, а не нарушение по умолчанию. |
| `classification` | Отдельные временные метки: симптом (ноль или несколько предложенных групп), тип доказательства и статус подтверждения. `cause`, ответственность и severity не кодировать в symptom. |
| `impact` | Наблюдаемое влияние и область, либо `unknown`; не присваивать приоритет из одного симптома. |
| `evidence_status` / `confidence` | Например: `verified` (прямой артефакт и критерий), `partial` (неполный источник/часть критерия), `unknown`. Confidence относится к уверенности в наблюдении/сопоставлении, не к вероятности причины. Качественная метка предпочтительнее псевдоточного числа без калибровки. |
| `fact` / `hypothesis` | Явно разделённые утверждения и основания. У гипотезы — подтверждающие/опровергающие данные и что проверить дальше. Не выдавать корреляцию за root cause. |
| `method_version` | Имя и версия применённого ручного протокола, правила или evaluator; `manual` также имеет версию чек-листа. Для автоматического результата — конфигурация evaluator и источник версии. |
| `privacy_note` | Ссылка на safe artifact или причина, по которой идентификатор/содержимое опущены; raw trace, credentials и приватные payload в запись не копировать. |

Статус доказательства отделять от статуса выполнения задачи и от статуса изменения Harness. Полезный маршрут вывода: **штатный шаг / сигнал без нарушения → проверенное наблюдение → evidence-backed problem → гипотеза причины → решение**. Это последовательность аналитических различий, а не новый workflow gate. Неуспешная команда сама по себе — факт о команде; для классификации как проблемы требуется показать, что шаг не должен был завершиться так, или что последующие ожидаемые проверки/восстановление не произошли.

## Временные группы симптомов и границы

Следующие метки — средство поиска похожих наблюдений, не принятая таксономия. Разрешены несколько меток и `unknown`; сначала записывается symptom, затем — при наличии доказательств — отдельные поля причины и владельца действия.

| Кандидатная группа | Наблюдаемый вопрос и граница |
|---|---|
| Context management | Передан ли нужный контекст для текущего outcome; потерян ли необходимый факт или перенесён ли нерелевантный контекст? Сам размер окна не доказывает вреда или расточительности. |
| Git management | Совпадает ли branch/base/HEAD/working tree с контрактом и PR? Технический конфликт — симптом; намеренное обновление ветки не является дефектом. |
| Task admission | Выполнены ли существующие R1–R7, scope и blockers до начала назначения/исполнения? Отдельно от ошибки последующего выполнения. |
| Contract / instruction compliance | Есть ли конкретное требование и проверяемое действие/результат, которые ему противоречат? Недостаток доказательств не равен нарушению. |
| Tool usage | Поддерживала ли операция заявленный CLI/API контракт, и подтверждён ли результат? Ошибка инструмента — не автоматически ошибка агента; отделять capability/permission и ошибочное предположение. |
| Retry loops | Повторялось ли действие при неизменном состоянии без новой информации/условия? Повтор после нового SHA, ошибки или recovery может быть штатным. |
| Token / time efficiency | Только доступные токены/длительность/число вызовов с источником и границами измерения. Нулевые интервалы, стоимость Langfuse и полный расход подписки не подменять оценкой. Efficiency не является качеством результата. |
| Testing | Проверка и exit code в контексте ожидаемого этапа. Красный тест как TDD/probe — ожидаемое свидетельство; проверять, был ли затем предусмотренный фикс и зелёный regression. |
| Scope creep | Изменения вне ограниченного результата или без соответствующего основания. Смежный документ/проверка могут быть необходимы контракту; сравнивать с заявленным scope. |
| Human intervention | Фиксировать конкретную просьбу/блокировку/ручное изменение и необходимость полномочий. Корректная остановка и обязательное owner decision не являются ошибкой агента. |
| False completion | Заявлен ли завершённый результат без необходимых артефактов, read-back, CI или owner acceptance. Ready, CI green, merged и accepted — разные состояния. |
| Environment | Нужны ли доступность runtime, зависимости, auth, sandbox или сервис; отделять ограничение среды от решения/действия исполнителя. |

**Ортогональные измерения:** symptom group отвечает «что наблюдали»; cause — «какой механизм это вызвал»; responsibility — «кто может принять/выполнить действие по действующему контракту»; impact/severity — «какой вред и масштаб подтверждены»; priority — «что делать раньше с учётом решений владельца». Их нельзя выводить друг из друга. Например, недоступное GitHub поле может иметь симптом `tool usage`, причину `permission/environment`, а действие — Coordinator; обязательный preflight из этого не следует.

## Минимальный пилот и условия для метрик

На текущих материалах допустим только **качественный пилот методики**: перепроверить уже опубликованные кейсы #150 и #144–#146 по контракту Finding, указав факты, гипотезы, штатный/ожидаемый шаг и отсутствующие поля. Не считать это независимой калибровкой: записи создавались в ходе тех же расследований и не являются слепой разметкой.

Если владелец отдельно решит измерить качество метода, минимальная безопасная процедура:

1. До просмотра результатов анализатора определить критерий и bounded набор уже существующих privacy-safe примеров: подтверждённые проблемы, штатные красные probe/TDD/retry, неоднозначные/неполные сигналы. Не создавать синтетические прогоны.
2. Два эксперта независимо и вслепую к output метода размечают каждую единицу как `problem`, `normal/expected`, `ambiguous/unknown`, с источником и критерием. Разногласия сохраняются и разрешаются отдельной adjudication; не превращать согласованную метку в доказанный факт без артефакта.
3. Сопоставить output метода с adjudicated labels. Для однозначных размеченных единиц привести абсолютные TP/FP/FN/TN и знаменатели; ambiguous/unknown показать отдельно. Не вычислять долю от неполного знаменателя и не объединять разные классы симптомов в одну метрику без задачи для этого.
4. Если оценивается judge, отдельно зафиксировать prompt/rubric version, модель/version, score/threshold, попытки и неизвестные затраты; сравнить с ручным базовым разбором. Рассматривать результат как advisory. При отсутствии разрешённого приватного доступа или достаточного объёма остановиться и сообщить gap.

Нет обоснованного порога приёмки judge или размера выборки для автоматизации; эта работа и #94 не разрешают вводить их по умолчанию. Не оценивать статистический риск из текущих единичных примеров. Экономические данные, цены или расход подписки не утверждать, если источник не подтверждает фактическое списание.

## Ограничения и рекомендация владельцу

- Имеющиеся GitHub records позволяют делать проверяемый разбор известных кейсов, но не восстановить все execution events или пропуски детектора.
- Текущий Langfuse access/capabilities не установлены; конфигурация не инспектировалась, обращения к trace API не выполнялись. Публичная документация не заменяет проверку конкретной версии/прав и не даёт права переносить raw data.
- Нет независимых экспертных labels для privacy-safe выборки задач уровня execution finding. Поэтому неизвестны FP/FN, межэкспертное согласие, стабильность любой proposed grouping и дополнительные затраты на ручную работу.
- HE ledger — открытая исследовательская запись из PR #138; использовать как индекс/контекст, не как утверждённый стандарт. #144–#149 — принятые конкретные изменения; операционный эффект в handoff ещё ожидает наблюдения на нормальной дальнейшей работе.

**Рекомендация:** принять Finding как минимальную структуру исследовательских записей; применять вручную к доступным фактам, разрешать `unknown`, разделять symptom / cause / responsibility / impact и не превращать категории в обязательную таксономию или score gate. Сохранить детерминированную проверку для явных полей и проверку источников человеком. Пока не добавлять analyzer, обязательный LLM judge, новую телеметрию, пороги или Langfuse queues/evaluators в Harness. Если нужна калибровка, отдельным решением определить безопасный закрытый набор, двух независимых разметчиков и допустимый способ хранения labels; только затем посчитать явные FP/FN. Если такого набора нет, честный результат — gap, зафиксированный здесь, без выдуманного процента.

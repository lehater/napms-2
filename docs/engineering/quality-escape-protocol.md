# SDLC — Quality Escape Handling (минимальный контур)

**Назначение:** превратить обнаруженный после прохождения CI дефект в проверяемое исправление продукта и, при подтверждённой необходимости, улучшение правил работы агента. Применять вместе с [SDLC roadmap](sdlc-improvement-roadmap.md) и [Issue #10](https://github.com/lehater/napms-2/issues/10). Это повторяемая процедура, а не отдельный сервис.

## Триггеры
- **Автоматический:** каждый PR проверяется применимыми blocking jobs в `.github/workflows/verify.yml`, включая `semantic-contract`; красный gate требует исправления до merge. Результат CI фиксируется для финального HEAD. GitHub ruleset `main` должен отдельно требовать прохождения проверок; наличие job в workflow само по себе не блокирует merge.
- **Escape:** пользовательская/ревью-ошибка, обнаруженная после успешного CI, регистрируется как Quality Escape; она показывает *пробел охвата* и требует нового проверяемого критерия. Manual report — временный вход до появления соответствующего автоматического детектора.
- **Escalation в Harness Improvement:** повторяемость одной категории, подтверждённое нарушение инструкций или доказанная неэффективность существующих проверок. Не каждое исправление продукта ведёт к изменению AGENTS.md/Skills.

## Контракт разбора
| Этап | Вход | Ответственность | Выход |
| --- | --- | --- | --- |
| Register | Сценарий, наблюдение, PR/commit | Владелец или CI | Issue с влиянием и ссылками |
| Reproduce | Нормативный договор и реальные/фиктивные данные | Исполнитель расследования | Минимальный воспроизводимый случай |
| Localize | Domain → Spec → UI/Code → Test | Независимый review | Первый переход потери семантики, отделённые гипотезы |
| Prevent | Подтверждённый инвариант | Исполнитель качества | Красный на нарушении, зелёный на исправлении blocking check |
| Improve Harness? | Доказанная системная причина и уже доступные проверки/исследования | Владелец / review | Минимальное обоснованное изменение инструкций либо решение «не менять»; A/B не требуется |
| Accept | CI, evidence, impact, review | Владелец | Merge через PR или отказ с аргументацией |

## Классификация причины
- `source-ambiguity`: исходные документы противоречат друг другу или не имеют статуса принятого решения;
- `spec-gap`: OpenSpec не формализует обязательное поведение;
- `implementation-drift`: реализация расходится с однозначной принятой спецификацией;
- `coverage-gap`: CI/test не проверяет значимое свойство;
- `harness-instruction`: доказуемая ошибка/пропуск AGENTS.md, Skills или handoff.

Одновременно возможны несколько причин. Не выводить конкретные мотивы Codex или расход токенов без доступных трасс. Для предотвращения повторения сначала использовать детерминированные регрессионные проверки и опубликованные инженерные практики. Собственные A/B-прогоны моделей не являются обязательной частью RCA и выполняются только по отдельному решению владельца.

## Критерий системного закрытия
**Патч без детектора недостаточен.** Для каждой подтверждённой категории Quality Escape нужен воспроизводимый `negative case → fail`, `corrected case → pass`, регистрация соответствующей проверки в PR CI и ссылка на исходный Issue. Важные немашиночитаемые различия отмечать как требующие независимого review; не обещать полной автоматической семантической корректности.

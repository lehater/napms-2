## 3. Гипотеза и единственная переменная

**Элемент Harness:** только `AGENTS.md`. **Не** менять Skills, `openspec/config.yaml`, workflow `Verify`, обязательные gates, тесты или продукт.

**Единственное кандидатное дополнение** к действующим instructions (один пункт; текст предназначен для проверки, **не применяется в SDLC-04A**):

> Before handing off OpenSpec artifacts for review, run `openspec validate --all --strict` in the project root; fix validation findings without dropping requirements or scenarios. If the validator is unavailable, report that validation was not performed and do not claim the change is validated.

Это **process preflight**, не правило «текст каждого Requirement <500» и не попытка обойти валидатор. Правило касается готовности к review, а не автоматического merge.

**Нулевая гипотеза H0:** этот пункт не увеличивает долю пригодных для review OpenSpec артефактов на одном фиксированном задании и commit; одинаковые deterministic checks дают сопоставимые результаты.  
**Альтернатива H1:** пункт повышает долю артефактов, которые проходят `openspec validate --all --strict` **до handoff**, при сохранении нормативных требований/сценариев и разрешённой области изменений.

**Основная метрика:** независимый exit code `openspec validate --all --strict` на итоговом дереве каждого прогона: PASS=1, FAIL=0. **Guardrails:** сохранение контрактной семантики и всех исходных сценариев/обязательств по заранее определённому checklist; отсутствие изменений вне OpenSpec planning artifacts; отсутствие фиктивного подтверждения запуска validator. Время/стоимость/число внутренних попыток не использовать для принятия решения, если отсутствуют надёжные машинные данные.

**Регрессии:** вырезание или ослабление требования ради зелёного validator; вывод «готово» без проверки; зависание/преждевременный BLOCKED при доступном CLI; добавление не относящихся к задаче инструментов, изменение CI/продукта; увеличение процедурной нагрузки без эффекта. Вариант нужно отвергнуть при ухудшении guardrails или отсутствии измеримого выигрыша.

### 4.2. Последовательность

1. Создать 3 **независимые пары** A/B (всего 6 Codex-прогонов), все от идентичного seed. Не брать historische PR attempts как A-триалы. Записать ID, seed SHA, SHA исходных файлов и hash candidate-пункта, digest task, окружение, группу и порядок.
2. Для каждой отдельной рабочей копии запустить агента с зафиксированными параметрами и одинаковым пределом wall-clock/time budget, получить окончательное дерево и полный **доступный** результат run. Отсутствующие agent metrics не восстанавливать из догадок.
3. **После завершения агента** внешний evaluator в той же закреплённой среде, отдельно от агента, выполняет `openspec validate --all --strict` и `git diff --check`; сохраняет exit codes и очищенные логи. Проверяет `git diff` и список затронутых файлов. Candidate-инструкция `AGENTS.md` — разрешённая экспериментальная переменная, а не продуктовый diff.
4. Сверить сохранение требований и сценариев с **заранее замороженным checklist**: один согласованный snapshot для решений/строк, одни `evaluationAt` и временные границы grants/Rule, актуальные Endpoint realizations, provenance, отсутствие historical as-of, поведение уже начатого экспорта при revocation, сохранение исходных сценариев. Удаление исходной гарантии не считается успехом даже если валидатор зеленеет. Для неоднозначной переформулировки — независимый **слепой** review по этому checklist; автоматическая проверка синтаксиса не объявляется семантическим oracle.
5. Для каждой группы считать `strict PASS / 3` и количество guardrail regressions. Сохранять все отрицательные/прерванные результаты; не повторять отдельный неудачный trial «до успеха». Не менять prompt, модель, критерии или порог после просмотра результатов.

**Основной oracle:** официальный OpenSpec CLI `openspec validate --all --strict`, pin 1.16.0; детерминированная проверка на итоговом файле (не GEval). `git diff --check` и contract-preservation checklist — обязательные защитные проверки. DeepEval и новые LLM judges **не требуются**.

### 4.3. Правило решения и остановки

**До начала запусков зафиксировать** максимум 3 пары, бюджет разрешённых агентных запусков и политику timeout; не придумывать цену/токены заранее. Остановить серию при смене модели/CLI, нарушении изоляции, выходе агента за разрешённый scope, невозможности запустить validator, риске секретов или исчерпании согласованного бюджета.

- **Предварительная поддержка H1 (pilot, не доказательство универсальной эффективности):** candidate проходит strict **3/3**, baseline — не более **1/3**, все candidate trials соблюдают contract/scope guardrails. Это основание показать owner Draft PR с локальной инструкцией и сырыми результатами, **не** автоматическое согласие на merge.
- **H1 отвергнута для этого задания:** baseline и candidate обе **3/3** (пользы не выявлено), candidate не превосходит baseline, либо candidate ухудшает сохранность контрактов/область изменений. Сохранить отрицательный отчёт, не предлагать включить пункт.
- **Неоднозначный результат:** разница лишь **1 из 3**, часть испытаний прервана, было 2/3 candidate без нарушений, либо неясны семантические последствия. Записать **INCONCLUSIVE** без post-hoc коррекции порога и без внедрения; решение о новом отдельно согласованном эксперименте принимает owner.
- **Отдельно:** если baseline уже устраняет дефект во всех 3 прогонах, это **floor-effect** для данного task; он не доказывает бесполезность preflight в других задачах. Любой результат здесь относится **только** к историческому seed и данному prompt.

Три пары — ограниченный инженерный smoke для выбора следующего действия; по ним нельзя оценивать надёжность в популяции задач, денежную экономию, token efficiency или число внутренних retry. Ретроспективные 2 CI failures PR #4 — **мотивирующее наблюдение**, не группа контроля. Нельзя причинно сравнивать разные PR, Quality Gates и GEval scores.

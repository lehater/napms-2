# Harness efficiency — реестр наблюдений и улучшений

Актуализировано: 2026-11-20. Область: агентный SDLC NAPMS 2.0, Codex CLI и его окружение.
Связь с существующим процессом: [SDLC improvement roadmap](sdlc-improvement-roadmap.md), [Issue #10](https://github.com/lehater/napms-2/issues/10).

## Назначение

Сохранить результаты исследований так, чтобы при повторном проявлении проблемы не проводить RCA с нуля. Цель — уменьшение времени и расхода ограниченных ресурсов при сохранении качества результата, а не сокращение контекста или рост доли кэша сами по себе.

Это исследовательский журнал, а не обязательная очередь исполнения и не нормативная конфигурация Harness. Принятые изменения процесса проходят обычное review; задачи на реализацию при необходимости ведутся в GitHub Issues. Сырые трейсы, payload, ключи и конфиденциальные сведения об окружении в публичный репозиторий не помещаются.

Статусы: **OPEN** — наблюдение/гипотеза требует проверки; **MITIGATED** — мера принята, эффект ещё не измерен; **WAIT_EXTERNAL** — ожидается внешнее исправление; **DEFERRED** — исследование отложено до появления оправданной возможности; **CLOSED** — вопрос исследован, решение и ограничения зафиксированы. Приоритет отражает очередность исследования, а не доказанный размер ущерба.

Перед новым RCA найти записи по симптомам и корневой причине. Если причина та же — дополнить запись доказательствами, версиями и статусом, не создавать дубль. Возобновлять отложенное исследование только при выполнении указанного условия.

## Исходная точка

- Исторический трейс задачи [PR #117](https://github.com/lehater/napms-2/pull/117): 210 событий (105 LLM, 104 TOOL, 1 AGENT), длительность около 32 мин 50 с; модель `gpt-6-luna`, reasoning `xhigh`.
- Суммарный вход около 10,59 млн токенов, доля кэша 98,33%; контекст одного вызова вырос примерно с 17,5 до 164,8 тыс. токенов. Расчётная стоимость Langfuse около $0,155; это не подтверждённое списание лимита подписки.
- E2E-сверка ZIP и Observations API v2: 210/210 ID, метрики 105/105, временные метки совпадают. Содержимое после учёта экранирования совпадает. Исторический трейс — не baseline нового гостевого окружения.
- Codex CLI 0.171.0 и Langfuse Tracing Plugin 0.4.3 — версии контрольного исследования контекста.

## Доказательства и границы выводов

### HE-001 — песочница

В историческом трейсе четыре попытки Python-проверок и диагностика заняли около 6 мин 50 с; соответствующий этап содержал 27 LLM-вызовов с расчётной стоимостью около $0,035. Не всё это время или стоимость доказанно потеряны. Вне песочницы 62 целевых теста прошли за 2,56 с. Отдельный эксперимент подтвердил запрет создания TCP-сокета в песочнице и успешное создание после разрешения; обычная Ubuntu и локальный Langfuse работали.

Владелец сообщил о переходе на гостевую ОС с полным доступом. Не добавлять специальное правило эскалации в проектный workflow без нового доказанного сбоя. Проверить следующий реальный запуск: повторные зависания по прежней причине отсутствуют, качество/проверки сохранены; безопасность хоста оценивается отдельно.

### HE-002 — дублирование базовых инструкций

Контрольный эксперимент с `CODEX_ROLLOUT_TRACE_ROOT`: одна копия базовых инструкций в захваченном исходящем клиентском запросе, одна в session metadata, одна в developer-сообщении rollout и две идентичные копии в реконструкции Langfuse (по 17 793 символа). Плагин объединяет эти два источника без дедупликации. Метрики токенов совпали с нативной телеметрией. Проверены версии плагина 0.4.2/0.4.3; механизм связан с [PR #91](https://github.com/langfuse/codex-observability-plugin/pull/91). Внешний баг [#20582](https://github.com/langfuse/langfuse/issues/20582) зарегистрирован и открыт на момент контрольного исследования.

Гипотеза избыточности фактического клиентского запроса не подтвердилась. Полный серверный контекст при `previous_response_id` не наблюдался. Не оценивать экономию токенов по удвоенному тексту Langfuse, не патчить плагин локально. Проверка после исправления: одна копия в реконструкции при неизменных корректных счётчиках.

### HE-003 — каталог возможностей

В локальном конфиге контрольного эксперимента явно включён только tracing-плагин, MCP-серверы не настроены. Наличие кешированных plugin-пакетов не доказывает активацию. Внешний контекст сессии содержал каталог Skills, рекомендации доступных плагинов и deferred tool namespaces; рекомендации не равны включённым плагинам. Один исходящий запрос содержал 3 namespace и 11 непосредственно объявленных инструментов.

Два контрольных запуска с одинаковым эффективным составом дали по 15 937 входных и 8 выходных токенов (кэш 0). Это проверка воспроизводимости, не содержательный A/B. Нельзя оценить экономию от отключения неиспользуемых возможностей. Не менять рабочую конфигурацию в отсутствие подтверждённой пользы.

### HE-004 — история и кэш

98,33% кэширования — доля повторно обработанного входа, не доказательство полезности каждого фрагмента или экономии от сокращения истории. Изучить рост контекста на актуальной задаче; при необходимости использовать Native Rollout Trace и сравнить сопоставимые запуски с проверенным качеством. Не выводить избыточность из одного размера или реконструированного system prompt.

### HE-005 / HE-006 — polling и reasoning

В исходном трейсе отмечено 16 обращений к данным PR #117 и 21 вызов `write_stdin`. Это наблюдения; ещё не установлено, сколько вызовов действительно можно исключить. 105 обращений в режиме `xhigh` также не означают, что режим избыточен. Сначала актуальные измерения по настоящим задачам, затем минимальные эксперименты только для существенных резервов.

### HE-007 / HE-008 — качество источников данных

У 97/105 генераций нулевой интервал; у 81 входа есть маркер пропущенной ранней истории. Эти ограничения присутствуют в Langfuse API, а не появились при скачивании ZIP. Внешний JSON экспорта валиден, но 45 вложенных GENERATION.input и 4 GENERATION.output не разбирались строго из-за управляющих символов. API возвращал экранированные значения; E2E не обнаружил потери содержания. Точный этап появления дефекта представления ZIP не установлен. Одноразовые локальные диагностические скрипты и отчёты удалены после фиксации результатов; постоянный валидатор не требуется.

## Измерения в гостевой ОС

### Сессия подготовки семейства #139–#143 (2026-11-20)

Источник: массовый экспорт Langfuse (17 сессий, 36 уникальных trace ID, 1100 уникальных событий); целевая сессия выделена по session ID из запроса на экспорт. Результат относится к работе Coordinator / Project Operator, не к реализации продуктового кода. [Отчёт в Issue #139](https://github.com/lehater/napms-2/issues/139#issuecomment-7037350167).

- 2 Codex Turn, 44 GENERATION, 42 TOOL; 498,347 с суммарной длительности двух Turn (около 8 мин 18 с); около 8 мин 47 с от начала первого до окончания последнего события. Модель `gpt-6-luna`, reasoning `medium`, CLI 0.171.0.
- Вход 3 060 521 токен (2 965 376 кэшированных, 95 145 некэшированных; 96,89% кэша); выход 12 081 (включая reasoning). Контекст 19 375 → 94 565 токенов. Расчётная стоимость Langfuse $0,04521; не подтверждённое списание подписки. 34/44 LLM-интервалов нулевые.
- HE-001: блокировок песочницы или попыток эскалации в этой работе не обнаружено. Сетевые операции GitHub работали; это подтверждение для данного класса задач, но не повтор старого сценария Python-тестов. Оставить MITIGATED до реальной задачи с тестами.
- HE-004/006: рост контекста и применимость medium для данного результата наблюдаются; экономия от сокращения истории или изменения reasoning не доказана сопоставимым сравнением. Не сравнивать напрямую с PR #117.
- HE-005/009: до изменений Project повторно запрошены field-list и item-list (пять пар вызовов); две попытки jq ошибочны из-за формы ответа, затем отдельно запрошены ключи, затем корректная выборка. Две ошибочные попытки заняли 12,41 с инструментального времени; также отдельный gh issue view с неподдерживаемым полем parent завершился ошибкой. Причина — неверное предположение о CLI-схеме, а не неисправность GitHub. Исключать повторную диагностику известных схем, сохранять независимый read-back после изменений. Минимальная мера при подтверждении повторяемости — короткая справка в существующем Skill decompose, без новых скриптов/gates.
- HE-010: GET user/issue-fields вернул HTTP 403 с указанием scope read:user. Первый Turn завершил остальные операции, оставив #140 Preparing. Во втором Turn выполнен gh auth refresh с read:user; четыре опроса процесса и одно ожидание sleep 30 с (около 45 с суммарного времени этих инструментов). Авторизация восстановлена; по отчёту агента значения Reasoning/Effort записаны и проверены, #140 Ready. Ожидание действий владельца не считать целиком устранимой потерей. Не добавлять обязательный preflight.
- Ограничения: экспорт охватывает несколько сессий; неизвестна его полнота относительно всей БД. Результат задачи зафиксирован по handoff агента, а не независимой проверке всех полей GitHub. Из-за реконструкции контекста и нулевых LLM-интервалов нельзя выводить точный состав payload, время LLM или причинную экономию всех токенов.

### Решения по повторяющимся наблюдениям

- **HE-001 MITIGATED:** development 449 LLM/420 TOOL, vdev 101 LLM/91 TOOL. В S16 сетевые операции GitHub успешны без эскалации; S13 содержит отдельный probe с отказом операции и эскалацией. В гостевой выборке нет полноценного продуктового прогона Python/Playwright, поэтому закрывать историческую проблему зависаний как проверенную нельзя.
- **HE-004 OPEN, приоритет P1 для границ сессии:** в S07 исходная реализация PR #117 продолжилась двумя административными Turn; итоговый контекст 198 052. В S08 после работы #131 отдельное исправление статусов #129/#130 унаследовало 236 630–240 773 токена; 5 генераций, 1 194 987 входных, 1 189 248 cached, $0,01473. Затем новая PR #137 началась с 242 485 токенов, достигла 244 196 и позже снизилась до 67 725. Это подтверждает накопление предшествующих задач, но не точный состав серверного payload и не измеренную экономию от сброса. **Минимальное действие:** отдельная сессия на независимый Issue/PR, существующий GitHub handoff вместо наследования всей истории, сохранять продолжение в той же сессии для одного связного задания. Не вводить принудительную compaction. Сравнить обычные следующие работы по входу, времени, качеству.
- **HE-005 OPEN:** S08 содержит 30 инструментальных событий с командами gh pr checks / gh run view / gh run watch и 10 sleep общей длительностью 140,7 с (не все sleep относятся к CI). В PR #137 одни и те же успешные проверки run 44444208472 читались повторно на неизменном HEAD, пока mergeStateStatus был BEHIND. После синхронизации новый run 44445234544 требовал новых проверок законно. Не устранять read-back после мутации, ожидание owner acceptance или проверки нового SHA. Оркестрацию ожидания фиксировать одним штатным watch точного run/HEAD при необходимости дождаться результата; применять существующую политику draft/ready, не пытаться исправлять ожидаемый draft gate. Не добавлять фоновые сервисы.
- **HE-009 OPEN, повторяемость подтверждена:** ошибки интерфейса GitHub в S07, S08, S16. Неподдерживаемые поля closingIssuesReferences и baseRefOid в gh pr view повторились в S07 и S08; в S08 также unknown flag --stat для gh pr diff, в S16 — parent для gh issue view и неверная форма collections jq. Отдельно S08 содержит две ошибки функций JS (TextEncoder и btoa недоступны), которые не следует смешивать с CLI. Минимальный кандидат: дополнить существующую справку decompose/execute-task проверенными командами/формами .fields/.items и ссылкой на нативные API отношений вместо неподдерживаемых полей; не дублировать справку между Skills, не создавать обёртку. Проверить на следующей релевантной задаче: отсутствуют известные ошибки, read-back сохраняется. Суммировать только подтверждённые повторы, не все обращения к GitHub.
- **HE-006 OPEN для сложных задач / DEFERRED для глобального изменения:** medium обеспечил заявленный результат S16, xhigh применялся даже в простых probes S01–S06 и уборке S12; снижение reasoning для одинаковой сложной задачи не проверялось. Использовать более лёгкий режим для коротких рутинных операций, если необходим агент; детерминированные команды и вычисления по возможности выполнять без LLM. Не делать вывод о качестве моделей из этих несопоставимых задач.

До выдачи задачи сверять место сервиса и нужный доступ; общие исследования и GitHub-операции с доступным коннектором выполнять в управляющем чате, локальному CLI оставлять узкие команды. Это уже соответствует roadmap, новую роль/инфраструктуру не вводить.
- **HE-002/003/007/008:** решения прежние. Вся выборка подтверждает ограничения времени; дубль реконструкции не превращать в экономию. Массовый экспорт успешно получен, но не ограничен одной сессией, поэтому отбирать по sessionId/Issue/Run и не считать все события одним запуском.

### Очередность практических улучшений

1. HE-011/004: применять существующую маршрутизацию и отдельные сессии независимых задач; не запускать искусственные исследования ради метрик.
2. HE-009: зафиксировать уже проверенные команды в одном существующем источнике инструкций (сначала сверить актуальные Skills; оформить отдельный review).
3. HE-005: точечное правило ожидания конкретного CI run и SHA; не нарушать необходимый read-back, draft/ready и owner acceptance.
4. HE-001: проверить на естественном продуктовом запуске в гостевой ОС; HE-006 — измерять только при сравнении сопоставимых результатов; HE-003 отложен, HE-002 ожидает upstream.

Ни одна из этих мер ещё не проверена контролируемым сравнением затрат/качества. Приоритеты — инженерное решение на основании наблюдаемого масштаба и низкой сложности мер, не гарантированный процент экономии.

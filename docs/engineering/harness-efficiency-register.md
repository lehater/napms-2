# Harness efficiency — реестр наблюдений и улучшений

Актуализировано: 2026-11-20. Область: агентный SDLC NAPMS 2.0, Codex CLI и его окружение.
Связь с существующим процессом: [SDLC improvement roadmap](sdlc-improvement-roadmap.md), [Issue #10](https://github.com/lehater/napms-2/issues/10).

## Назначение

Сохранить результаты исследований так, чтобы при повторном проявлении проблемы не проводить RCA с нуля. Цель — уменьшение времени и расхода ограниченных ресурсов при сохранении качества результата, а не сокращение контекста или рост доли кэша сами по себе.

Это исследовательский журнал, а не обязательная очередь исполнения и не нормативная конфигурация Harness. Принятые изменения процесса проходят обычное review; задачи на реализацию при необходимости ведутся в GitHub Issues. Сырые трейсы, payload, ключи и конфиденциальные сведения об окружении в публичный репозиторий не помещаются.

Статусы: **OPEN** — наблюдение/гипотеза требует проверки; **MITIGATED** — мера принята, эффект ещё не измерен; **WAIT_EXTERNAL** — ожидается внешнее исправление; **DEFERRED** — исследование отложено до появления оправданной возможности; **CLOSED** — вопрос исследован, решение и ограничения зафиксированы. Приоритет отражает очередность исследования, а не доказанный размер ущерба.

Перед новым RCA найти записи по симптомам и корневой причине. Если причина та же — дополнить запись доказательствами, версиями и статусом, не создавать дубль. Возобновлять отложенное исследование только при выполнении указанного условия.

## Исходная точка

- Исторический трейс задачи [PR #117](https://github.com/lehater/napms-2/pull/117): 210 событий (105 LLM, 104 TOOL, 1 AGENT), длительность около 32 мин 50 с; модель `gpt-6-luna`, reasoning `xhigh`.
- Суммарный вход около 10,59 млн токенов, доля кэша 98,33%; контекст одного вызова вырос примерно с 17,5 до 164,8 тыс. токенов. Расчётная стоимость Langfuse около $0,155; это не подтверждённое списание лимита подписки.
- E2E-сверка ZIP и Observations API v2: 210/210 ID, метрики 105/105, временные метки совпадают. Содержимое после учёта экранирования совпадает. Исторический трейс — не baseline нового гостевого окружения.
- Codex CLI 0.171.0 и Langfuse Tracing Plugin 0.4.3 — версии контрольного исследования контекста.

## Доказательства и границы выводов

### HE-001 — песочница

В историческом трейсе четыре попытки Python-проверок и диагностика заняли около 6 мин 50 с; соответствующий этап содержал 27 LLM-вызовов с расчётной стоимостью около $0,035. Не всё это время или стоимость доказанно потеряны. Вне песочницы 62 целевых теста прошли за 2,56 с. Отдельный эксперимент подтвердил запрет создания TCP-сокета в песочнице и успешное создание после разрешения; обычная Ubuntu и локальный Langfuse работали.

Владелец сообщил о переходе на гостевую ОС с полным доступом. Не добавлять специальное правило эскалации в проектный workflow без нового доказанного сбоя. Проверить следующий реальный запуск: повторные зависания по прежней причине отсутствуют, качество/проверки сохранены; безопасность хоста оценивается отдельно.

### HE-002 — дублирование базовых инструкций

Контрольный эксперимент с `CODEX_ROLLOUT_TRACE_ROOT`: одна копия базовых инструкций в захваченном исходящем клиентском запросе, одна в session metadata, одна в developer-сообщении rollout и две идентичные копии в реконструкции Langfuse (по 17 793 символа). Плагин объединяет эти два источника без дедупликации. Метрики токенов совпали с нативной телеметрией. Проверены версии плагина 0.4.2/0.4.3; механизм связан с [PR #91](https://github.com/langfuse/codex-observability-plugin/pull/91). Внешний баг [#20582](https://github.com/langfuse/langfuse/issues/20582) зарегистрирован и открыт на момент контрольного исследования.

Гипотеза избыточности фактического клиентского запроса не подтвердилась. Полный серверный контекст при `previous_response_id` не наблюдался. Не оценивать экономию токенов по удвоенному тексту Langfuse, не патчить плагин локально. Проверка после исправления: одна копия в реконструкции при неизменных корректных счётчиках.

### HE-003 — каталог возможностей

В локальном конфиге контрольного эксперимента явно включён только tracing-плагин, MCP-серверы не настроены. Наличие кешированных plugin-пакетов не доказывает активацию. Внешний контекст сессии содержал каталог Skills, рекомендации доступных плагинов и deferred tool namespaces; рекомендации не равны включённым плагинам. Один исходящий запрос содержал 3 namespace и 11 непосредственно объявленных инструментов.

Два контрольных запуска с одинаковым эффективным составом дали по 15 937 входных и 8 выходных токенов (кэш 0). Это проверка воспроизводимости, не содержательный A/B. Нельзя оценить экономию от отключения неиспользуемых возможностей. Не менять рабочую конфигурацию в отсутствие подтверждённой пользы.

### HE-004 — история и кэш

98,33% кэширования — доля повторно обработанного входа, не доказательство полезности каждого фрагмента или экономии от сокращения истории. Изучить рост контекста на актуальной задаче; при необходимости использовать Native Rollout Trace и сравнить сопоставимые запуски с проверенным качеством. Не выводить избыточность из одного размера или реконструированного system prompt.

### HE-005 / HE-006 — polling и reasoning

В исходном трейсе отмечено 16 обращений к данным PR #117 и 21 вызов `write_stdin`. Это наблюдения; ещё не установлено, сколько вызовов действительно можно исключить. 105 обращений в режиме `xhigh` также не означают, что режим избыточен. Сначала актуальные измерения по настоящим задачам, затем минимальные эксперименты только для существенных резервов.

### HE-007 / HE-008 — качество источников данных

У 97/105 генераций нулевой интервал; у 81 входа есть маркер пропущенной ранней истории. Эти ограничения присутствуют в Langfuse API, а не появились при скачивании ZIP. Внешний JSON экспорта валиден, но 45 вложенных GENERATION.input и 4 GENERATION.output не разбирались строго из-за управляющих символов. API возвращал экранированные значения; E2E не обнаружил потери содержания. Точный этап появления дефекта представления ZIP не установлен. Одноразовые локальные диагностические скрипты и отчёты удалены после фиксации результатов; постоянный валидатор не требуется.

## Следующий исследовательский шаг

Получить новый трейс реальной задачи в гостевой ОС. Использовать идентификаторы Issue/Run/Source SHA по [существующей процедуре](../../.ai/codex-task-tracing.md), если применимо. Сопоставить результат, качество и затраты с доступным историческим baseline; учесть различия задач, среды и режима reasoning. По актуальному трейсу выбирать следующий RCA по ожидаемой и измеримой пользе. Не повторять закрытые исследования без новых симптомов, версий или доказательств.

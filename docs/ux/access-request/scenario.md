## 1. User Problem & Goal

### 1.1. Бизнес-цель

Обеспечить сетевую коммуникацию, необходимую для выполнения существующего бизнес-процесса.

**Вход:** BusinessProcess и связанная с ним ConnectivityNeed.

**Желаемый конечный результат:** участвующие развёрнутые компоненты могут обмениваться необходимым сетевым трафиком.

Фактическая сетевая доступность требует отдельного подтверждения. Сохранение разрешения в NAPMS само по себе её не гарантирует.

### 1.2. Пользовательская цель

Получить авторизованное решение о разрешении конкретной коммуникации.

Заявитель должен:

1. Выбрать ConnectivityNeed.
2. Установить участников и точные параметры коммуникации.
3. Проверить доступную информацию о существующих заявках и разрешениях.
4. Подать AccessRequest.
5. Получить и проверить сохранённый результат решения.

**Успех пользовательского сценария:** заявка имеет прослеживаемое решение ALLOWED или DENIED. При ALLOWED система создаёт либо переиспользует канонический PolicyRule для точного AccessSubject.

**Граница:** ALLOWED и ACTIVE PolicyRule описывают декларированное разрешение, а не доказанную сетевую доступность.

### 1.3. Цель первоначального Mock UX-пилота (исторический этап)

Проверить, способен ли пользователь пройти понятный процесс от бизнес-потребности до результата решения, используя осмысленные названия объектов вместо ручного ввода UUID.

**Вход:** согласованный набор синтетических BusinessProcess, ConnectivityNeed, InteractionRevision, ComponentDeployment, AccessRequest и PolicyRule.

**Выход:** интерактивный сценарий с выбором объектов, имитацией подачи заявки, передачи её решающему субъекту и отображением результата.

Состояния и переходы моделируются локально. Создаваемые объекты, решения и полномочия являются демонстрационными и не считаются серверными фактами.

### 1.4. NID-first и Resource-first

| | NID-first | Resource-first J02 |
|---|---|---|
| Отправная точка | ConnectivityNeed | Resource |
| Известный контекст | Бизнес-потребность | Исходный ресурс |
| Требуется определить | Revision и Deployments | Need, Revision и destination |
| Результат | Exact AccessSubject и AccessRequest | Тот же |

**Решение:** это два маршрута к одной пользовательской цели. Они используют одинаковые доменные инварианты и сходятся в общем процессе формирования заявки.

Для первого UX-пилота выбирается NID-first. Resource-first сохраняется как существующий маршрут J02, без отдельного пилота.

## 2. Scope и участники

### 2.1. Участники сценария

| Участник | Ответственность |
|---|---|
| **Заявитель (Requester)** | Выбирает предмет доступа, обоснование и подаёт заявку |
| **Решающий субъект (Decider)** | Независимо рассматривает PENDING-заявку и принимает ALLOWED/DENIED |
| **NAPMS** | Проверяет совместимость и полномочия, сохраняет заявку, решение и Rule согласно доменным контрактам |

В mock-пилоте действия NAPMS и полномочия участников симулируются.

В real-сценарии создание заявки требует effective `access.request` на исходный Resource, решение — отдельного `access.decide`. Ответственность за Resource и принадлежность к бизнес-процессу не предоставляют этих полномочий.

### 2.2. Границы

**Входит:** выбор Need, направленной Interaction, immutable Revision, source/destination Deployments, составление заявки, просмотр доступной истории, PENDING, ALLOWED/DENIED, переход к PolicyRule.

**Не входит:** CRUD каталогов, изменение Revision, прямой CRUD PolicyRule, отзыв/реактивация Rule, сбор сетевых данных, применение ACL, оценка фактической доступности и реализация backend.

### 2.3. Синтетический предмет сценария

| Понятие | Пример |
|---|---|
| BusinessProcess | Settlement |
| ConnectivityNeed | Запись бухгалтерской операции |
| Application | Order-to-Ledger |
| Interaction | OrderClient → LedgerApi |
| InteractionRevision | rev-1, TCP / destination 443 |
| Source Deployment | OrderClient на order-api-01 |
| Destination Deployment | LedgerApi на ledger-api-01 |

Идентификаторы `mock-*` остаются локальными тестовыми ссылками. Данные не переносятся в SQLite и не выдаются за реальный доменный каталог.

## 3. Основной Task Flow

### 3.1. Заявитель — формирование и подача

| Шаг | Действие | Реакция интерфейса | Результат |
|---|---|---|---|
| R01 | Открывает «Потребности в коммуникациях» | Показывается коллекция доступных Need | Контекст найден |
| R02 | Выбирает ConnectivityNeed | Открывается Need Detail с BusinessProcess и назначением | Need выбрана |
| R03 | Изучает направленную Interaction | Отображаются source/destination Component и Application | Направление установлено |
| R04 | Выбирает InteractionRevision | Показываются точная Revision и её traffic semantics | Revision зафиксирована в выборе |
| R05 | Выбирает source Deployment | Показаны допустимые исходные варианты | Источник определён |
| R06 | Выбирает destination Deployment | Показаны совместимые целевые варианты | Назначение определено |
| R07 | Просматривает контекст существующих заявок/правил | Показываются доступные состояния, история и ограничения видимости | Пользователь понимает контекст повтора |
| R08 | Проверяет summary и подтверждает подачу | Моделируется создание самостоятельной PENDING-заявки | Request создан в mock-state |

**Проверка перед R08:**

`AccessSubject = (sourceDeploymentId, destinationDeploymentId, interactionRevisionId)`

Показываются направление, имена ресурсов и компонентов, точная Revision, параметры трафика и бизнес-основание.

Need не входит в identity AccessSubject. IP-адреса также не входят в identity.

При единственном варианте Interaction, Revision или Deployment интерфейс может сделать предварительный выбор. Перед отправкой результат должен быть виден пользователю.

### 3.2. Передача заявки решающему субъекту

После R08 заявка получает состояние PENDING и становится элементом коллекции «Заявки на доступ».

В mock-пилоте пользователь вручную переключает демонстрационную роль с Requester на Decider и открывает коллекцию заявок.

Это **симуляция двух независимых участников**, а не реальная аутентификация или делегирование полномочий.

Никакие уведомления, очереди сообщений или автоматическое назначение задач не предполагаются.

### 3.3. Решающий субъект — принятие решения

| Шаг | Действие | Реакция интерфейса | Результат |
|---|---|---|---|
| D01 | Открывает «Заявки на доступ» | Видит доступные PENDING-заявки | Заявка обнаружена |
| D02 | Открывает Request Detail | Видит Need, exact subject, заявителя и основание | Предмет проверен |
| D03 | Выбирает ALLOWED или DENIED | Требуется явное подтверждение | Решение инициировано |
| D04 | Подтверждает решение | Моделируется неизменяемое терминальное решение | Request → ALLOWED/DENIED |
| D05 | Проверяет результат | Отображается Decision и связь с Rule при ALLOWED | Решение зафиксировано |

При ALLOWED моделируется создание ACTIVE Rule либо переиспользование существующего Rule для exact subject.

При DENIED новый Rule не создаётся. Существующее правило не отзывается.

### 3.4. Заявитель — получение результата

Заявитель снова открывает коллекцию «Заявки на доступ» или сохранённую карточку Request Detail и обновляет представление.

- Если PENDING сохраняется, решение ещё не представлено.
- Если ALLOWED, отображаются Decision и ссылка на канонический `policyRuleId`.
- Если DENIED, отображается терминальный отказ без нового Rule.

В mock-пилоте обновление читает локальное моделируемое состояние. В real-интеграции результат должен поступать из авторизованного серверного чтения.

Доступ к защищённой карточке PolicyRule рассматривается отдельно от права видеть результат собственной заявки.

## 4. Wireflow первого UX-пилота

**Маршрут заявителя**

`S01 Need Collection → S02 Need Detail [выбор Revision и Deployments → просмотр существующего состояния → подтверждение] → S04 Request Detail [PENDING]`

**Передача решающему субъекту**

`PENDING → переключение демонстрационной роли → S03 Request Collection → S04 Request Detail [проверка → ALLOWED / DENIED → подтверждение]`

**Получение результата заявителем**

`S03 Request Collection → S04 Request Detail [терминальный Decision] → S05 PolicyRule Detail [только при ALLOWED и доступной детализации]`

**Альтернативный путь**

`S02 [невозможен выбор / ошибка] → исправление выбора либо возврат к S01`

При DENIED путь завершается в S04. Пользователь может инициировать новую самостоятельную заявку через S02.

S02 включает составление заявки. **Отдельный экран Access Request Composition не создаётся.**

## 5. Existing State Matrix — повторная подача

Существующая заявка и существующий Rule — независимые факты. Для одного exact subject возможны несколько исторических заявок и одно каноническое Rule.

Матрица ниже определяет поведение при условии, что соответствующая информация доступна пользователю.

| Состояние перед подачей | Что видит пользователь | Зачем может потребоваться новая заявка |
|---|---|---|
| **Нет видимых Request/Rule** | Отсутствие записей в доступной области; кнопка подачи | Первичное обращение, если отсутствие подтверждено |
| **PENDING** | Существующая заявка, её дата, заявитель и отсутствие терминального решения | Другая Need, отдельное бизнес-обоснование или осознанное повторное обращение |
| **DENIED** | Терминальный отказ, предмет и доступное основание решения | Новое самостоятельное обращение после пересмотра потребности либо изменения предмета |
| **ACTIVE Rule** | При наличии права чтения — существующее декларированное разрешение, exact subject и provenance | Новое обоснование или независимое решение; не для автоматического восстановления уже разрешённой связи |
| **INACTIVE Rule** | Сохранённое, но неактивное правило, если разрешено чтение | Получить новое решение по потребности; пользователь предупреждён, что ALLOWED не активирует Rule |
| **Повторное ALLOWED для same subject** | Новая ALLOWED-заявка и прежний `ruleId` | Сохранение дополнительного самостоятельного decision evidence |
| **DENIED при существующем ACTIVE/INACTIVE Rule** | Отказ по новой заявке и неизменное состояние старого Rule | Отдельное рассмотрение нового обращения; предыдущий Rule не отзывается |
| **Нет применимой Revision** | Отсутствие подходящих вариантов и недоступная отправка | Сначала требуется корректный профиль коммуникации вне данного flow |
| **Нет совместимого Deployment** | Отсутствие подходящего участника и недоступная отправка | Сначала требуется актуализация каталога вне данного flow |
| **Нет права request на source** | Недоступное действие или моделируемый отказ в допуске | Нужны надлежащие полномочия; DENIED не создаётся |

### Правила UX при повторной подаче

1. Показывать известные совпадения по exact subject, а не только по названию Need.
2. Явно различать повтор по тому же subject и заявку с изменённой Revision или участниками.
3. При существующем PENDING предлагать сначала открыть заявку; повторную подачу не запрещать автоматически.
4. При ACTIVE Rule предупреждать о существующем декларированном разрешении, не обещая фактической сетевой доступности.
5. При INACTIVE Rule предупреждать, что повторный ALLOWED не реактивирует правило.
6. Не изменять прежние Requests, Decisions или Rule при повторной подаче.

Предупреждения информируют пользователя, но не вводят дополнительные доменные запреты.

## 6. Отображение доступности информации

Интерфейс должен различать четыре ситуации.

| Ситуация | Значение | UX-поведение |
|---|---|---|
| **Доступные сведения** | Данные получены из разрешённой области | Отображаются факты и доступные действия |
| **Подтверждённое отсутствие** | В проверенной доступной области записей нет | «Записи не найдены» |
| **Доступ ограничен** | Известно, что операция чтения запрещена, либо сведения не раскрываются | «Недостаточно прав для просмотра» или нейтральное ограничение без раскрытия деталей |
| **Состояние неизвестно** | Данные не загружены, запрос завершился ошибкой или полнота не установлена | «Не удалось определить состояние» с повтором чтения |

**Критическое различие:** «Rule отсутствует» и «Rule не доступен для просмотра» неэквивалентны.

Пустая коллекция после ограничения видимости подтверждает только отсутствие *видимых* объектов, а не отсутствие всех объектов системы.

### Mock UX

Синтетические fixtures могут моделировать все четыре ситуации, включая ограничение доступа. Каждый результат обусловлен явно заданным тестовым состоянием.

Mock-переключатель роли не является проверкой настоящего `access.request`, `access.decide` или `policy.export`.

### Future Real Integration

Правила server-side catalog visibility, допустимые destination metadata, фильтрация по полномочиям и защита от раскрытия существования скрытых объектов являются отдельными архитектурными решениями.

UX-контракт не определяет новую IAM-модель и не объявляет source-only `access.request` универсальным правом чтения каталогов.

## 7. Screen Inventory

### Минимальная композиция

Для пилота используются существующие типы представлений UI/IA Baseline v0.2.

| Экран | Назначение и вход | Отображение и действия | Результат |
|---|---|---|---|
| **S01. ConnectivityNeed Collection** | Поиск Need | Название, процесс, назначение, доступный статус; поиск и открытие карточки | Выбрана Need |
| **S02. ConnectivityNeed Detail** | Need + синтетические связи | Обзор, Communication/Revision, выбор Deployments, доступная история, summary, подтверждение подачи | Новый mock PENDING Request |
| **S03. AccessRequest Collection** | Список видимых заявок | Статусы, даты, предмет, переход в карточку; представление заявителя/решающего субъекта | Найдена нужная Request |
| **S04. AccessRequest Detail** | Request ID | Subject, Need, admission, Decision; для Decider на PENDING — подтверждение ALLOWED/DENIED | Терминальное решение |
| **S05. PolicyRule Detail** | Rule ID и доступность | Exact subject, ACTIVE/INACTIVE и provenance; read-only | Проверено известное состояние Rule |

S05 — существующий тип карточки раздела «Правила политики», а не новый экран для сценария. Его содержимое в mock может моделировать разрешённый просмотр и ограничение доступа.

### S02 — ключевая композиция

**Вкладка «Обзор»:** ConnectivityNeed, BusinessProcess, бизнес-основание.

**Вкладка «Коммуникация»:** направленная Interaction, роли Component, применимые immutable InteractionRevision и выбираемые source/destination ComponentDeployment.

Здесь же размещается компактный блок **«Запросить доступ»**, содержащий summary выбора, информацию о существующих заявках/разрешениях и действие подтверждения.

**Вкладка «Заявки»:** связанные видимые Requests с состояниями и переходами на S04.

Дополнительный мастер, modal wizard или новый пункт Sidebar для составления заявки не требуется.

### Ошибки и пустые состояния

- S01: нет доступных Need, ошибка получения списка.
- S02: нет Revision, нет совместимых Deployments, невалидная комбинация, недоступная информация, ошибка подачи.
- S03: нет видимых Requests, ошибка чтения, ограничение видимости.
- S04: PENDING, ALLOWED, DENIED, запрет решения, конкурентное завершение, ошибка чтения.
- S05: ACTIVE, INACTIVE, отсутствие Rule, недостаточно прав, неизвестное состояние.

## 8. Соответствие домену и UI Baseline

### Действующие доменные инварианты

| Инвариант | UX-проявление |
|---|---|
| Need обосновывает Interaction, но не permission | В S02 бизнес-основание отдельно от разрешения |
| Interaction направлена | Source и destination различаются визуально и семантически |
| Revision immutable | Показывается и выбирается точная Revision |
| Subject — exact ordered triple | Summary фиксирует участников и Revision |
| IP и Need вне subject identity | Изменение адреса/Need не переименовывает subject |
| Source-only request admission | Подача не требует destination request grant |
| Independent decision authority | Решение выполняет отдельный Decider |
| Request admission ≠ ALLOWED | PENDING не отображается как разрешение |
| DENIED ≠ revoke | Отказ не изменяет существующий Rule |
| Repeated ALLOWED ≠ new Rule | Повторное решение использует прежний `ruleId` |
| INACTIVE ≠ automatically ACTIVE | Повторный ALLOWED не меняет состояние Rule |
| Effective Policy — computed | Не создаётся отдельная хранимая сущность или Sidebar-пункт |

## 9. UX Acceptance Criteria — Mock UX (первоначальный этап)

Изначально проверялись на согласованном наборе синтетических данных, без реального API, IAM и постоянного хранения. Эти критерии описывают MOCK-контракт и не заменяют приёмку текущих REAL-срезов.

| ID | Критерий приёмки |
|---|---|
| M-01 | Пользователь находит Need по осмысленному названию и открывает S02 |
| M-02 | S02 показывает бизнес-основание и правильное направление Interaction |
| M-03 | Можно выбрать точную Revision, source и destination Deployment без ввода UUID |
| M-04 | Summary перед подачей явно показывает Need, exact subject и traffic |
| M-05 | Некорректные комбинации и отсутствие вариантов представлены понятными состояниями |
| M-06 | Перед повторной отправкой показаны состояния PENDING, DENIED, ACTIVE и INACTIVE и их последствия |
| M-07 | Подтверждение моделирует самостоятельную PENDING-заявку, доступную в S03/S04 |
| M-08 | Переключение демонстрационной роли позволяет пройти отдельный Decider flow без имитации реальной авторизации |
| M-09 | ALLOWED/DENIED моделируют независимые терминальные решения и правильное поведение Rule |
| M-10 | Заявитель может повторно открыть Request и увидеть итог; при ALLOWED — доступную ссылку на Rule |
| M-11 | Различаются empty, unknown и restricted состояния (**DEFERRED, не PASS; не блокирует ближайшие реальные функциональные срезы**) |
| M-12 | Все переходы выполняются в композиции Baseline v0.2 без новых разделов и экранов составления заявки |

**Актуализация 2026-11-12:** первый NID-first Mock UX-пилот принят; в `main` уже реализованы REAL BusinessProcess и AccessRequest/Decision с React/FastAPI/SQLite и серверными grants (PR #44–#46). Полный NID-first путь через выбор Need/Revision/Deployments остаётся вне текущего REAL-покрытия. `M-11` перенесён на поздний Visibility UX и не засчитывается как выполненный. Реальная серверная авторизация и применимые `RI-07/RI-08`, `SG-01…SG-06` обязательны **сейчас**, для каждого предоставленного API/read path; расширенные UX-состояния не заменяют защиту данных. См. [принятый порядок работ](../../product.md#принятый-порядок-дальнейшей-продуктовой-разработки-решение-2026-11-10-актуализировано-2026-11-12).

**Минимальная последовательность проверки:** создать mock PENDING → переключиться на Decider → ALLOWED → вернуться к Requester → увидеть Decision и Rule; затем проверить DENIED и основные повторные/ошибочные состояния.

Долговременное сохранение после перезапуска браузера и реальные server grants не входят в Mock UX acceptance.

## 10. Acceptance Criteria — Real Integration (поэтапно)

Эти критерии относятся к **полному реальному NID-first сценарию**, а не к уже завершённому mock-пилоту. Отдельные backend-операции заявки, решения и хранения реализованы, но доступный REAL UI не покрывает весь путь через Need/Revision/Deployments. Статус каждого критерия подтверждается применимым end-to-end срезом; наличие частичной реализации не означает PASS всей таблицы.

| ID | Критерий |
|---|---|
| RI-01 | Варианты Process/Need/Revision/Deployment получены из авторизованного server-backed read path |
| RI-02 | POST создаёт реальную PENDING-заявку с серверной повторной проверкой полномочий и предметной совместимости |
| RI-03 | Request сохраняет immutable subject, Need, заявителя, время и admission evidence |
| RI-04 | Decider с действительным `access.decide` принимает единственное терминальное решение |
| RI-05 | ALLOWED создаёт либо переиспользует канонический Rule; DENIED не создаёт и не отзывает Rule |
| RI-06 | После перезагрузки S04 восстанавливает Need, exact subject, состояние и доступный Decision из серверного хранения |
| RI-07 | Списки и детали показывают только разрешённые сведения; ограничения реализованы сервером |
| RI-08 | Rule Detail требует действующих полномочий `policy.export` на оба Resource |
| RI-09 | Проверена сохранность состояния после перезапуска backend на той же БД, включая повторные заявки и решения |
| RI-10 | Реальный E2E проходит без использования `mock-*` объектов, фиктивных данных и ручного ввода четырёх UUID |

## 11. Real Integration — Security Gates

Эти требования обязательны **для каждого применимого действующего и нового REAL API/read path** до его приёмки. Уже реализованные проверки `business.process.read/create`, `access.request`, `access.decide` и `policy.export` сохраняются; отсутствие расширенного Visibility UX (M-11) не ослабляет grants, ограничения выдачи данных и отрицательные security-тесты. Для ещё не реализованных Need/каталоговых read models требования применяются при вводе соответствующих операций.

| Gate | Приоритет | Требуемое решение |
|---|---|---|
| SG-01. Catalog visibility | P0 | Определить серверную область видимости BusinessProcess, Need, участников и destination metadata; исключить раскрытие чужих данных |
| SG-02. Submission integrity | P0 | Серверная проверка Need/Interaction/Revision/Deployment и source-only `access.request` при фактическом POST |
| SG-03. Decision authority | P0 | Независимый `access.decide`, защита единственного терминального решения и корректная обработка конкуренции |
| SG-04. Protected rule read | P0 | Не предоставлять Rule Detail в обход `policy.export` на оба Resource |
| SG-05. Read-model disclosure | P0 | Исключить утечки скрытых ID, counts и metadata через discovery, pagination и ошибки |
| SG-06. Reconstructible details | P1 | Согласовать авторизованный DTO для восстановления Need и exact subject после reload |

Issue #37 и Draft PR #38 содержат исследовательское предложение read model. Их решения не считаются принятыми до согласования.

Новые OpenSpec-требования этим UX-контрактом не вводятся.

## 12. UX-вопросы исходного mock-пилота P1–P3 (исторический контекст)

| Приоритет | Вопрос | Рекомендация |
|---|---|---|
| P1 | Достаточна ли встроенная форма S02 при нескольких Revision и Deployments? | Проверить на интерактивном mock; отдельный экран только при обнаруженной сложности |
| P1 | Понятны ли пользователю PENDING/ALLOWED/DENIED относительно ACTIVE/INACTIVE? | Проверить сценарии с повторным запросом и прежним Rule |
| P1 | Понятно ли, что ALLOWED не гарантирует сетевую доступность? | Проверить трактовку результата в Request/Rule Detail |
| P2 | Насколько подробно показывать историю заявок в S02? | Сначала компактные состояния и ссылки на S04; расширять после пилота |
| P2 | Как показывать длинные списки совместимых Deployments? | Начать с ограниченных синтетических данных; оценить необходимость поиска |
| P3 | Наименования меток и полей | Следовать UI/IA v0.2 и принятой доменной терминологии |

## 13. Решение для координатора (исторический этап UX-пилота, 2026-11-09)

**Предлагается принять как основу первого UX-пилота:**

- NID-first как основной маршрут.
- Пять существующих типов представлений, без отдельного экрана составления заявки.
- Два независимых участника: Requester и Decider.
- Синтетические интерактивные состояния с корректными доменными последствиями.
- Разделённые Mock UX и Real Integration критерии.
- Security gates как самостоятельные обязательства применимого real-среза.

**Исторический результат:** контракт послужил входом для интерактивного mock UX-пилота. Актуальная разработка ведётся реальными вертикальными срезами по [продуктовой стратегии](../../product.md#принятый-порядок-дальнейшей-продуктовой-разработки-решение-2026-11-10-актуализировано-2026-11-12); документ сам по себе не добавляет требований OpenSpec и не расширяет объём реализации.

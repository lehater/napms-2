# Основная навигация перед продуктовой приёмкой

Решение владельца для PR #55 заменило общую семиколлекционную навигацию UI/IA Baseline v0.2 на рабочую навигацию. Issue #64 добавил группу каталогов приложений и развёртываний; change `real-resource-endpoint-catalog` добавляет Resource. Текущий REAL Sidebar содержит маршруты из [`web/src/main.tsx`](../../web/src/main.tsx):

| Группа | Пункт | Маршрут |
| --- | --- | --- |
| Бизнес-контекст | Бизнес-процессы | `/business-processes` |
| Каталоги | Ресурсы | `/resources` |
| Каталоги | Профили приложений | `/applications` |
| Каталоги | Развёрнутые компоненты | `/deployments` |
| Управление доступом | Заявки на доступ | `/access-requests` |
| Управление доступом | Правила политики | `/policy-rules` |

Потребности открываются через вкладку соответствующего процесса. Выбор строки открывает карточку `/business-processes/{pid}/needs/{nid}`. На действующем экране активной потребности при активном процессе композиция заявки открыта во вкладке «Обзор». Вкладка `?tab=requests` ведёт к истории. Полный состав заявки показан перед отправкой.

Правило политики — отдельная REAL-карточка `/policy-rules/{ruleId}`, доступная по серверной ссылке из ALLOWED заявки. Коллекция `/policy-rules` показывает доступные канонические ACTIVE/INACTIVE правила, подписи и трафик. Доступ требует `policy.export` на оба ресурса. Выгрузка доступной текущей политики содержит только авторизованные ACTIVE правила; глобальная полнота не заявляется. На карточке сохранены Rule ID при смене actor, breadcrumbs и возврат к коллекции правил, включая состояние 403 для Decider до переключения на Exporter.

Пункт «Ресурсы» ведёт к коллекции, созданию и деталям Resource/Endpoint с реальными связанными Deployments. Пункт «Профили приложений» ведёт к Application/Component/Interaction, а «Развёрнутые компоненты» — к ComponentDeployment и связанным Resource. Sidebar не показывает неработающие коллекции, учебные ссылки или отдельные метки REAL/MOCK. Сохранены группировка, активный пункт (включая контекст Rule в управлении доступом), контраст, изменение ширины 200–360 px, клавиатура/указатель и мобильная компоновка. Прежний ключ предпочтения ширины сохранён для совместимости.

Исторические UX-материалы прототипа сохранены в документации. В текущем runtime отсутствуют маршруты `/prototype/*` и клиентские mock-коллекции: это подтверждает [README.md](../../README.md), а действующая навигация перечислена выше и задана в [`web/src/main.tsx`](../../web/src/main.tsx). Исторические описания прототипа не задают рабочее поведение.

Рабочие пункты навигации и семантические инварианты зафиксированы в [JSON-контракте](../contracts/ux-0-semantic-boundaries.json), который также запрещает маршрут `/prototype`. Исторические UX-материалы сохраняются; требования каталогов описаны в OpenSpec changes `real-application-deployment-catalogs` и `real-resource-endpoint-catalog`.

## Целевая навигация ConnectivityNeed (#140)

Контракт для #141–#143 вводится поэтапно после приёмки владельцем. В реализованном Sidebar выше перечислены пункты текущей версии. Обновление рабочего JSON-контракта и меню входит в #141. Историческое решение PR #55 исключало отдельный вход в Needs. Новый вход ограничен реальной коллекцией доступных потребностей. [Проект UX/API и источники данных](../../openspec/changes/connectivity-need-workspace/design.md)

| Вход или действие | Адрес и возврат |
| --- | --- |
| Sidebar → Бизнес-контекст → Потребности (#141) | `/connectivity-needs?offset=N`. Строка ведёт в существующую карточку. Активный пункт при таком входе — «Потребности». |
| Бизнес-процессы → процесс → Потребности (#141) | `/business-processes/{pid}?tab=needs&needsOffset=N`. Параметр `offset` здесь по-прежнему обозначает страницу родительской коллекции процессов. Активный пункт — «Бизнес-процессы». |
| Создать потребность (#142) | `/connectivity-needs/new` из реестра, с `processId={pid}` из процесса. Отмена возвращает на исходную страницу списка. После 201 открыть карточку сохранённого ID с тем же контекстом возврата. |
| Карточка (#141, вкладки в #143) | `/business-processes/{pid}/needs/{nid}`, вкладки `?tab=overview`, `?tab=communication`, `?tab=requests&offset=N`. Вкладки, reload и breadcrumbs сохраняют исходный список. Без контекста — возврат к вкладке потребностей указанного процесса. Несовпадение pid/nid даёт 404 по действующему detail API. |
| Создать заявку (#143) | `/business-processes/{pid}/needs/{nid}/requests/new`. Отмена ведёт в ту же карточку и вкладку, 201 — в сохранённую заявку. История остаётся во вкладке «Заявки». |

Чтобы ссылки работали и после reload, в переходах передавать только тип источника (`from=registry` или `from=process`) и валидные числовые смещения. Для возврата различать страницу реестра/Needs (`listOffset`), коллекции процессов (`processOffset`) и истории заявок (`offset`). Для отмены композиции сохранять исходную вкладку и смещение истории. Хлебные крошки из реестра ведут на «Потребности», из процесса — на процесс и его вкладку. Параметры возврата описывают навигацию, права каждого чтения проверяет сервер.
